# docs/book/ — 本仓库技术书

## 这是什么

`docs/book/` 不是代码说明书，不是 API 文档，不是行号索引。这是一本**关于自动驾驶中间件设计思想**的书。

读这本书的目标：
- 理解这个仓库里**为什么**是这样设计（而不是 API 怎么调用、行号在哪里）
- 在自己写类似系统时，能判断哪些设计值得借鉴、哪些是坑
- 跨章节看到**领域内反复出现的取舍**（一致性 vs 延迟、解耦 vs 协调、安全 vs 性能）

**这书不**：
- 不替你读代码。读完一节你应该想去翻代码，但代码永远比文字新
- 不绑行号与文件名。`grep` 比翻章节快，章节的价值在思想
- 不复述 API。`include/*.h` 是 API 的真源
- 不掩盖权衡。每个决策都附"另一种选择是什么、为什么没选"

## 写作风格约束（commit 前自检清单）

每章/节写完后，逐条对照：

### ❌ 不要写这些

- **行号引用**：`foo.cpp:324` `bar.h:42-58` —— 代码会动，行号会腐化
- **函数符号全名大段罗列**：`foo_serialize` / `foo_deserialize` / `foo_swap` —— grep 比读章节快
- **魔术数字清单**：`MSG_BUS_MAX_DATA_SIZE = 65536`、`TTL_THRESHOLD = 2.5s` —— 数字在头文件里
- **代码逐行解读**："第 N 行 if (...) {...}" —— 这是给同事讲代码，不是写书
- **"按源码逐条重建"** —— 违背"书应超越代码"的初衷
- **50+ 行的对比表** —— 表格在 PR 描述里能动态更新，在书里只会腐化

### ✅ 应该写这些

- **设计动机**：当初面对什么问题、为什么选 A 而不是 B
- **取舍故事**：性能 vs 安全、一致性 vs 延迟、灵活性 vs 简单性
- **领域常识**：定位融合为何用 EKF 而不是粒子滤波；为什么控制循环比规划快 10 倍
- **失败模式与防御**：哪些 corner case 被踩过、为什么加这条保护
- **跨章节串联**：第 8 章的状态机和第 14 章的行为决策共享了什么抽象
- **行业坐标**：与 Apollo / autoware / Tesla 的差异在哪
- **作者立场**：明确"我不确定" / "这是经验之谈，不是教科书真理" / "2026 年仍是这样，未来可能变"

### 字数控制

- 章节总长 **300~600 行**（含代码示例）
- 单节 **50~150 行**
- 单段 **不超过 10 行**

## 章节命名

每个新章节命名遵循 `NN_topic_phrase.md`：

| 文件名 | 真实章节号（BOOK.md 维护） |
|---|---|
| `00_preface.md` | 序 |
| `07_serializer.md` | 类型安全的零拷贝序列化 |
| `13_sensor_fusion.md` | 传感器融合：从卡尔曼到 EKF |

如果重排后文件名与 BOOK.md 章节号对不上——**BOOK.md 是真源，文件名跟随**（不要反过来）。

## v1 → v2 迁移

**v1（已归档）**：`docs/_archive/book_v1/`。内容按源码逐条重建、绑定行号。
**v2（本目录）**：按本 README 风格重写。轻装上阵，每章只讲一个核心思想。

迁移期策略：
- 已重写的 v2 章进入 `docs/`，删除 `docs/_archive/book_v1/` 对应文件
- 未重写的章节暂时保留 `docs/book/old_<n>_<topic>.md`，标注"待 v2 重写"
- BOOK.md 索引指向**当前真源**（v2 章节优先，archive 章节标注历史）

## 编辑纪律

- **不在 PR 中间改 docs/book/**：每次重写一整章；不要小步编辑（会留下半新半旧）
- **作者自报**：commit body 写明"为什么这一章要存在" / "v1 的哪一条内容搬到这里"
- **CI 守门**：`tools/gates/book_guard.py` 监控每章行数突变（>20%）、行号密度（>5 个 `:NNN` 引用）、函数符号密度（>10 个）

## 何时不写 docs/book/

- 修复一个 bug → 写到 commit message 或 release note，不写书
- 新增一个 API → 写到 `include/*.h` 注释，不写书
- 跨多章节的概念 → 写一节 `cross-cutting/<topic>.md`，不重写各章节
- 临时讨论 → 写到 `docs/_reports/`，归档时考虑是否升格为书

## 参考书目（真技术书范式）

- **《Designing Data-Intensive Applications》**（Martin Kleppmann）—— 用真实生产事故讲取舍
- **《Operating Systems: Three Easy Pieces》**（Arpaci-Dusseau） —— 用"为什么"代替"是什么"
- **《The Pragmatic Programmer》** —— 经验格言 + 反模式 + 类比
- **《C++ Concurrency in Action》**（Anthony Williams）—— 思想 + 图示 + 关键代码片段（非全本）

我们要接近的目标是 DDIA 的"思想密度"而不是 OS-3EP 的"教学耐心"。
