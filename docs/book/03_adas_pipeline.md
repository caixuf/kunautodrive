# 卷三 · 第三课：让车学会安全地超车

## 本章问题

现在你的车会往前开了（卷一），15 个模块会互相说话了（卷二）。但这辆车只会「直着开」。

给它一个真正的任务：**前面有一辆慢车，你要超过它，然后在它前面回到原车道。** 你会
发现，这一个任务把自动驾驶的所有问题都逼出来了：

- 车得**看见**前车（它多快？离我多远？它占了我旁边的车道吗？）；
- 车得**决定**该不该超（距离够吗？旁边车道空吗？我现在的速度合适吗？）；
- 车得**算出一条路**（往左偏多少？什么时候打方向盘？什么时候回正？）；
- 车得**执行**（方向盘打多少？油门踩多少？）；
- 车还得**不出事**（如果超到一半，前车突然刹车怎么办？）。

这就是一条完整的算法链。这一章带你从头走到尾——不跳步，每一步都先问你「你会怎么做」，
再看「系统为什么这么做」。

## 先看全貌：一个任务，五个角色

还是那辆超车任务。把它拆开，你会发现五个角色各管一段，**谁也不越界**：

```
感知    看见：前车在 30 米外，速度 8 m/s，在我这条车道
决策    决定：前车太慢，我要变到左车道超它
规划    算路：未来 3 秒，轨迹先左偏 3.5 米，速度保持 12 m/s
控制    执行：方向盘 0.05 弧度，油门 30%
安全    兜底：如果离前车 < 5 米，不管谁的命令，先刹车
```

**这五个角色，就是全书反复讲的「职责铁律」的来处。** 先记住一个判断标准：**任何一个
角色做了它不该做的事，系统迟早会在某个深夜出 bug。** 后面每一步，我都会指出「如果
它越界会发生什么」。

## 第一步：感知——车怎么「看见」前车

### 你自己的答案

你会怎么做？最朴素的想法：直接问仿真「前面有没有车」。但这在真实世界里行不通——真实
的车没有上帝视角，它只有传感器（雷达、相机），而传感器的数据是**带噪声的、可能遮挡
的**。

### 为什么不够

如果算法在仿真里「直接读真值」，那么它练出来的本领到了真车上**全部失效**——因为真车
的传感器不给它真值。所以系统刻意加了一个 `sensor_model` 层：**把真值伪装成带噪声的
传感器数据**（加高斯噪声、做 FOV 裁剪、视线遮挡）。这不是「多此一举」，而是「让算法
从第一天起就学会跟不完美的传感器打交道」。

### 真正的方案：从点云到「有 3 辆车」

LiDAR 扫出来的是一堆点云——几万个小点，你得从里面找出「这是几辆车、分别在哪」。项目
用的是 **DBSCAN 聚类**：密度高的点聚成一簇，一簇 = 一个障碍物。配合 RANSAC 把地面
点去掉（地面不是障碍物）。

**关键点：感知只输出「盒子」（障碍物列表），不输出「这是什么」**（那是语义，另说）。
下游拿到的就是一个带位置、速度、尺寸的盒子列表。DBSCAN 的好处是不需要预先知道有几辆
车——你不知道点云里有 3 辆车还是 30 辆车，DBSCAN 自己从密度找。

### 一个感知的「隐性缺陷」：漏检不报错

停下来想一个可怕的问题：如果 DBSCAN 漏掉了一辆车，会发生什么？

什么都不会发生——**没有报错，没有异常，那辆车就像不存在一样。** 感知是整条链里唯一
「漏了不吭声」的环节：控制错了会抖动、规划错了会画奇怪的线，但感知漏了，一切照常，
只是那辆车不存在了。这就是为什么感知要做得保守（宁可多报，不可漏报），也是为什么
后续会往「占据网络」演进（卷十展望里有讲）——**直接把空间填满，而不是数盒子。**

## 第二步：决策——车决定「该不该超」

### 你自己的答案

拿到障碍物列表，最朴素的决策规则：

```
if (前车速度 < 我的巡航速度) → 变道超车
```

### 为什么不够

真实世界里，这条规则会害死你：前车只是**暂时**慢（马上要转弯），旁边车道有车
（你变过去就撞），前面马上是红灯（你超过去还是要停），旁边是实线。**「该不该超」
不是一个 if，而是一个需要综合很多条件的判断。**

### 真正的方案：有限状态机（FSM）

系统把决策建模成**有限状态机**：车永远处于 8 个状态之一，每个「事件」触发「状态转移」。

```
CRUISE（巡航）──(前车太慢，旁道可超)──▶ LEFT_CHANGE（变道中）
CRUISE ──(前方红灯)──▶ STOP（停车）
STOP ──(灯绿)──▶ CRUISE
CRUISE ──(到掉头点)──▶ U_TURN（掉头）
...
```

**为什么用状态机而不是一堆 if？** 因为状态机强制你回答一个问题：**每一个「状态 × 事件」
的组合，会发生什么？** 用 if 写，你很容易漏掉某个组合（比如「变道中遇到红灯」），而
状态机逼你把表填满。**状态转移表缺一行 = 某个边界情况卡死**——这是行为层最经典的 bug
来源，项目真实踩过「该走不走/该停不停」。

**职责边界**：决策层**只决定「做什么」**（变道/停车/掉头），不输出任何连续控制量。
方向盘打多少、油门踩多少，那是规划和控制的事。**为什么？** 因为决策是离散的（好验证），
控制是连续的（容易出问题）——把两者混在一起，你既说不清「它为什么变道」，也说不清
「它为什么打这么多方向盘」。

## 第三步：规划——车算出一条「带速度的路」

### 你自己的答案

决定变道了，怎么算路？最朴素：画一条从当前车道到旁边车道的直线。但直线变道是斜着
开过去的——**车不会斜着开**（卷一学的），你得画一条**平滑的曲线**。

### 真正的方案：Frenet 轨迹 + 速度剖面

规划层输出的是 `planning/trajectory`：一串点，每个点带位置**和速度**。它是整条链的
**唯一权威**——控制层不许质疑它，安全层只许限幅它。

**轨迹**：横向变道用五次多项式生成平滑曲线（起点和终点的一阶、二阶导数都对齐，
保证方向盘连续）。**速度**：用 ST 图 + DP 算出每个点的速度。ST 图把「时间-位置」网格
化，把约束填进去：

- 前方 50 米有红灯 → 在 50 米处速度必须为 0（红灯墙）；
- 前方 30 米有慢车 → 它的时空占据格子里不能有我的轨迹（动态障碍墙）；
- 弯道曲率太大 → 速度不能超上限（曲率限速）。

然后 DP 在网格上找一条「代价最小」的速度曲线。**这不是搜索出来的最优，是约束满足的
可行解**——自动驾驶的规划，先求「不撞」，再求「好」。

### 一个规划层的经典 bug（记住它）

规划层曾经有个 bug：红灯 override 在速度剖面算完**之后**才设 `command_speed=0`，但
轨迹里的 `points[].v` 读的是**旧的**速度剖面——控制层拿到的还是巡航速度，于是车
**闯红灯**。修复：override 触发时，要**同步重建**整个速度剖面（当前速度 → 0 的减速
斜坡），轨迹末点真的归零，控制才会刹停。

**这个 bug 的教训**：当两个模块共享一个状态（速度剖面），一个模块改了它，另一个模块
必须**同步知道**。否则你改的是 A，车执行的是 B。

## 第四步：控制——把「路」翻译成「方向盘和油门」

### 你自己的答案

拿到轨迹，怎么踩油门打方向？最朴素：算一个横向误差（车偏了轨迹多少），误差大就多打
方向——这就是 **P 控制**（比例控制）。

### 为什么不够

纯 P 控制会震荡：你看到偏了 1 米，打了方向盘；车转过去，过头了，偏到另一边，再打回来……
来回摆动。真实世界里你还需要**阻尼**（heading 的偏差，抑制震荡）和**前馈**（弯道
本身需要预打方向）。

### 真正的方案：横向 Stanley + 纵向 PID

- **横向**（方向盘）：Stanley 控制器 = 横向误差项 + heading 阻尼项 + 弯道曲率前馈。
  它比纯 P 多了一个「看车头朝哪」的项，让车**平滑地收敛**到轨迹，而不是震荡。
- **纵向**（油门/刹车）：PID = 比例 + 积分 + 微分，追踪目标速度；ACC 模式根据前车
  距离动态压低目标速度。

### 一个控制的经典 bug（积分饱和）

PID 的「积分项」如果不会清除，会累积出灾难。项目真实踩过：加速阶段积分累积到 +500，
进入减速后，比例项不足以抵消积分项 → **油门全开撞前车**。修复：误差方向一变，直接
清零正积分（anti-windup）。

**这个 bug 的教训**：控制算法的每个项（P/I/D）都有「它以为自己在做什么」的假设，
你必须保证这个假设在边界情况也成立。

## 第五步：安全——最后一道闸门

### 你自己的答案

超车超到一半，前车突然急刹。这时候控制层还在「跟着轨迹走」（轨迹上可没写「前车会急
刹」）。怎么办？

### 真正的方案：独立的 TTC 闸门

`safety_control` 是**独立的最后一道闸门**，它不算路、不追轨迹，只做一件事：**计算
碰撞时间（TTC），太近就限速/刹车。**

```
TTC = 距离 / 相对速度
if (TTC < 阈值) → 限速/刹车/MRM（最小风险机动）
```

**为什么它必须独立于控制层？** 因为它的任务和别的层**不一样**：控制层想「跟好轨迹」，
安全层只想「不出事」。如果安全逻辑写在控制层里，那么当车「必须违反轨迹才能不出事」
时，控制层会纠结（该听谁的），而独立闸门没有纠结——**它的唯一职责就是踩刹车。**

### 一个安全层的经典 bug（坐标系血泪）

安全层曾经用「世界 x 坐标」判断前后车——正常行驶没问题，但车**掉头返程**（朝西开）
时全错：返程的同向车被误判成「迎头」（幽灵刹车），返程的前车又因为 x 坐标符号被跳过
（该防撞的没防）。修复：所有威胁判断改成**沿车头方向投影**——用自己的朝向重新定义
「前/后/左/右」。**这个 bug 的教训：用世界坐标做判断，就等于假设车永远朝一个方向。**

## 把五个角色连起来，重看职责铁律

现在你完整走过了一遍超车。回头看那五条铁律，每条都是一次真实的翻车：

| 角色 | 唯一职责 | 如果越界（真实发生过） |
|------|---------|----------------------|
| 感知 | 看见 | 漏检不报错（隐性的，最危险） |
| 决策 | 决定「做什么」 | 转移表缺行 → 卡死 |
| 规划 | 速度轨迹唯一权威 | 改了速度剖面但没同步给轨迹 → 闯红灯 |
| 控制 | 纯跟随，不质疑 | 积分饱和不清零 → 油门全开撞车 |
| 安全 | 限幅 + 紧急制动 | 用世界坐标判断威胁 → 掉头返程全失效 |

## 动手实践

```bash
bash scripts/demo.sh
# 观察超车全程：找一个慢车挡路 → 看车怎么打灯变道 → 超过后怎么回来
# 然后打开 /tmp/flow_topology.json（实时更新），看这几个字段：
#   metrics.behavior.state   —— 决策层当前状态（CRUISE / LEFT_CHANGE ...）
#   metrics.vehicle          —— 控制层的油门/刹车
#   metrics.scene.trajectory —— 规划层算出来的轨迹点
# 你会看到：决策先切到 LEFT_CHANGE，规划才画曲线，控制才打方向——一条链，节奏分明。
```

**改一处观察**：把 `scenarios/straight_road.json` 里慢车的速度调快（比如让它只比你的
巡航慢一点），再看——决策层可能**决定不超了**（不值得超）。这就是决策层的判断在起作用。

## 小结

这一章你亲手走过了一条完整的算法链：

- **感知**把点云变成「盒子」；**决策**用状态机决定「做什么」；**规划**算出带速度的
  平滑轨迹；**控制**把轨迹翻译成方向盘和油门；**安全**在最后兜底。
- 五个角色**各管一段、谁也不越界**——越界就是 bug，项目每一条铁律都有一次真实翻车
  记录。
- 你学会了四个真实 bug 的教训：漏检不报错、状态表缺行、改了不同步、积分不清零。
  这四个 bug 类型，后面几卷还会反复出现。

2. **思考题**：为什么规划层是「速度与轨迹的唯一权威」，而不是决策层？提示：决策层
   是离散状态，规划层是连续曲线——连续的东西需要连续的地方算。

   铁律，你**不应该**让安全层理解意图。那正确的做法是什么？（提示：卷三 3.6 的
   「机动窗口豁免」是怎么实现的？）
