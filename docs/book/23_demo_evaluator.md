# 第 23 章：改动一行代码，怎么知道它没把别处弄坏

> **v2 范式章节**（2026-09 整治后保留）。本章保留低行号密度、真技术书
> 风格，参照 `docs/book/README.md` 写作风格约束与 `docs/book/08_discovery.md`
> 范式示范。v1 行号清单版本归档于 `docs/_archive/book_v1/`。

在自动驾驶这种大工程里，一个看起来很小的改动，往往会在别处掀起大浪。横向控制的滤波系数调一调，直线段是更顺了，可到了急弯车就冲出了车道；感知阈值松一点，静态假目标的误检是少了，可暴雨天里行人又被漏掉。要压住这种回归，靠人工逐条跑场景并不现实，得有一套分层的自动化验证。这章讲 KunAutoDrive 是怎么从毫秒级的静态检查一路铺到分钟级的端到端黑盒评估的。

## 三道由快到慢的验证关卡

```
KunAutoDrive 质量验证阶梯:
  ┌─────────────────────────────────────────────────────────────┐
  │  L2 / End-to-End 黑盒回归评估 (demo_evaluator.py, 3~5 分钟) │
  │  • 多场景全栈仿真 (高速、城区、十字路口、掉头、匝道)        │
  │  • 动力学边界考核 (0 碰撞, 0 越界, 舒适度 Jerk, 变道成功率) │
  └──────────────────────────────┬──────────────────────────────┘
                                 │
                                 ▼
  ┌─────────────────────────────────────────────────────────────┐
  │  L1 / 单元测试与集成测试 (CTest / GTest, 10~30 秒)          │
  │  • 28+ CTest 测试套件 (MessageBus, EKF, FlowCoro, IPC)      │
  │  • 内存泄漏扫描 (Valgrind / ASan / UBSan 内存越界检测)      │
  └──────────────────────────────┬──────────────────────────────┘
                                 │
                                 ▼
  ┌─────────────────────────────────────────────────────────────┐
  │  L0 / 极速静态与流水线门禁 (pipeline_check.py, < 1 秒)      │
  │  • 30 项硬性门禁 (符号命名规范、头文件包含、ABI 门禁版本号) │
  │  • 架构铁律检查 (禁止业务插件直接依赖全局 g_bus)            │
  └─────────────────────────────────────────────────────────────┘
```

## 最快的一道：L0 静态门禁

L0 门禁跑在每次 `git commit` 或 PR 提交上，一秒不到就能拦下常见的底层代码异味和架构违规，代码在 `tools/pipeline_check.py`：

```python
# 核心校验规则举例:
# 1. 节点插件 ABI 版本一致性
assert plugin.api_version == NODE_PLUGIN_API_VERSION, "ABI 版本不匹配"

# 2. 严禁在插件内直接引用全局变量
assert "extern MessageBus g_bus" not in code, "违背依赖注入铁律"

# 3. 前端离线环境资源合规检查 (严禁外部 CDN 外链)
assert "http://" not in frontend_code and "https://" not in frontend_code
```

## 分钟级的 L2 黑盒回归评估

`demo_evaluator.py` 是评估整套 ADAS 栈表现的引擎。它用黑盒方式把完整的多进程/多线程 Pipeline 拉起来，驱动场景回放，并逐帧记录车辆轨迹与物理指标。

### 评分报告里的指标和权重

跑完一轮，评估器会自动输出一份结构化评分报告：

| 指标类别 | 考核项目 | 达标红线 (Pass/Fail) | 权重 |
| :--- | :--- | :--- | :--- |
| **安全性 (Safety)** | 碰撞次数 (Collisions) | **严格等于 0** | 40% |
| **安全性 (Safety)** | 道路越界 (Road Departure) | **严格等于 0** (横偏 $< 1.75\text{ m}$) | 30% |
| **通过性 (Mobility)** | 任务到达率与平均车速 | 耗时在理论基准 $+15\%$ 以内 | 15% |
| **舒适度 (Comfort)** | 加速度与加加速度 Jerk | $\|a_x\| \le 3.0\text{ m/s}^2, \|J\| \le 2.5\text{ m/s}^3$ | 10% |
| **控制精度 (Tracking)** | 稳态横向偏差 (CTE) | $P_{95} < 0.15\text{ m}, \text{Max} < 0.30\text{ m}$ | 5% |

### 怎么跑、怎么出报告

```bash
# 1. 针对全量场景执行端到端回归评估
python3 tools/demo_evaluator.py --scenarios all --timeout 60

# 2. 导出 HTML / JSON 诊断摘要
python3 tools/demo_evaluator.py --report build/evaluation_report.json
```

## 参数调到头大？让扫描替你搜

规控算法里有一大把要调的超参数，比如 Stanley 增益 $k$、LTV MPC 预测时域 $N_p$、TTC 阈值。KunAutoDrive 支持基于网格搜索的参数敏感度自动扫描：

```bash
# 自动扫描 Stanley 增益 k 从 0.5 到 2.0 对横向误差与 Jerk 的影响
python3 tools/param_sweep.py \
  --param control.stanley_k \
  --range 0.5,2.0,0.1 \
  --scenario scenarios/zhongkai_road_full.json
```

扫完之后工具会自动画出一张参数-性能热力图（Sensitivity Pareto Curve），帮你在图上挑出鲁棒性最好的那一段参数。

## 常见故障速查

下面这张表把平时最容易出问题的两处攒在一起，遇到就照着查。

| 现象 | 更可能的原因 | 处理办法 |
| :--- | :--- | :--- |
| 回归测试偶发失败，重跑又好了 | 测试脚本里用了系统的真实睡眠（如 `time.sleep(1)`），CI 机器负载一高，断言就超时报错 | 把测试接到统一时钟服务 `ClockService` 上，用离散逻辑时钟推进，不再依赖物理时钟 |
| 直线场景全过，掉头和路口让行却出问题 | 回归场景覆盖太窄，只用 `infinite_straight.json` 测不到复杂逻辑 | CI/CD 里强制覆盖急弯、汇入、多车交互、掉头和信号灯的综合场景集 |

## 权重为什么是这个分配

上面那张表里最值得看的不是红线，是**权重**。

碰撞占 40%、越界占 30%——**安全和舒适度的比例是 7:1**。这不是拍脑袋，是把
"两类错误的代价不对称"直接写进了评分函数：

| | 后果 | 可逆吗 |
|---|---|---|
| 横向偏差大一点 | 乘客觉得晕车 | 可逆，减速即可 |
| 撞上护栏 | 车毁人伤 | 不可逆 |

一旦你接受"代价不对称"这个前提，权重的形状就被决定了。**任何线性加权和的评分
函数都在表达一个信念**——它把不可比的量（米 和 m/s³）放在一起乘以人为系数，
这个系数不是数学，是价值判断。

所以我不太喜欢"调权重直到通过"这种做法。正确的问题是：
"如果我把碰撞权重从 40% 调到 20%，什么样的 bug 会开始漏过去？"——这个问题有答案，
而"怎么调权重"没有。

同理，那条"耗时在理论基准 +15% 以内"的红线，也不是性能指标而是**功能指标**：
一条慢了 15% 但不碰的车，比一条快 15% 但擦到的车好。把它放进"通过性"而不是
"性能"，说明这一版的评估器是按"能不能完成任务"设计的，不是按"跑得快"设计的。

> **作者立场**：安全类指标用"严格等于 0"而不是"小于某个阈值"，我认为是这类
> 评估器唯一正确的做法。阈值是给连续量用的，而碰撞次数是离散计数——设成
> "碰撞 < 0.5" 只是在给"允许撞一次"找借口。

## L0 门禁为什么值得单独存在

有人会问：静态门禁这么低级的东西，值得写一章吗？

值得。因为它是整个阶梯里**唯一一个能在提交时就给出反馈**的层次。L1 要 30 秒、
L2 要 5 分钟——对于一天提交二十次的人来说，反馈延迟本身就决定了他们会不会
真的去看结果。

更重要的是 L0 拦下的是**架构层面的腐烂**。上面那三条规则里，
"禁止插件直接引用全局 g_bus" 是一条真正的架构铁律：它保证每个节点都能被单独加载、
单独测试、单独替换。违反了不会立刻出事，但一年后你想给某个算法换个进程跑，
会发现所有东西都焊死在同一个全局对象上。

这类腐烂的特征是：**每一次提交都合规，加起来却回不去了。** 只有把它做成
提交时必过的门禁才拦得住。

对比一下第 24 章学到的教训：那里也有一个门禁（模型准入门禁），但它管的是
统计意义上的质量（碰撞数、Jerk 方差），这些指标**天然有噪声**，所以门禁阈值
必须宽松、必须允许人工 override。而 L0 管的是"有没有写 `extern g_bus`"——
零噪声，所以可以做成硬失败。

> **门禁设计的通用原则**：能做成硬失败的，就不要做成软警告。软警告的默认
> 行为是被人忽略，而被忽略的门禁等于没有门禁，还额外背上了"我们有门禁"的
> 虚假安全感。

## 这一章没讲什么

没讲 CI 怎么接线、怎么调超时、报告往哪儿存——那些读 `.github/workflows/ci.yml`
比读我这段文字快。

也没讲一个更重要的问题：**这套评估器本身怎么被验证**。你没法用有 bug 的评估器
来判断你的代码有没有 bug。仓库里的做法是每条规则都配了对应的"应该失败"的
反例输入——这本身是个好办法，但只有当你**故意破坏**代码时才会用到它。

如果你接手这套东西，最该先做的事是：随便改一处代码，看 L2 能不能抓到。抓不到，
说明你的评估器和你的代码一样有盲区。

## 假通过：车没动，评估器说通过

这是端到端评估器最容易犯、也最危险的错误。原因是**它需要主动构造才能发生**——一个什么都不
做的系统，在大多数指标下天然是"完美"的：不碰撞、不越界、横向误差为零、速度为零。零碰撞
和零越界这两条最重的红线，在一辆没动过的车上都会通过。

更麻烦的是，**"车没动"和"车正常跑"在数据里长得不一样，但在某些指标上一样**。所以防御
不能靠"多写几条判据"，得靠改变判据的**结构**。

### 三层防御，从最弱到最强

```
   最弱  ┌──────────────────────────────────────────────┐
         │ 阈值类判据：速度 > 5 m/s、位移 > 10 m        │
         │   ↑ 漏法：设阈值的人自己知道"活着"长什么样 │
         └──────────────────────────────────────────────┘
                    ▲
   中等  ┌──────────────────────────────────────────────┐
         │ 活性判据：liveness_report() 扫"值有没有变过" │
         │   ↑ 不预设阈值，测"这个量全程是不是死值"   │
         └──────────────────────────────────────────────┘
                    ▲
   最强  ┌──────────────────────────────────────────────┐
         │ 可判定性判据：require() —— 前置不满足时      │
         │ 记 INCONCLUSIVE 并计入失败                   │
         │   ↑ 根除"没测到 = 通过"这一整类漏洞         │
         └──────────────────────────────────────────────┘
```

第三层是这里最值得学的一条。它的注释里写清了和旧实现的差别：旧写法是 `if n < MIN:
continue`——样本不够就不判了，**结果渲染成 PASS**。而"无法判定"和"通过"在语义上完全不是
一回事：前者说的是"我没能力回答这个问题"，后者说的是"我回答了，答案是好的"。把前者渲染
成后者，等于给整个体系造了一个静默的漏洞。

### 那三层具体长什么样

**活性判据**扫的是每个受监控量在整轮 run 里的**取值分布**：只有一种取值就是"死值"，依赖它
的判据全部失去意义。这个设计的好处是它**不需要有人事先想清楚"活着应该长什么样"**——
它只问"这个量变过没有"。

但它需要例外。`y` / `heading` / `steer` / `lane_count` 这几个量在直路场景里本来就应该
恒定，如果也按死值判，直路场景会全挂。所以它们被标成"允许常量"。这个例外的代价是：**一条
判错的路（应该变道却没变）在直路场景下依然抓不到**。能抓到的只有那些场景自己声明了
`required_lane_changes` 的。主动声明自己期望的场景，才能享受更严的活性检查。

**可判定性判据**用在识别率上：场景 JSON 里声明了多少个 `vehicle`、多少个 `vru`，这是一份
**独立的期望值来源**。真值实体是场景给的，感知输出是被测系统给的，两者对不上就是问题。
如果这份期望没有——比如"场景里其实没放行人"——那识别率的分母是零，而零除出来仍然是零，
看起来完美通过。`scenario_actor_layer_counts` 存在的全部意义就是堵这个洞。

### 还有一类更隐蔽的假通过

车动了，但**决策没动**。

评估器专门检查了这件事：`behavior/state` 字段如果整轮都是空值或 `NA`，直接判 FAIL。理由
写在注释里——决策块被跳过了，最可能的原因是"空的感知列表被当成'还没准备好'"。这在任何
单项指标上都看不出来：车在动、不碰撞、不越界，只是从来没做过任何决策。

这类判据的共同特征：**它们检查的不是输出的数值，而是输出的"尝试痕迹"。** 一个函数
被调用过，这件事本身就是证据。

> **作者立场**：我认为评估器最重要的性质不是"能不能抓到 bug"，而是**"在什么都没发生的时候
> 会不会诚实地说没发生"**。一个永远给 PASS 的评估器和一个没有评估器，在工程上是等价甚至更
> 差的——后者至少不给人虚假的安全感。所以我更看重 INCONCLUSIVE 这个机制，而不是任何一条
> 具体阈值。

## 并行度与确定性：为什么它们天然冲突

场景回归的驱动器支持并发和重复，两者的组合方式暴露了这个矛盾的核心。

**并行**用线程池跑不同场景。**同一场景禁止并发**——注释说得很清楚：它们共享同一份 worker
工作区，并发跑会互相覆盖拓扑快照。

**重复**是同一个场景串行跑 N 次，然后**取中位数**合并，极差记进结果里。

```
   允许：场景 A ──┐
        场景 B ──┼── 同时跑（彼此独立，不共享工作区）
        场景 C ──┘

   禁止：场景 D ──┐
        场景 D ──┼── 同时跑（共享工作区 → 拓扑快照互相覆盖）
        场景 D ──┘

   做法：场景 D ──── 串行跑 3 次 → 取中位数，极差记为不确定性
```

为什么同一个场景重复取中位数，而不是取第一次？理由和"测试为什么要跑三次"一样：单次结果里
混着信号和噪声，而**噪声的方向是随机的**。跑两次取平均会互相抵消一部分噪声但剩下方差；取
中位数更稳，因为它完全不受极端值影响——而极端值恰恰是最可能来自系统崩溃的那一次。

极差被记下来，是因为它有独立价值：**极差大的场景，它的 PASS/FAIL 本身就不该被当硬结论。**
一个极差 3m/s 的场景，PASS 了不代表它是稳的。极差是这个场景的"测试质量"指标。

**这条规则的代价是并发度被拓扑限制了，不是被 CPU 限制了。** 如果场景之间有共享资源（工作区、
端口、临时文件），那"能不能并行"这个问题就退化成了"哪些东西是共享的"——而这个答案每次
都要人肉判断。**并行度的问题到最后几乎总是共享状态的问题。**

> **作者立场**：我认同"不共享就并行"这条规则，但更认同它的推论——**与其花力气把场景并行化，
> 不如花力气让场景之间真的互不影响**。本仓库现在的做法是先用"禁止同场景并发"这条简单规则
> 把安全边界划出来，等哪天真需要更快的反馈，再来消除共享。这比一开始就设计一套隔离机制便宜。

## 指标和真实安全性之间的差距

前面那张权重表读起来像是"安全"的度量。实际上它度量的是"在这套仿真、这批场景、这版代码下，
没有发生可观测的坏事"。这两句话之间的距离比看起来大得多。

```
   指标覆盖的                      真实安全的
   ┌──────────────────────┐       ┌──────────────────────┐
   │ 碰撞：几何上撞上了   │       │ 碰撞：物理上撞上了   │
   │ 越界：横向出界 1.75m  │       │ 越界：任意时刻的实际位置│
   │ 舒适：加加速度上限   │       │ 舒适：乘员的真实体感  │
   │ 精度：稳态横向偏差   │       │ 精度：整个生命周期内  │
   └──────────────────────┘       └──────────────────────┘
          ↑ 差距在这两栏之间
```

具体的差距有四条：

**一、仿真碰撞不是物理碰撞。** 判定碰撞用的是仿真器发布的碰撞计数和日志里的碰撞记录。
碰撞检测本身是几何判据——两个 actor 的包围盒相交。它没有建模"擦一下"和"撞上去"的力学
区别，也没有建模车辆材料的溃缩。一个低速下的轻微接触和一个高速下的正撞，在指标里可能都
只是"1 次碰撞"。指标把两者压成同一个数，而这个压扁丢掉的信息正是安全评估最需要的。

**二、覆盖的场景之外，指标什么都不是。** 上面所有红线的成立范围就是"跑过的那些场景"。没有
跑过的场景不产生指标——而**没跑过的场景在报告里和跑过的是一样的**。这一点和前面说的
INCONCLUSIVE 是同一个病根的另一面：INCONCLUSIVE 至少诚实地记了"这里没法判断"，而
"场景没跑"根本不会在报告里留下任何痕迹。

**三、舒适度和安全在物理上会互相冲突，而指标没表达这个冲突。** 一次成功的紧急避让几乎
必然带来大 Jerk，指标会因此扣分。但那可能正是**避免了一次 30% 事故**的操作。换句话说，
一条"加加速度超 2.5 判 FAIL"的红线，在极端场景下会**因为系统救得及时而失败**。

这不意味着不该设这条红线——它确实能抓住控制器的抖动 bug。而是意味着**你不能把这份报告
读成"这次运行是安全的"**，它读成的是"这次运行满足了这几条被形式化的偏好"。

**四、指标只测平均，不测尾部。** 横向偏差用 P95 和 Max——已经比平均值好了很多，但仍然
是单帧指标。真实安全关心的是**时间上的连续性**：一个每秒发生 0.5 次的 0.4m 偏差，和一个
永远 0.05m 的偏差，哪个更危险？数据不同，答案可能相反。指标体系目前表达不了"发生频率 ×
单次幅度"这个组合。

**那这套东西还有什么用？** 用处是**回归检测**，不是安全认证。它极擅长回答"我刚才改的那一行，
有没有让情况变差"。这个问题的价值极高——不是因为它能证明安全，而是因为**变更导致的事故是
最常见的事故类型**，而手动回归不可能每次都做。

> **作者立场**：如果有人拿这份报告说"我们的系统是安全的"，我会认为这是误用。它能支持的
> 最强结论是"**这批场景在这次改动下没有退化**"。这两句话看起来差不多，但前者是不可证伪的
> ——而出于安全和合规考虑去做一套声称能证明安全的指标体系，是评估体系能造成的最坏结果，
> 因为它会让决策者相信一个假的东西。
