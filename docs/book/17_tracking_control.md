# 第 17 章：跟踪控制 —— 当「意图」终于碰到「力」

> **v2 范式章节**（2026-09 整治后保留）。本章保留低行号密度、真技术书
> 风格，参照 `docs/book/README.md` 写作风格约束与 `docs/book/08_discovery.md`
> 范式示范。v1 行号清单版本归档于 `docs/_archive/book_v1/16_tracking_control.md`。

规划层交出来的只是一条「该往哪儿走」的期望轨迹；能不能真的贴着它走，取
决于转向角打多深、油门踩多狠、什么时候收油。这一章讲的是 KunAutoDrive
整条链路上唯一一个把「意图」翻译成「力与力矩」的地方——控制节点。

读完这一章你会知道几件事：

- 横向控制器**不叫教科书里的 Stanley**——实际是三级级联 PD + 曲率前馈
- 纵向控制器**不输出加速度**——直接输出油门开度 + 制动压力
- 那个所谓的「MPC」其实是离散 LQR（后向 Riccati），**默认关闭**
- 跟踪控制有真实失败故事——PID 步长 / 控制频率不一致整整一年没暴露
- 机动跟踪器（掉头/泊车）为什么独立于常规控制循环

## 一、为什么把控制单独切出来

理论上，规划层完全可以把轨迹终点速度、终点位置打包成「目标位姿」，让下游
直接消费。可**「目标位姿」到「油门/刹车/转向」的物理量级跨越太大**——从
`(x, y, θ, v)` 跳到 `(throttle ∈ [0, 1], brake ∈ [0, 1], steer ∈ [-0.5, 0.5])`
没有任何解析映射。中间必须有反馈。

而且这条反馈链对**实时性**的要求和规划层不一样：

| 层 | 频率 | 周期 | 延迟预算 |
|---|---|---|---|
| 规划 | 20 Hz | 50 ms | 50 ms |
| 控制 | 40 Hz | 25 ms | 25 ms |
| 安全 | 100 Hz | 10 ms | 10 ms |

频率分层不是任意的：**控制必须比规划快，否则规划每发一帧轨迹，控制还没收敛
轨迹就更新了**——典型的振荡源。

```
规划（20 Hz） ──► 控制（40 Hz） ──► 安全（100 Hz） ──► 执行器
   Trajectory       ControlRaw          ControlCmd        PWM/CAN
  64 点 10 Hz        40 Hz               100 Hz            硬件
```

> **作者立场**：分层频率是这本书里**和教科书最一致**的设计——Apollo 6.0+、
> autoware.universe、Waymo 的公开论文都接近这套数字。**和教科书的差异在
> 工具实现**（纵向 PID 而非线性控制、横向级联 PD 而不是 Stanley、离散 LQR
> 而不是 MPC），不在架构。

## 二、控制节点的真实频率：40 Hz

主循环在 `CoroutineTask` 的 `run()` 里——消息驱动，被 `fusion` 或 `planning`
的消息唤醒，再靠 25 ms 的时间戳比较把频率压到 40 Hz。规划节点 20 Hz 发轨迹，
所以稳态下大约每来一条轨迹执行一次有效控制。

### 2.1 一个真实的不一致

**这里有一个真实的不一致，读者应当知情**：

频率是 40 Hz，但**积分和微分用的步长是硬编码的 0.05**——同文件其它地方
注释明明白白写着「控制环周期: 20Hz」：

```cpp
g.integral   += pid_error * 0.05;          /* 硬编码 20Hz */
double derivative = (pid_error - g.prev_error) / 0.05;
```

后果是可预测的：实际采样周期是 0.025 s，积分每帧只累 0.05 s 的量，**积分
增益被系统性放大了一倍**；微分则是拿 0.05 的分母去除 0.025 s 间隔的差，
**微分增益被砍掉一半**。后者反而起了额外阻尼作用，掩盖了问题，所以这个
不一致至今没暴露成 bug。

相比之下 MPC 的步长是老老实实的：`cfg.dt = 0.025`，注释写明「匹配
control_node 40Hz 控制周期」。

> **这是 2026-09 才挖出来的事实**——之前大家都以为控制是 20 Hz，文档也写
> 20 Hz。`control_node.cpp` 真实跑 40 Hz 已经一年多了，没人发现，因为 PID
> 的增益**恰好**在「I 放大 / D 缩小」两个方向上互相抵消。这一类「隐式
> 均衡」的 bug 极难发现，**重构 PID 时一定要先核对实际 dt**。

## 三、纵向：一个带镜像处理的 PID

先明确一件事：**KunAutoDrive 的纵向控制器不输出加速度，它输出油门开度和
刹车压力**。`ControlRaw` 消息里根本没有 `accel` 字段。

这一点值得反复强调，因为它决定了 PID 的**量纲和整定逻辑完全不同**。经典
纵向 PID 整定假设 `u = K_p·e` 出来的是 m/s²，配上车辆质量就是力；这里
`u` 直接就是归一化的油门，所以 `K_p` 的物理意义是「每秒多少开度对应多少
m/s 的速度误差」。

### 3.1 三个工程设计要点

三个设计要点，都是从实车跑出来的：

**归一化系数不对称**（5000 / 8000）：同样的 `output` 幅值，油门开得比刹车
轻。这不是笔误，是发动机与制动系统的物理差异——油门响应有 200~500 ms 延迟，
制动响应 50~100 ms，分母给大一点让油门不至于太「凶」。

**积分限幅不对称**（`[-200, +500]`）：允许积累更多正积分（维持油门），
但严格限制负积分（防止长时间刹车后「一松刹车就窜出去」）。

**倒车镜像**：倒挡时目标速度和当前速度同时取反，PID 全程在正域工作，出口
再把油门取反。`flowsim/physics.cpp` 用负油门触发倒车，所以镜像后再取反。
这个三步操作（镜像目标 + 镜像当前 + 镜像输出）是为了让 PID 永远在「加速
为正 / 减速为负」的同一组公式里跑——不需要写两套逻辑。

### 3.2 三重抗积分饱和

这是全章最值得学习的一段工程代码——三层机制，缺一不可：

```cpp
/* 急清：误差从正翻负且幅度大（e < -2），立刻清零正积分。
 * 防追尾的第一道闸。 */
if (pid_error < -2.0 && g.integral > 0) {
    g.integral = 0;
} else {
    /* 慢泄：输出饱和但误差方向未变时，按 e·dt 反向泄放积分，
     * 保住正常的稳态跟踪能力。 */
    if (g.integral > 0 && throttle >= 1.0 && pid_error > 0)
        g.integral -= pid_error * 0.05;
    if (g.integral > 0 && brake    >= 1.0 && pid_error < 0)
        g.integral += pid_error * 0.05;
}
/* 负向对称清除：机动模式下、车已近停而目标转正时清掉负积分。
 * 2026-08-05 掉头返程实测卡死 30s timeout。 */
if (g.maneuver_mode && g.integral < 0 &&
    pid_error > 0.2 && fabs(g.current_speed) < 1.0) {
    g.integral = 0;
}
```

三层机制各防一类饱和：

| 层 | 触发条件 | 防御对象 | 工程教训 |
|---|---|---|---|
| 急清 | `e` 从正翻负且 `|e| > 2` | 加速→减速瞬时残余正积分 | 追尾 |
| 慢泄 | 输出饱和但误差方向不变 | 长期累积的同向积分 | 稳态速度漂移 |
| 负向对称清除 | 机动 + 近停 + 目标转正 | 减速→加速瞬时残余负积分 | 掉头卡死 |

第三层是**真实事故逼出来的**——2026-08-05 在掉头场景里实测：车在掉头第二
阶段 Phase 1 刹停到 0，error 翻负使积分转负，掉头进入 Phase 2（驻停慢转）
时 target 转正，**残留负积分把车钉在原地 30 秒**。直到 TIMEOUT 才被强制回
`CRUISE`。

### 3.3 换挡必须物理刹停

掉头要「左打满 → 倒车 → 再打右」三把方向，每一把之间都必须真的停住。用巡
航 PID 的软制动去停一个 2.4 m/s 的车需要近 2 秒，在这段距离里车会一路冲
过倒车段的起点。

```cpp
/* 掉头三把方向的"停"字：直接绕过 PID 给全刹 */
if (g.maneuver_mode && g.gear_pending) {
    throttle = 0.0;
    brake    = 1.0;
    mode     = "SHIFT_STOP";
    g.integral = 0;
}
```

这行 `brake = 1.0` 就是「三把方向的停字」的字面实现。**这是 2026-08-03 实
测到的另一个教训**：未加物理刹停的车会在 D→R 交界处冲到 y=8.8（路面外
y=8.5），因为巡航 PID 给的减速只够 0.23 brake（≈1.2 m/s²），刹不停 2.4
m/s 的车速。

### 3.4 目标速度的来源：1.5 秒近窗最小值

控制层**不做任何速度决策**——没有巡航速度覆盖、没有超速降档、没有 boost。
这是 Apollo 的原则，源码注释写得很明确。但「取轨迹**末点**的 v」这个做法
曾经出过大问题，改成了**近窗最小值**：

```cpp
/* 取轨迹 1.5s 内最小 v 而非末点 v。
 * 末点在 80m/4s 外，弯后全速值让 PID 弯中还在加速
 * （陆家嘴实测 v=10.6 过 R=20 弯 → steer_limit_for_speed 按速
 * 限幅到 0.034 ≪ 所需 0.135 → 转向被锁、车直冲路口 → ROAD_GUARD）。 */
double tv = traj.points[n_pts - 1].v;
for (uint32_t i = 0; i < n_pts; i++) {
    if (traj.points[i].t_rel_us > 1500000.0) break;
    if (traj.points[i].v < tv) tv = traj.points[i].v;
}
```

这是一个**级联延迟**的经典案例：

- 轨迹末点在 80 m / 4 s 之外，那里是「弯后」的速度
- 弯中读到弯后的全速值 → PID 不减速
- 车速不降 → 转向包络 `steer_limit_for_speed` 随 `v²` 收紧 → 舵量不够 →
  转向被锁死 → 车直冲路口

**4 秒前的意图，害死了 4 秒后的转向。** 改成取 1.5 s 近窗最小值，等于让纵
向提前 2.5 秒感知到即将到来的弯道减速，这 2.5 秒恰好够把车速压下来、把
转向权限还给控制器。

> **「这是经验之谈，不是教科书真理」**：1.5 s 这个窗口是陆家嘴环线上扫出来
> 的经验值——城市场景的典型轨迹节奏（弯半径 20~50 m，弯前减速 2~3 s 启动）。
> 高速场景应该再短一点（1.0 s），低速场景可以稍长（2.0 s）。本仓库不区分
> 场景——这是工程妥协。

## 四、横向：不是 Stanley 的横向级联 PD

绝大多数讲 Stanley 的材料给出的公式是：

```
δ(t) = ψ_e(t) + arctan(k · e_y(t) / (v(t) + k_soft))
```

**KunAutoDrive 里没有这个公式。** 没有 `k_soft`，没有 `arctan(k·e_y/v)`。
实际落地的是一条**三级级联**：

```
横向偏差 e_lat
     ↓  k_vy=0.35, k_vy_damp=0.6
期望横向速度 v_y_des  ←── 横向速度反馈
     ↓  asin(v_y_des / speed_eff)，限幅 ±0.5
期望航向角 ψ_des
     ↓  atan2(lat_kp·e, speed_eff) − 2.0·Δψ − 0.28·ω
转向角 δ
```

**三级串联的意义**：横向误差不直接映射成转向角，而是先翻译成「我此刻应该
横着走多快」，再翻译成「我此刻车头该朝哪」，最后才翻译成「前轮该打多少度」。
多出来的这一层冗余，是**为了打断误差与转向角之间的直接高增益通路**——
直接通路 `e → δ` 在实车上必然震荡。

### 4.1 完整公式

最终 `steer` 是五项之和，符号是 `+ - - + +`：

```
steer = cte_term − heading_term − yaw_damp_term + ff_term + delta_ff
```

| 项 | 系数 | 默认 | 物理含义 |
|---|---|---|---|
| `cte_term` | `lat_kp` | 0.5 | 横向误差 → 转向角（位置纠偏） |
| `heading_term` | `lat_kd_heading` | 2.0 | 航向误差 → 转向角（主阻尼） |
| `yaw_damp_term` | `yaw_damping` | 0.28 | 横摆角速度阻尼（抑制自激） |
| `ff_term` | — | ×1.0/×1.5 | 曲率前馈（稳态零误差的关键） |
| `delta_ff` | — | — | 运动学前馈（让级联内环自洽） |

**符号是减的**，因为代码里 `steer` 是**右正左负**（消息定义：「正值右转，
负值左转」），而 `lat_err_n` 是**左正右负**的左法向投影。两套符号约定不一
致，所以误差类项要减。

### 4.2 `speed_eff` 的 3.0 m/s 地板

```
speed_eff = fmax(|v|, 3.0)
```

`atan2(lat_kp · e, speed_eff)` 这个式子的分母就是防止低速时转向角发散的那
道软化。教科书 Stanley 用 `v + k_soft` 做加性软化，这里用 `max(v, 3.0)`
做**截断式软化**——效果类似但行为不同：加性软化下低速时增益仍会缓慢上升，
截断软化下 3.0 m/s 以下增益**完全冻结**。

3.0 m/s 这个地板是标定出来的：低于 10.8 km/h 时横向控制的精度要求可以放
松（反正车走得慢，横向偏差有充足时间被消掉），而放大增益只会引来低频漂移。

**注意用 `fabs` 取绝对值**：倒车时 `v < 0`，若直接代入会让 `v_lat_actual`
和 `cte_term` 的符号全部翻转，反馈变成正反馈。源码注释点明了这一点。

### 4.3 曲率前馈的 1.5 倍增益

曲率半径小于 60 m 时，前馈权重从 1.0 抬到 1.5。理由是：`ff_term = L·κ`
只是**理想运动学**的稳态前馈（假设 `δ = L·κ` 精确跟随），但真实车辆在弯
中还有轮胎侧偏带来的稳态横摆误差，实际需要的前轮转角大于 `L·κ`。在大曲
率弯道上这个偏差被放大，不补偿就只能靠 `cte_term` 去纠，而 `cte_term` 的
增益只有 0.5，补起来会引入明显滞后。

补偿系数在 `R < 60 m` 时取 1.5，是实车在多个弯道上扫出来的经验值。

### 4.4 限幅：`steer_limit_for_speed`

```cpp
static double steer_limit_for_speed(double speed_mps, double max_lateral_accel_mps2) {
    double speed = speed_mps;
    if (speed < 2.0) speed = 2.0;        /* 速度地板 2.0 m/s */
    double limit = atan(max_lateral_accel_mps2 · wheelbase / (speed · speed));
    if (limit < 0.016) limit = 0.016;     /* 下限 0.016 rad ≈ 0.92° */
    if (limit > 0.16)  limit = 0.16;      /* 上限 0.16 rad ≈ 9.2° */
    return limit;
}
```

`atan(a_max · L / v²)` 是「以 `a_max` 为横向加速度上限、`L` 为轴距时，前轮
转角的最大值」——弯越急、车越快，允许的转角越小。**上限 0.16 rad 是执行器
物理限位**，**下限 0.016 rad 是低速打角的下限**（再低执行器动不了）。

`max_lateral_accel_mps2` 默认 1.5 m/s²。这个值是**横向不舒适感的分界**——
> 1.5 m/s² 时乘客能明显感受到离心力，< 1.5 m/s² 时几乎无感。

## 五、横向 MPC：LTV-LQR，不是 QP

控制节点的 `ltv_mpc.h` 里有个叫 `ltv_mpc_solve` 的函数，**这不是 MPC**。
没有 OSQP、没有内点法、没有 ADMM。它是一个**3 状态、1 控制的离散仿射
LQR**，靠后向 Riccati 递推 `O(N)` 闭式解算。

### 5.1 为什么叫 LTV-MPC

「LTV」是「Linear Time-Varying」——每个预测时步对系统线性化（用当前状态
处的雅可比），沿着预测时域串起一族不同 `(A, B)` 的 LQR。所以：

```
prediction horizon  N = 20
discretization dt   = 0.025 s      ← 40 Hz 控制周期
state dim           n_x = 3       ← (e_lat, Δψ, ω)
control dim         n_u = 1       ← steer
```

「MPC」只是个名字——算法本质是 LQR。**约束（max_steer、max_dsteer）是在
解完之后做饱和截断**，不是在优化里当约束处理。

### 5.2 Riccati 递推

```
Aᵀ P + P A − P B R⁻¹ Bᵀ P + Q = 0      ← 离散 Riccati 方程（后向递推）
Kᵢ = R⁻¹ Bᵀ Pᵢ                            ← 控制增益
uᵢ = −Kᵢ · x                              ← 控制量
```

预测时域上每个点都有不同的 `(Aᵢ, Bᵢ)`，所以要递推 N 次 Riccati。**性能开销
是 N = 20 时约 80 µs**，比 OSQP 快 100 倍。

### 5.3 2026-09 的 Riccati 递推 bug

Riccati 递推的 `p`（代价矩阵）计算有 3 处数学错——2026-09 修过一次（commit
`0f44118`），**修复前在 `κ ≠ 0` 场景里 `u[0]` 与精确解偏差 5.8 倍**。

回归保护 `modules/adas_nodes/test_ltv_mpc.c` 给了 5 个用例，参考值用纯
Python 标准 affine-LQR Riccati 算出（无 numpy 依赖），容差 1e-9。**临时回
退 fix 跑测试 → 3/21 FAIL**，确认测试真的能拦 bug。这是「门禁自检」的
好例子——验证测试本身能抓 bug，而不是「测试 PASS 所以没 bug」。

### 5.4 默认关闭

`use_ltv_mpc{0}` 默认关闭，且没有任何 `config/*.json` 打开过它。**原因不是
Riccati 修完了就没事**——而是在变道场景的回归里 3 次 3 次挂：

- 横向级联 PD + 曲率前馈已经能在所有场景里跑通
- LTV-LQR 在变道第一帧偶发**过冲**——控制律不变，状态在某个初始条件下
  会超过 `max_steer` 限位
- 事后截断虽然不会爆出去，但**控制律的实际值低于 LQR 想要的**，跟踪误差
  比纯 PD 还大

这是**「能跑 ≠ 该跑」**的典型例——一个理论上更好的控制器，在**没标定好**
之前不如一个标定好的简单控制器。

> **「我不确定」**：长期来看 LTV-LQR 应该会启用（多目标优化、控制律与执行
> 器更紧的耦合），但**短期不要切**。这条建议在 HANDOFF_2026-09-21b §3.5
> 里有详细论证。

## 六、机动跟踪器：参考线断了之后

掉头和泊车有一个共同特征：**参考线是断的**——掉头时你要倒车回到另一条参考
线，泊车时你要画四条不在原 ref_path 上的折线。常规的「沿轨迹跟踪」在这两
种工况下不工作：

- 跟踪 `d_out ≈ 0` 意味着永远在当前车道中心
- 跟踪 `v ≈ 0` 意味着永远停下来
- 但掉头需要「横着跨过对向车道 + 倒着回去」

### 6.1 ManeuverTracker 的角色

`modules/adas_nodes/maneuver_tracker.h` 是一个**header-only** 的机动跟踪器
——它吃「目标点列表」（`ArcPoint`），逐弧长推进到下一段。它和常规控制循环
的接口：

```
ManeuverTracker::tick(current_pose, current_speed)
   ↓
target_steer, target_speed, gear
   ↓
覆盖 control_node 的常规输出
```

只要 `g.maneuver_mode = true`，控制循环就把控制权让给机动跟踪器。**这一段
控制**——「打满舵左转 90° → 倒车 → 打满舵右转 90°」——**完全不依赖轨迹**。

### 6.2 三个 phase：直行倒车交界是最大的坑

掉头分为三个 phase：

| Phase | 动作 | 挡位 |
|---|---|---|
| Phase 1 | 左打满 → 弧线推进到掉头中点 | D（前进） |
| Phase 2 | 刹停 → 物理刹停（`brake = 1.0`）| N（中立）|
| Phase 3 | 右打满 → 弧线推进到新方向 | R（倒车）|

**Phase 1 → Phase 3 的交界处是 2026-08-03 实测卡死的故障点**：

1. Phase 1 刹停时 PID 给出 `brake = 0.23`，但车还有 2.4 m/s 的速度
2. 软制动需要 ~1.9 s 才能停住，这期间车冲过倒车段起点
3. 最近点投影跳到 Phase 4 正向 → gear 翻回 D → 加速冲出路面
4. **修复**：换挡必须物理刹停（`brake = 1.0`），刹够 0.3 s 再翻挡

### 6.3 倒挡横向反号

倒车时**横向偏差的符号反过来**——这不是代码 bug，是几何事实。车在倒车的
时候，原本在参考线左侧的偏差现在「感觉上」在右侧（因为车头朝向了反方向）。

机动跟踪器内部对这个问题做了**统一的符号翻转**——`maneuver_mode = true`
且 `gear = R` 时，所有 `lat_err_n` 在送进级联 PD 之前取反。这避免了控制
器在倒车时反馈反向。

> **「这是经验之谈」**：这个符号翻转是手动做的，不是从 `gear` 自动推出来的。
> 我个人觉得这是个**代码味道**——「控制方向这件事应该由控制器自己知道，
> 不该外部传一个 `is_reverse` 标志位进来」。但现状就是这样，重构成本高于
> 留作待办。

## 七、跨模块信号约定

控制层和别的模块之间的边界信号只有一条：`control/raw_cmd.mode` 字符串。

例如：`"+MANEUVER"` 后缀让安全层**豁免机动窗口内的转向包络限幅**——因为
掉头时打满舵需要 0.6 rad，但正常行驶的 `max_steer` 是 0.25 rad。这是
2026-08 那次掉头横向 WARN 的修复（见第 23 章的 liveness gate 章节）。

> **作者立场**：**带外信号是必需的，但应该是有限的**。我反对「所有判断
> 都靠 mode 字符串」的写法——那会演化成「另一个状态机」。当前只有 +MANEUVER
> 一种后缀，这是**受控的边界扩张**，暂时可接受。

## 九、破除的 v0 错误说法

- **「横向控制器是 Stanley」**——v0 草稿这么写，**代码里一行 Stanley 公式
  都没有**。实际是三级级联 PD + 曲率前馈。本章第 4 节明确破除。
- **「MPC 是 QP 求解器」**——v0 暗示 MPC = QP。本仓库**没有 OSQP、没有
  内点法、没有 ADMM**。`ltv_mpc_solve` 是离散 LQR（后向 Riccati）。本章
  第 5 节明确。
- **「MPC 默认启用」**——v0 早期草稿里暗示 MPC 是主控制器，实际**默认关
  闭**，且没有任何 config 打开过。原因见第 5.4 节。
- **「PID 步长 = 控制频率倒数」**——v0 文档写 20 Hz / 0.05，**实际跑 40 Hz
  但 PID 步长还是 0.05**——这个不一致整整一年没暴露。本章第 2.1 节明确。
- **「变道/掉头用同一套控制器」**——v0 暗示规划层给完整轨迹，控制层直接
  跟。实际**掉头/泊车由 ManeuverTracker 接管，绕过常规控制循环**。本章第 6
  节明确。
- **「`cte_term` 是主项」**——v0 强调 `atan2(lat_kp·e, v)` 是核心，实际
  三项 `cte_term − heading_term − yaw_damp_term` **缺一不可**，单跑
  `cte_term` 会振荡。

## 十、跨章节串联

- **第 03 章**——控制节点是仓库里**仅有的两个实现了热重载 param_get_float**
  的节点之一（22 次 + 8 次）；另一个是行为决策（17 次）。其余 14 个节点
  参数改不动。
- **第 15 章**——决策层发布的 `Behavior.target_lane_offset` 被控制层用来
  触发 `maneuver_mode = true`（如果 Behavior 携带机动标志的话）。
- **第 16 章**——规划层发布的轨迹被控制层当目标值；轨迹的 `kappa` 字段是
  控制层曲率前馈的输入。
- **第 18 章**——安全层用 `control/raw_cmd.mode` 字符串做带外通信（`+MANEUVER`
  后缀豁免转向包络）。
- **第 23 章**——liveness gate 里有专门针对控制层的检测：横向翻转率、掉头
  扫角、纵向 TTC 兜底触发等。
