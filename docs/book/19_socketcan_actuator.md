# 第 19 章：浮点数变成电压的最后那一段

> **v2 范式章节**（2026-09 整治后保留）。本章保留低行号密度、真技术书
> 风格，参照 `docs/book/README.md` 写作风格约束与 `docs/book/09_discovery.md`
> 范式示范。v1 行号清单版本归档于 `docs/_archive/book_v1/22_socketcan_actuator.md`。

前面 18 章的所有输出，到本章为止都还只是一串浮点数。这一章是它们变成
**电气信号**的地方：要么是 I2C 总线上写进 PCA9685 寄存器的 5 个字节，要
么是 SocketCAN 套接字里发出的 8 字节报文。

这是整条链路上最短、也最容易出致命事故的一层。控制节点算出 0.3 rad 的
转角，执行器把它变成 $1500 + (0.3/0.22) \times 500 \approx 2181$ μs
—— 一个超出舵机量程 9% 的指令。如果钳位写错一个字符，舵机就会打到机械
限位。

在读之前，先破除旧稿里几个根深蒂固的误解：

1. **仓库里没有 `send_can_frame()`，也没有 `set_servo_pulse()`。** 旧稿
   所有 C 代码片段都是凭空编造的。
2. **SocketCAN 后端（`actuator_node.c`）从未被任何流水线配置加载过。**
   它被编译、被安装、被 CI 登记，但**零引用**。真正在跑的只有 PWM 那一个。
3. **执行器不碰串口。** `serial_write()` 全仓库零调用者。旧稿暗示 RC 小
   车走串口，这不对。
4. **默认配置里存在一个真实的、当前生效的参数不匹配**：安全层授权
   ±0.35 rad，执行器在 ±0.22 rad 饱和，中间 37% 的授权被静默丢弃。第 4
   节详述。

## 一、两个后端，一个活着

```
  [safety_control_node] ──control/cmd (ControlCmd, 20B)──┐
                                                          │
        ┌─────────────────────────────────────────────────┴──┐
        │                                                      │
   活的分支（所有 config 引用）                          死的分支（零 config）
        │                                                      │
   actuator_pwm_node.c                                  actuator_node.c
   libactuator_pwm_node.so                              libactuator_node.so
   I2C → PCA9685 寄存器                                 SocketCAN → can0
        │                                                      │
   ESC 电调 + 转向舵机                                  线控底盘 EPS + 刹车
```

`actuator_node.c` 自己就交代了：
> 部署状态：真车 CAN 部署预留实现。当前 `config/pipeline*.json` 默认用
> `actuator_pwm_node`（RC 小车形态），本节点无 pipeline 引用、无测试覆盖，
> 真车高速场景切换部署时启用。

正确读法：CAN 后端不是「备用的第二条路」，而是**一段为未来保留、从未验证
过的代码**。本章会以它为主线之一，因为真实的乘用车线控底盘就是这样接的；
但读者必须清楚它当前不在生产路径上。

## 二、订阅的那一条话题

两个节点都只订阅 `control/cmd`，都不发布任何东西：

```
s_inputs[]  = { "control/cmd", NULL }
s_outputs[] = { NULL }
```

**执行器是整条流水线的终点。** 它的输出不是消息，是物理量 —— 没有下游
可以再检查它，没有安全层可以再否决它。

`actuator_node.c` 里有**多处注释**声称它订阅 `control/raw_cmd`，而实际
代码订阅的是 `control/cmd`。`control/raw_cmd` 是第 17 章控制节点的内部
输出，是给安全层审的草稿；`control/cmd` 才是审完之后、真正能动车的指
令。**把执行器接到 `raw_cmd` 上，等于绕过整道安全闸门**。

代码是对的，注释是错的。这类「代码正确但注释说谎」的情况在本仓库不罕
见 —— 读者应以代码为准。

## 三、PWM 映射：33 行被精心抽成了纯函数

### 为什么单独抽出一个 .c 文件

`pwm_map.c` 整个文件只有 33 行，它被刻意从节点里抽出来，理由写在
`pwm_map.h` 和节点的注释里：

> 映射逻辑在 `pwm_map.c`（纯函数，tests 直接编同一份，真车改曲线时单测
> 跟着变）。这里只负责取缩放参数 + 落到硬件。

「**直接编同一份**」是这句话的重点：CMake 把 `pwm_map.c` 加进测试目标，
所以测试跑的**就是生产代码**，不是复制品。真车改了映射曲线，单测会跟
着变。

这与第 18 章形成鲜明对比 —— 那里 `apply_safety` 塞在 `.cpp` 匿名命名空间
里，TTC 公式一行测试都没有。**同样是纯函数逻辑，抽出来与否决定了它能
不能被验证**。

### 完整实现

```c
void pwm_map_control_cmd(double throttle, double brake, double steering_rad,
                         int e_stop,
                         double throttle_scale, double steering_scale,
                         int* esc_us, int* steer_us) {
    int esc;
    if (e_stop) {
        esc = PWM_CENTER_US;                       /* 紧急停转：中位 */
    } else if (brake > 0.01) {
        esc = (int)(PWM_CENTER_US - brake * throttle_scale);
    } else {
        esc = (int)(PWM_CENTER_US + throttle * throttle_scale);
    }

    double steer_norm = steering_rad / PWM_MAX_STEER_RAD;
    if (steer_norm > 1.0) steer_norm = 1.0;
    if (steer_norm < -1.0) steer_norm = -1.0;
    int steer = (int)(PWM_CENTER_US + steer_norm * steering_scale);

    if (esc_us)   *esc_us   = clamp_pulse(esc);
    if (steer_us) *steer_us = clamp_pulse(steer);
}
```

纵向是一条三分支的优先级链：

```
e_stop ≠ 0   ───────────►  esc = 1500              （ESC 停转）
brake > 0.01 ───────────►  esc = 1500 − brake·S    （反打，反向制动）
    否则 ───────────────►  esc = 1500 + throttle·S  （正打，前进）
```

三个要点：

**刹车映射是「往中位以下走」。** `1500 − brake·S`，`brake = 1.0` 且
`S = 500` 时得到 1000 μs，和「倒车」是同一个脉宽。**对 RC 电调来说，倒
车和刹车本来就是同一个方向** —— 这与第 17 章控制节点「倒挡用负油门触发
倒车」的思路一致。

**刹车优先于油门。** `brake > 0.01` 就走刹车分支，`throttle` 被完全丢
置。刹车和油门共存时，永远按刹车解释。

**`e_stop` 只管 ESC，不管舵机。** 这是本章最需要警惕的一条 —— 紧急停
转时转向舵机保持原指令。如果紧急停转是「立即靠边」，那么保持原转向是
对的；如果紧急停转是「前方有障碍原地刹停」，那么转向保持原指令意味着
车会按原方向撞上去。这是一个值得产品经理参与的设计选择，**我不确定
当前默认值是否正确**。

### 转向：归一化后再换算

`PWM_MAX_STEER_RAD = 0.22` rad 是**满量程对应的前轮转角**。`pwm_map.h`
里有一行注释写明：「`ControlCmd.steering`（rad）：正值右转，负值左转，
范围约 ±0.22 rad，**actuator 负责归一化**」。

也就是说 **0.22 rad 这个数在整条链路上出现了至少三次**（安全层限幅、执
行器归一化、CAN 编码），每一处都靠人工同步 —— 这是第 4 节要讲的真实
bug 的根源。

## 四、当前生效的不匹配：±0.35 vs ±0.22

**这是本章最重要的一段。**

`config/pipeline_car.json` 第 269 行附近配置 `safety_control` 的
`max_steer: 0.35` rad（约 20°），意即「安全层授权的自车最大转向角」。
但执行器的归一化常数 `PWM_MAX_STEER_RAD = 0.22` rad（约 12.6°），超过
的转向指令会被执行器截断。

**后果**：安全层觉得它授权了 0.35 rad 的转向，执行器却把 0.35 rad 当
作 $0.35 / 0.22 \approx 1.59$，归一化后只产生 1.0 倍满舵的舵机指令**，
中间 0.59 倍的授权被静默丢弃。

```
控制节点 ─► "steer = 0.30 rad"
                    │
                    ▼
安全层（max_steer = 0.35）─► 通过
                    │
                    ▼
pwm_map（MAX_STEER_RAD = 0.22）─► steer_norm = 0.30 / 0.22 ≈ 1.36
                                   钳位到 1.0
                    │
                    ▼
舵机 ─► "满舵"（但只有 1.0 倍）
```

中间 36% 的转向授权被静默丢弃。两条记录不同步、没有编译警告、没有运行
时检查 —— 控制节点以为最大转向是 0.35 rad（会按这个做轨迹规划），执行器
实际收到 0.22 rad。

**两类可能的后果**：

- **弯道轨迹偏窄** —— 规划器按 0.35 rad 的极限能力算轨迹，但执行器只
  能提供 0.22 rad，弯道内侧留出比预期更大的余量；
- **掉头失败** —— 掉头需要 0.60 rad 满舵（`steer_override` 时放宽），
  而执行器只能接受 0.22 rad（机动放宽后到 0.62 rad 是安全层给的，不是
  执行器给的）。这两个数都「对」，但合并起来就是一个隐性的轨迹失控。

**这是和第 20 章那个 `ego.wheelbase` 静默覆盖完全同型的问题**：配置值
在某一层被静默忽略，整条链路各自的内部状态自洽，但跨层合作时崩盘。
排查方向：跑一次急弯场景，看 `control/debug` 里的 `mode` 串里是否出现
`SAFE`（如果出现，说明安全层在收紧；如果不出现但车还是没按预期转，
那一定是执行器层在做截断）。

## 五、从微秒到 PCA9685 寄存器

### 分频公式

PCA9685 是 12 位 PWM 扩展板，I2C 接口，频率可调。分频公式：

$$\text{prescale} = \frac{f_{\text{osc}}}{4096 \cdot f_{\text{pwm}}} - 1$$

代入 50 Hz（默认）：$(25 \times 10^6) / (4096 \times 50) - 1 \approx 121$。
这个 12 位分频器的可调范围约 23.8 Hz 到 24.4 kHz —— 50 Hz 远在中间，
是个安全的取值。

### 微秒 → tick

$$\text{tick} = \frac{t_{\mu s}}{t_{\text{period}}} \times 4096, \qquad t_{\text{period}} = \frac{10^6}{f_{\text{pwm}}}$$

注意：PCA9685 的 tick 直接决定脉宽，**用四舍五入**而非截断 —— 这与
`pwm_map.c` 的截断不同，因为这里的误差直接是占空比，舍入能减小误差。

`period_us` 从 `g.pwm_freq_hz` 算，**不是硬编码的 20000** —— `pwm_freq_hz`
是运行时参数，从节点参数解析。这一点旧稿写错。

### 双重钳位

脉宽被钳了**两次**，分属两个文件：

- `pwm_map.c` 用命名常量 `PWM_MIN_US` / `PWM_MAX_US`；
- `actuator_pwm_node.c` 里直接写 `1000` / `2000` 字面量。

第二处应该直接用 `PWM_MIN_US` / `PWM_MAX_US`。用字面量的后果：有人改
了 `PWM_MAX_US` 宏，映射层会放行新范围，但硬件层仍然按旧的 2000 截断
—— 而且不会有任何编译警告。

### 写失败是静默的

`pwm_set_pulse` 的返回值被丢弃 —— I2C 写失败（舵机掉线、I2C 总线被占、
PCA9685 复位）不会有任何日志。安全层的 `+SAFE` 标签、`control/debug`
的一切诊断，在硬件层失效时统统看不见。

这段代码位于 `on_control_cmd` 回调里，而 `pwm_set_pulse` 是一次阻塞式
I2C 写。如果 I2C 从设备卡住不回 ACK，**安全层的发布线程会被阻塞**
—— 这个反馈路径会一路顶到第 18 节的发布循环。

### 上电先回中

PCA9685 上电后所有通道输出是 0（全开），如果不先写中位，舵机会先抖到
极限再回来。清理时同样强制回中。**这是一条真实的、有价值的实践**。

## 六、SocketCAN 后端：真实的报文布局

CAN 后端不在生产路径上，但它是理解真车线控底盘接法的唯一材料。

### 三个报文 ID

```
0x100  油门/刹车   DLC=8   [0-1] throttle u16 LE
                       [2-3] brake    u16 LE
                       [4]   gear     i8
                       [5]   e_stop   u8
                       [6-7] 保留（0）
0x101  转向        DLC=4   [0-1] steering i16 LE
                       [2-3] seq      u16 LE
0x102  状态心跳    DLC=8   [0-3] frames_sent   u32 LE
                       [4-7] cmds_received u32 LE   10 Hz
```

旧稿声称油门和转向打包在同一个 8 字节帧的 `[0-3]` —— 这与系统里任何一
个 ID 都不匹配。真实实现是**两个独立报文**，因为真实的线控底盘协议就
是这样分帧的（一个给动力总成，一个给转向）。

### 定点编码

CAN 路径**比 PWM 路径更严谨** —— 它先钳位再编码（throttle/brake 钳位
到 [0, 1]），PWM 路径依赖输出侧的 `clamp_pulse` 兜底。两条路径对同一份
输入的处理方式不同，这是一个值得统一的分歧。

`throttle_scale` / `steering_scale` 默认 **1000.0**，即满量程对应整数
1000。这是 0~1000 的定点约定，10 位精度足够，接收方按 0.1% 解析即可。

### 那个重复的 0.22

CAN 路径和 PWM 路径各自在文件内局部声明了最大转向角 0.22 rad。**0.22
这个物理常数在两个互不相干的文件里各写了一遍，没有任何东西让它们保持
同步。**

换一辆转向比不同的车，要改两个地方，漏掉任何一个就会出现「PWM 满舵和
CAN 满舵对应不同转角」的不对称 —— 而其中一个后端不在生产路径上，所以
它连一次实车验证的机会都没有。

### dry-run 下报「永远健康」

dry-run 模式下 `return 0`（成功），而 `frames_sent` 的自增在分支**之
后**。后果是：

- `frames_sent` 永远停在 0；
- 0x102 心跳帧的 `[0-3]` 字段永远是 0；
- 健康判定 `frames_failed > frames_sent && frames_failed > 100` 在
  dry-run 下 `frames_failed` 也是 0，**所以永远返回「健康」**。

**一个从不发帧的节点会一直宣称自己健康。** 这是把「发帧成功」与「帧
计数」绑定的副作用。修复方向：dry-run 下也要更新计数器，让健康判定有
意义。

## 七、我们踩过的坑

**1. ±0.35 vs ±0.22 的静默截断（当前生效）。**
安全层授权与执行器饱和不一致，中间 37% 的授权被静默丢弃。**这是配置
驱动的系统里最阴险的 bug 形态**：每层看自己都对，跨层合并就崩。修复
方向：抽出一个共享的「最大转向角」配置项，三处（安全层限幅、PWM 归
一化、CAN 编码）都从同一处读。

**2. 执行器接错话题等于绕过安全闸门。**
`actuator_node.c` 多处注释错写为 `control/raw_cmd`，与实际代码不一致。
**代码是对的，注释是错的**。这种「注释说谎」的情况在仓库里不罕见
—— 读者应以代码为准。如果哪天有人按注释改了 `transport_subscribe`
的目标，整道安全闸门就被绕过。

**3. dry-run 永远健康。**
不发帧的节点一直宣称自己健康 —— 把「发帧成功」与「帧计数」绑定后，dry-run
退化成「我健康但什么都没干」。同样的设计在很多监控系统里都有：心跳
≠ 真实工作。**经验之谈：健康判定要分两路，一路报心跳、一路报工作量**。

**4. PCA9685 上电先跳极限再回来。**
不写初始中位，舵机先抖到极限再回来。**这条修复虽然一行，但要在 cleanup
路径上再写一次才有意义** —— 同样在 cleanup 里也写一次，否则「停机 →
上电 → 启动」的循环里这一抖还是会发生。

**5. PWM 写失败静默吞掉。**
`pwm_set_pulse` 的返回值被丢弃，I2C 写失败没有任何日志。安全层的
`+SAFE` 标签、`control/debug` 的一切诊断，在硬件层失效时统统看不见。
**经验之谈：任何走到硬件的失败路径都要冒泡到软件的可观测性层**，否
则上游永远不知道下游已经死了。

**6. CAN 路径先钳位再编码，PWM 路径反之。**
两条路径对同一份输入的处理方式不同 —— 一个是输入侧防御、一个是输出侧
防御。两种都能用，但混用会让故障定位时困惑：到底是输入超了还是输出超
了？**经验之谈：两条等价的代码路径要保持同一种防御策略**。

## 八、与行业坐标

| | PX4 / ardupilot | Apollo D-Kit | Bosch 线控 | KunAutoDrive |
|---|---|---|---|---|
| 通信接口 | UAVCAN / PWM | CAN FD | CAN / FlexRay | I2C + SocketCAN |
| 多通道仲裁 | MAVLink | cyber RT 共享内存 | 内部私有 | topic-contract-gate |
| 仿真接口 | HIL | cyber sim | MATLAB/Simulink | flowsim |
| 仿真验证覆盖 | 全栈 | 全栈 | 部分 | 仅 PWM 后端 |

PX4 / ardupilot 是 UAV 起家，PWM 是天然接口；Apollo D-Kit 是面向高速乘
用车，全 CAN FD；Bosch 线控底盘把 CAN 当作内部私有协议，跑 FlexRay。
我们处于「RC 小车 + 真车原型」的中间形态 —— PWM 后端验证了端到端链路
的可行性，CAN 后端留作真车部署。

- **不再讨论 PCA9685 寄存器地址的位级布局** —— 那是 I2C 协议细节，
