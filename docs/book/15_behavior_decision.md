# 第 15 章：决策层为什么只回答「做哪件」，不回答「怎么做」

> **v2 范式章节**（2026-09 整治后保留）。本章保留低行号密度、真技术书
> 风格，参照 `docs/book/README.md` 写作风格约束与 `docs/book/08_discovery.md`
> 范式示范。v1 行号清单版本归档于 `docs/_archive/book_v1/14_behavior_decision.md`。

前面有辆车挡住了你。你脑子里其实同时转着两个问题——**走不走**，和**往哪走**。
前者是离散的（跟车、变道、让行、掉头，选项就那么几个），后者才是连续的（一旦
决定变道，方向盘得画出一条平滑曲线过去）。自动驾驶把这两件事拆成上下两层：
上层只管「选哪一个」，下层管「怎么走过去」。

本章讲上层：**行为决策器**。它坐落在感知融合之后、轨迹规划之前，整条链路上
唯一一个把「意图」翻译成离散选项的节点。它做的事情在外人看像是「点菜」，把
车子下一秒该干的事情从 8 个候选里挑一个出来，发给规划层去执行。

读完这一章你会知道几件事：

- 为什么 `Behavior` 消息只有 22 字节——它刻意只携带「意图」，不携带「连续量」
- 状态机里 8 个状态有 3 个其实是死状态——讲 FSM 的时候要把这个说破
- 跟车律为什么是 CTG（常时距）而不是固定距离
- 为什么变道条件是「三个 AND」，后向安全为什么左右不对称
- 行为决策器自己有一个真实失败故事——空障碍列表曾把整个决策块静默 30 秒

---

## 一、为什么把它单独拎出来

理论上，规划层完全可以顺手把「该不该变道」这个决策一并做了。但那样规划器就
要同时管两件性质完全不同的事——一件是几何拓扑（这条曲线能不能绕过去），另一
件是社会规则（这条曲线该不该走）。前者需要优化器求解，后者需要状态机表达。
两个工具搭在一起，状态机会被优化器的代价函数污染，优化器会被状态机的离散
分支绊住。

所以把这层决策切出来不是哲学偏好，是工具适配的结果：上层的离散选项用反射式
状态机自然（见第 04 章），下层的连续曲线用 Frenet 轨迹网格枚举自然（见下章）。
两个工具各管自己擅长的部分，决策器只是中间那条缝线。

```
感知/融合 ──► 行为决策（本章） ──► 轨迹规划（下章） ──► 跟踪控制
   连续量           离散意图            连续曲线           油门/刹车/转向
                  Behavior             Trajectory          ControlRaw
                22 字节 1 枚举         64 点 1 Hz           40 Hz
```

输出的 `Behavior` 消息只有 22 字节——这是设计上的明确信号：决策层到规划层之间
不传任何连续量。规划器拿到的只有「你要变道，目标是右边」这一类离散意图，具体
怎么变、变多快，是规划器自己的事。

> **作者立场**：把决策做成纯离散是这本书里少数几个我觉得「教科书就应该是这样
> 写」的边界。Apollo / autoware / Tesla 的实现在这一层都接近纯离散；偶尔出现
> 的「规划器直接看轨迹」「决策器兼任规划」的混合体，几乎都是工程妥协而不是
> 更好的设计。

## 二、状态机：8 个状态，5 个活着

行为决策器内部是一个反射式状态机（`include/state_machine.h` 那一套，第 04 章
讲过它的反射含义）。**这里的「反射」不是订阅消息，而是用同一张表同时驱动转移
和自省**——状态机引擎扫同一张表两遍（先非 auto，再 auto），查询 API 也读同一
张表。这个性质对行为决策很关键：每个 tick 都要问「我此刻能接受哪些事件」来
打日志、做单元测试，否则没办法排障。

```
8 个状态枚举值 = 200..207：

   CRUISE        = 200    ← 主状态：自由巡航
   FOLLOW        = 201    ← 主状态：跟车
   LEFT_CHANGE   = 202    ← 主状态：左变道中
   RIGHT_CHANGE  = 203    ← 主状态：右变道中
   STOP          = 204    ← 死状态：仅作 from，未作 to
   YIELD         = 205    ← 死状态：仅作 from，未作 to
   EMERGENCY     = 206    ← 完全死：无任何规则使用
   U_TURN        = 207    ← 主状态：掉头中
```

这个枚举表是这本书里值得停下来想一想的地方。**8 个状态里只有 5 个是真的可达
的**。`STOP`、`YIELD`、`EMERGENCY` 在转移表里只作为 `from`（起点）出现过——
没有任何规则的 `to` 是它们。连带的，`BehaviorCommand` 里那 3 个命令值（`BEH_STOP`、
`BEH_YIELD`、`BEH_EMERGENCY`）在生产代码里**永远不会发布出去**。讲这一章时
如果说「8 态状态机」，得同时说明 3 个是占位。

为什么会留下这三个占位？最早的版本把它们当作「我准备刹停/我准备让行/我紧急
制动」的语义状态机意图放进去了。后来发现它们的触发条件和安全层（见下下章）
的紧急制动、TTC 制动有冲突，干脆把决策让给安全层做。代码删了但枚举值还在，
新人改代码一不小心就会调用 `statem_transition(&sm, BEH_EV_BLOCKED, BEH_ST_EMERGENCY)`，
期望进入紧急模式——而状态机会返回一个非法策略错误，因为它根本不知道这个
目标状态长什么样。

> **「我不确定」**：要不要把这三个枚举值从代码里彻底删掉？维护上更干净，但
> 会破坏与外部监控（仪表盘显示、训练样本标注）的字段稳定。**目前保留是
> 显式选择**，未来可能改。

### 2.1 实际能走通的五条路径

```
                ┌────────────────────────────────────────┐
                │                                        │
[CRUISE]──BLOCKED──►[FOLLOW]──LOST_LEAD──►[CRUISE]       │
    │                  │                                │
    │                  │                                │
 OVERTAKE_LEFT  OVERTAKE_LEFT/RIGHT              UTURN_TRIGGER
 OVERTAKE_RIGHT       │                                │
    │                  ▼                                │
    │          [LEFT/RIGHT_CHANGE]                      │
    │            │           │                          │
    │       COMPLETED/TIMEOUT                            │
    │            │           │                          │
    └────────────┴───────────┴────►[CRUISE]             │
                                       │                │
                                 UTURN_TRIGGER          │
                                       ▼                │
                                   [U_TURN]─────────────┘
                                 COMPLETED/TIMEOUT
```

**注意变道完成后回的是 `CRUISE` 而不是 `FOLLOW`**。这意味着变道结束后车会重新
评估一次前车——如果变道是为了超车，那新车道上的前车仍会被检测到，下一拍就发
`BLOCKED` 回 `FOLLOW`。这个「多走一拍」的设计避免了状态在变道期间累积复杂
上下文。

### 2.2 频率是编译进去的

`config/pipeline.json` 的 `behavior_planner` 块**根本没有 `params` 键**。想改
运行频率只能改代码重编译——这违反了第 03 章讲的「三处都通」纪律：参数注册
中心里根本没有这条参数。诊断和热重载都做不到。

至于为什么没加，朴素的工程理由：行为决策的频率是参考规划频率（20 Hz）的硬
约束，跑太快会让行为抖动，跑太慢会让规划吃不到意图。**给一个不能调的比给
一个能调错的要好**。这是少数我赞同的「故意不灵活」的设计。

## 三、跟车律：常量时距

跟车是行为决策的核心问题：前方有车多快？该用多大间距？这两个量直接决定纵向
PID 的目标速度。KunAutoDrive 用的是**常量时距（Constant Time Gap, CTG）**，
不是固定距离，也不是自适应巡航里那种复杂的模型。

```
d_desired = d_0 + T · v_ego
v_follow  = v_lead + k_gap · clamp(Δ - d_desired, ±c)
```

三件事各解释一下。

**间距是速度的线性函数**。20 m/s 时 `d = 5 + 30 = 35 m`，2 m/s 时
`d = 5 + 3 = 8 m`。固定距离（比如 30 m）在低速时太远、高速时太近；CTG 让
**时间**而非空间恒定——这是接近人类驾驶员的策略。

**比例控制收敛**。`k_gap` 是比例控制：`Δ = 0` 时 `v_follow = v_lead`，**车
会自己收敛到期望间距**。不是精确证明——真实收敛速度取决于下游 PID 的增益
——但方向是对的。

**两个限幅各有必要**。`acc_gap_err_clamp = 8.0 m/s`：前车突然刹停时 `Δ`
可能到 −35 m，不限幅的话 `k_gap × (−35) = −14 m/s`，指令速度会变成负数。
限幅后最多是 `v_lead − 3.2 m/s`。`kFollowMaxRange = 200.0`：超过 200 m
的「前车」不参与跟车——远处的车用不着跟。

| 参数 | 默认 | 范围 | 物理含义 |
|---|---|---|---|
| `acc_standoff` | 5.0 m | 0.5–20.0 | 静止最小间距 |
| `acc_time_headway` | 1.5 s | 0.5–4.0 | 时距 |
| `acc_k_gap` | 0.4 s⁻¹ | 0.0–2.0 | 间距误差→速度的比例增益 |
| `acc_gap_err_clamp` | 8.0 m/s | 1.0–30.0 | 误差限幅 |

> **「这是经验之谈，不是教科书真理」**：常量时距系数（5 m + 1.5 s）是城市
> 高速工况的标定值，乡村道路（无前车连续车流）应该再保守一点，赛道场景
> 应该激进一点。本仓库不区分场景——统一用一组数。Apollo / autoware 在这
> 一点上做得更细，会按「高速/城区/低速」分桶切参数，但代价是状态机要多
> 一个「场景」维度。我个人倾向本仓库的简单做法——把场景自适应推到规划层
> 而不是决策层。

### 3.1 「被堵住」和「值得超」

跟车的核心不只是「多近要跟」，还有「多远该放手」。这里有两个判据：

**判据一：被堵住**（`blocked`）

```
r_blocked = max(r_min, k · d_desired)
```

`blocked_range_min = 30.0 m`，`blocked_range_mult = 3.5`。在 20 m/s 时
`d_desired = 35`，`r = 122.5 m`——**122 米内有车就算堵**。这不叫「被堵住」，
这叫「进入跟车模式的触发距离」。

**判据一之半：迟滞**（`follow_hysteresis = 1.3`）

已经在 FOLLOW 时，阈值放大 1.3 倍。这是标准的迟滞设计：进入用短阈值
（122.5 m），退出用长阈值（159 m）。没有它，车会在 122.5 m 这个边界上反复
横跳——这是 2026 年上半年在没有迟滞的版本上**实测到的 bug**，每帧在状态机
里进进出出，CPU 占用上升、轨迹抖动。

**判据二：最小超车间距**

```
d_min = min(d_cap, d_base + (v_ego - v_lead)+ · k_rel)
```

**这个公式的含义是：相对速度越大，需要的跟车距离越大。** 20 m/s 巡航、10 m/s
的前车，相对 10 m/s ⇒ `d_min = 25 + 20 = 45 m`。上限 90 m 防止高速时把阈值
推到不可达。

**判据三：值得超**（`worthwhile`）

```
worthwhile = blocked && (best_gap > min_gap)
```

**注意这是 AND**。间距比 `d_min` 还小的时候**不许超**——那时候超过去就是贴着
前车走，比跟着更危险。

## 四、变道：三条件与门

变道是行为决策里最复杂的一条规则。三个条件必须全部满足：

```
left_ok  = left_same_side && left_rear_safe && (left_gap  > min_gap × 1.5)
right_ok = right_same_side && right_rear_safe && (right_gap > min_gap × 1.5)
```

三个条件各解释一下。

**同向（`*_same_side`）**：邻道必须是同向车道。双向道路时 `lane_count/2` 以
下的车道是对向车道，禁止进入。**「误入对向车道」的恢复只允许移到最近的合法
车道**，并把两个 gap 都设成 `1e9`（禁用超车判断）。

**后向安全（`*_rear_safe`）**：后方来车不构成威胁。但**左右不对称**——这是
旧稿里最需要修正的地方：

- 左侧：`max(rear_safe_min_m, v_rear · rear_safe_time_s)`，**真正的运动学判据**
- 右侧：`max(min_gap, rear_safe_min_m)`，**固定的最小间距**

**这个不对称值得注意。** 右侧的判据不随后车速度增长，所以一辆 25 m/s 逼近
的后车，只要距离 ≥ `min_gap`（最高 90 m）就允许右变道。左侧更严格。反过来说，
**如果后车很快，右侧的判据会给出「可以变道」的结论**——这依赖规划器和控制
器的横向包络去兜底。

这不是 bug（右变道通常是往慢车道变，后车速度差小），但它是一个不对称的物理
假设，值得记住。

**前方空隙（`gap > min_gap × 1.5`）**：变道要求的前方空隙比跟车时更严——跟车
只要 `d_min`，变道要 `1.5 d_min`。这个 1.5 倍的余量给了轨迹插值时间。

> **「我不确定」**：0.8 章里讲到的安全控制能不能接住后向右侧判据过于乐观的
> 情况？理论上能——它会用 TTC 拦下来。但这是经验，没有定量验证过。**值得
> 未来做一组 sensor 模式回归**。

### 4.1 变道后的状态回滚

变道 `COMPLETED` 或 `TIMEOUT` 之后，状态机回到 `CRUISE` 而不是 `FOLLOW`。
原因是变道期间的「跟车」上下文已经过期——车道换了，前车也换了。再让车在
`FOLLOW` 里积累一个完整的状态周期，意味着变道后第一帧无法重新选目标车，会
沿着变道前那辆车的尾迹跑一两拍才反应过来。**回 `CRUISE` 等于强制重新评估**。

## 五、掉头：路端触发的单状态

掉头是行为决策里看起来最奇怪的状态——它没事件能进，只有事件能维持。

**所有状态都有一条 `UTURN_TRIGGER` → `U_TURN` 的转移**（包括死状态 `STOP` /
`YIELD`）。这看起来是「任意状态都能进入掉头」，实际上更准确的描述是「任意
状态都不能阻止掉头」。`UTURN_TRIGGER` 是路端到达事件——车开到了 ref_path
的尽头、或者路线规划要求掉头——每帧都发出。状态机从 8 个里挑一个能进掉头
的进。

`U_TURN` 自己的出口只有 `COMPLETED` 和 `TIMEOUT`，回到 `CRUISE`。`COMPLETED`
是机动跟踪器（见下下章）报告「掉头走完了」，`TIMEOUT` 是兜底——30 秒还没
走完就强制回 `CRUISE`。

```
[任意非U_TURN状态] ──UTURN_TRIGGER──► [U_TURN] ──COMPLETED/TIMEOUT──► [CRUISE]
```

注意 `UTURN_TRIGGER` 每帧都被发出，状态机每帧都拒绝（已经是 U_TURN 了）
或接受。日志里会看到 `[BEH] rule "X + UTURN_TRIGGER -> U_TURN"` 这种记录
反复出现，看着像重复触发，实际上是被拒绝的同一条规则在自审。

## 六、红绿灯门控

行为决策器把红绿灯当作「前方虚拟障碍」处理，不是当作状态机事件。这是行为
决策与规划层交接的边界选择：

```
stop_range = max(60, v²/8 + 23)   单位：米
```

`v²/8` 是减速距离（假设最大减速度 4 m/s²，加 23 m 的安全余量），下限 60 m
确保低速也能看到足够的红灯距离。如果前方 60~122 米内有红灯（依据减速距离
动态算），就当作有前车处理——FOLLOW 状态机就会接住。**这意味着红绿灯不是
单独的事件，而是前车检测的特例。**

绿灯状态（`TL_GREEN` / `TL_FLASHING_GREEN`）直接跳过——表示当前可以通行。
黄灯/红灯则按上述距离算「前车距离」。这种处理方式的代价是：行为决策无法
表达「准备停车等灯」和「已经停车等灯」的区别，二者都表现为 `FOLLOW` 状态
+ 目标速度被规划层压到 0。

## 七、决策器的真实失败故事：空障碍列表

2026-09-23 那次回归抓出来一个真实故事，比任何教科书都值得讲。

**症状**：默认编排跑 `curve_road` 场景，45 秒评估全绿——但车**从不掉头**。
它一路直行冲过 ref_path 终点，停在路网外的虚空里。门禁说一切正常，因为所有
活性门禁（碰撞、频率、拓扑）都是绿的。

**根因**：`on_raw_obstacles()` 收到 `perception/obstacles` 消息时，会做
一次空检查——如果 `count == 0`，它**直接 return**。这个判断的初衷是「感知
还没就绪，等下一帧」。但行为决策的主循环用了「`has_obs == true` 才跑决策」
这个守卫，所以**只要感知永远不返回任何障碍物（场景里确实没有），整个决策
块就被静默跳过了**——包括路端掉头触发 `UTURN_TRIGGER` 的发布。

**为什么活性门禁抓不到**：决策器静默 30 秒，它仍然在消费感知消息、仍然在
写日志——只是不再转移状态、不再发布 `planning/behavior`。从总线上看，节点
还活着，主题还在发，只是发的是占位符。

**修复**：把空障碍列表处理成「感知已就绪但场景里没东西」，而不是「感知未
就绪」。守卫 `if (has_obs)` 改成 `if (has_obs || last_seen_recent)`。

> 这个修复很轻，但**揭示了一个更深的问题：行为决策器不应该用「有没有收到
> 障碍物」来守卫自己的运行**——那是把上游的活性当成自己的运行前提。应该
> 用「上次收到障碍物是什么时候」来判断感知活性，超时才降级。这个教训后
> 来推广到了 sensor 编排的 `liveness gate`（见第 23 章）。

## 九、破除的 v0 错误说法

- **「8 个状态里 3 个不可达」**——v1 章节已经说破，但 v0 早期草稿写成「8 个
  状态都可达」，会被新读者反复误解。本章明确标注 5 个活的、3 个死状态。
- **「后向安全用的是 RSS（责任敏感安全模型）」**——v0 草稿这么写，代码里
  没有这个四分式。真实判据是纯运动学的 `max(rear_safe_min_m, v · t)`，且
  左右不对称。本章第 4 节明确破除。
- **「`evaluate_noa_navigation()` 这个函数存在」**——v0 草稿里点过一个函数
  名，仓库里没有。导航触发变道不在决策节点，在规划节点里。
- **「变道冷却 5 秒」**——v0 草稿写的 5 s，真实默认是 `lane_change_cooldown_s
  = 3.0 s`，30 s 那个是掉头专用的（`cooldown × 6`）。本章第 2.2 节明确。
- **「频率可调」**——v0 暗示行为决策器有运行频率参数，实际 20 Hz 是编译进
  去的硬编码。`pipeline.json` 的 `behavior_planner` 块没有 `params` 键。
