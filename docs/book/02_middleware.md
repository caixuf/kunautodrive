# 卷二 · 第二课：手写一个消息总线

## 本章问题

上一课结尾，你发现一件事：你的车不是一个程序在开，是 **15 个模块在协作**。感知模块
算出「前车 30 米外」，规划模块要拿到这个信息才能决定「减速」，控制模块要拿到规划
结果才能踩刹车。

那么问题来了：**这 15 个模块，怎么互相说话？**

这一章带你亲手写出答案。学完本章，你会理解：为什么「发布/订阅」是中间件的第一个
设计选择，为什么消息队列要存指针而不是存 64KB 的消息体，为什么要有 4 个分发线程，
以及时钟、协程、监控这些「看不见的地基」为什么存在。

## 你自己的答案：直接调用函数

假设你是第一次写多模块系统，最自然的想法是：**一个模块直接调用另一个模块的函数。**

```c
// 感知模块处理完点云，直接告诉规划模块
void perception_on_lidar(void) {
    ObstacleList obstacles = cluster(cloud);
    planning_on_obstacles(&obstacles);   // 直接调规划的函数
}
```

看，多简单。但运行几分钟后，你会发现三个问题：

1. **耦合**：感知模块要 `#include` 规划模块的头文件，规划模块要 `#include` 控制模块的
   头文件。你改一下规划模块的接口，感知模块也要重新编译。加一个「新模块想听障碍物
   信息」，你得去改感知模块的代码。
2. **不可替换**：你想把感知模块换成另一个更好的实现（比如从 DBSCAN 换成深度学习），
   但感知模块内部直接调了所有下游的函数——你没法只换一个。
3. **不可观测**：模块之间直接函数调用，你**没有地方**插进去「统计一下这些消息的频率」
   或「录下来回放」。出了问题，你只能干瞪眼。

这三个问题，本质上是同一个：**模块之间绑得太紧，紧到无法独立演化。**

## 一个关键转折：从「模块之间」到「模块与总线之间」

要解开耦合，办法是引入一个中间人——**消息总线（Message Bus）**。规则变成：

- 每个模块**不再直接认识其他模块**；
- 模块只做两件事：把消息**发布**到总线上（按话题名），或者**订阅**总线上的话题；
- 总线负责把发布者的消息，转交给所有订阅者。

```
  感知模块 ──publish("perception/obstacles")──▶ 消息总线 ──▶ 规划模块（订阅了该话题）
  规划模块 ──publish("planning/trajectory")────▶ 消息总线 ──▶ 控制模块
```

现在，前面三个问题全部消失：

- **解耦**：感知模块不再 `#include` 规划模块，它只认识「话题名」`perception/obstacles`。
  改接口 = 改话题契约，下游跟着改就行，不用改感知的代码。
- **可替换**：换感知实现 = 写一个新模块，发布同一个话题名。下游无感。
- **可观测**：总线成了所有消息的必经之路——你可以在总线上插统计、插录制、插监控。

这就是「发布/订阅」（Pub/Sub）模型。**它是中间件的第一个设计选择，也是整个项目通信
的基石。**

## 真正的方案：读消息总线的真实代码

下面是仓库里真实运行的 `src/core/message_bus.c`。我们不跳着看，跟着设计思路走。

### 第一步：总线要记住「谁订阅了什么」

总线必须维护一张表：话题名 → 订阅者回调。这是 `SubEntry`：

```c
typedef struct {
    char            topic[MSG_BUS_MAX_TOPIC_LEN];  // 订阅的话题名
    MessageCallback callback;                        // 收到消息时调用的函数
    void*           user_data;                       // 回调的用户数据
    bool            active;                          // 是否还在生效
    atomic_int      in_flight;                       // 当前在途回调数（后面讲为什么）
} SubEntry;
```

「订阅」= 往这张表里加一行；「取消订阅」= 删掉这一行。

### 第二步：发布 = 遍历表，调回调

发布消息的逻辑，本质就是一个循环：找到订阅了这个话题的所有条目，逐个调用它们的
回调。这就是「回调在发布者线程执行」这句话的由来——发布者在自己的线程里，直接调用
订阅者的回调函数。

**这里有一个性能陷阱**，值得停下来想：如果发布者逐个调回调，那么一个慢的订阅者
（比如处理要 50ms）会卡住发布者。所以项目又加了一层：**先把消息丢进队列，由独立
的分发线程去调回调**——发布者只要入队，立刻返回。

### 第三步：消息队列，为什么存指针不存消息体

这是 `message_bus.c` 里最值得读的一段注释（`RingBuffer` 的定义处）：

```c
/* 存 Message* 而非 Message 值：Message 内联 data[MSG_BUS_MAX_DATA_SIZE]=64KB，
 * 若按值存储，入队/出队各拷贝一次完整 64KB（memset 也 64KB），是压测吞吐瓶颈
 * （~70K 条/秒 ≈ 9GB/s memcpy）。改为堆分配 + 指针传递后，队列只搬 8 字节指针，
 * 拷贝从 128KB/条 降到 ~0，吞吐转为受 mutex/线程约束。 */
typedef struct {
    Message* msgs[MSG_BUS_QUEUE_SIZE];   // 只存指针！
    uint32_t head, tail, count;
    pthread_mutex_t mutex;
    pthread_cond_t  not_empty, not_full;
} RingBuffer;
```

**你为什么也会踩这个坑**：直觉上，「队列里存消息」听起来理所当然。但一条消息内联了
64KB 的缓冲区，按值入队 = 拷 64KB，出队再拷 64KB。每秒 7 万条消息，就是 9GB/s 的
内存拷贝——你的 CPU 全在搬数据，什么正事都没干。改成存指针，一次入队只搬 8 字节。
**这是「先想清楚数据有多大，再决定怎么存」的经典案例。**

类似的还有消息池：每消息 malloc/free 一次 64KB 太贵，就用互斥保护的空闲链表复用
已消费的消息块（`message_bus.c` 的 Message 池）。注释里还记了一个更狠的教训：早期用
**无锁栈**做池，高并发下触发 ABA 问题 → 同一节点被并发 pop 两次 → double-free 崩溃。
换成互斥链表后，用锁换来了正确性。**「无锁」听起来高级，但正确性永远优先。**

### 第四步：为什么是 4 个分发线程

单分发线程调回调，如果回调有耗时操作，吞吐就卡在单线程上。项目用 4 个分发线程并行：

```c
/* 多个生产者 message_bus_publish 按 msg_id % N 分片入队，
 * 每个分发线程独占一条队列（各自锁），并发 pop 并分发回调。 */
#define MSG_BUS_DISPATCH_THREADS 4
```

要点是**分片**：每个分发线程独占一条自己的队列，各队列之间无竞争。多生产者按
`msg_id % 4` 把消息分到不同队列。订阅表本身还是用互斥锁保护——「分片并行 + 共享结构
加锁」是并发编程的经典组合。

## 从进程内到进程外：发现总线不够用

消息总线解决了「一个程序里 15 个模块」的通信。但自动驾驶不是单进程的：你可能想把
监控单独跑一个进程、把仿真和算法分开跑、甚至跨两台电脑。

**跨进程怎么传高频数据？** 用 socket 太慢（每次拷贝 + 系统调用）。答案是**共享内存 +
无锁环形缓冲 + 信号量**：两个进程映射同一块内存，写端往里写，读端往里读，几乎零拷贝。

```
进程 A (写端)                     进程 B (读端)
  shm_open/mmap                    shm_open/mmap
        └── [head | data... | tail] ──┘  无锁 ring buffer
            sem_post ──▶ sem_wait（通知）
```

项目把 local（进程内）/ IPC（共享内存）/ TCP（跨机）统一收进一个 **Transport** 抽象，
业务层不关心消息走了哪条路——同机走 IPC，跨机走 TCP bridge。**这就是「面向接口，不
面向实现」**：上层写一次，底层可换。

## 为什么需要一个「统一时钟」

假设你要回放一段录制数据，验证新算法。录的时候，感知每 20ms 收到一帧。回放时，如果
各模块用「自己的墙钟」，那么「20ms 一帧」就乱了——有的模块快、有的慢，算法表现完全
失真。

解决办法：**全系统只认一个时钟**。回放时把这个时钟拨到录制时间；仿真时让它按任意
倍速走；测试时固定住让它可复现。这就是为什么项目规定 `clock_now_us()` 是唯一时间源，
谁直接调 `clock_gettime` 谁违规——**不是教条，是回放和仿真能不能工作的前提。**

## 协程（flowcoro）：让节点「优雅地等待」

现在到了这一卷最重要、也最值得多花笔墨的部分。消息总线解决了「模块怎么说话」，
但还留着一个更微妙的问题：**一个节点，在等数据的时候，代码该怎么写？**

### 问题：回调地狱

假设你写一个传感器融合节点：先等 lidar，再等 gps，然后融合。用回调，你写成这样：

```cpp
void on_lidar(const Message* m, void* self) {
    auto* node = (FusionNode*)self;
    node->lidar = *m;
    // 存下 lidar，等 gps...（逻辑在这里被打断）
}
void on_gps(const Message* m, void* self) {
    auto* node = (FusionNode*)self;
    // 拼起来（但"拼起来"的逻辑分散在两个回调里）
}
```

看明白问题了吗？**「先等 lidar 再等 gps 再融合」这一句完整的逻辑，被拆碎进了两个
回调**，中间状态（lidar 已经拿到了）只能靠成员变量存着。如果这个流程有 5 步（等 lidar、
等 gps、等超时、请求服务、等应答），你的逻辑就被拆成 5 个回调 + 5 个状态变量——
这就是**回调地狱**：读代码的人完全看不清「这个节点到底在干什么」。

### 真正的方案：让「等待」成为语言的语法

C++20 协程给出了一个漂亮的解：**把「等待」变成 `co_await` 语法**。逻辑可以按顺序写，
跟同步代码一样直白：

```cpp
Task run() override {
    while (!should_stop()) {
        // 等一条 lidar 消息，50ms 内没到就当丢帧
        auto r = co_await next_for("sensor/lidar", 50'000);
        if (r.cancelled()) break;          // 系统要停机，干净退出
        if (r.timed_out()) { watchdog(); continue; }
        process(*r);                       // 收到消息，处理
    }
}
```

这一眼就能看懂：「循环等 lidar，超时就报警，停机就退出」。**读协程代码就像读同步代码
——因为它的逻辑真的是按顺序写的。**

`co_await` 背后发生了什么？当你 `co_await` 一个 awaitable 时：

1. 协程**挂起**（suspend）——不占线程、不占 CPU，就「睡」在那里；
2. 数据到达时（bus 回调、定时器、或超时），某个恢复路径把它**唤醒**（resume）；
3. 协程从 `co_await` 的下一行继续执行。

**关键点：协程挂起时不占线程。** 如果 100 个节点都用协程等数据，你可能只需要几个线程
——这比「每个节点一个线程 + 忙等」省几个数量级。

### 四个等待原语

flowcoro 把消息总线的四类操作都包装成了 awaitable：

```
co_await next(topic)            等一条消息
co_await next_for(topic, us)    等一条消息，带超时（传感器丢帧/看门狗）
co_await select({t1, t2})       多路竞争，谁先到谁唤醒
co_await ask(topic, ...)        请求/应答（RPC）
        + _for(timeout) 变体
```

`select` 特别有用：你同时在等 lidar 和 gps，谁先到谁唤醒。用回调写，这是两个回调抢
一个变量；用协程写，是一次 `co_await`：

```cpp
auto r = co_await select_for({"sensor/lidar", "sensor/gps"}, 20'000);
```

### 优雅停机：协程最容易被忽略的正确性问题

现在问一个刁钻的问题：**协程正睡在 `co_await` 上，这时候系统要停机了，怎么办？**

最简单的想法：置一个 `stop_flag`。但问题来了——如果协程睡在「等消息」上，而消息永远
不来，那它**永远不会醒来检查 stop_flag**，永远退不出去。停机就卡死了。

flowcoro v2 的解法很干净：**取消不靠「唤醒」，靠「周期性醒来检查」**。每轮循环协程
都会检查 `rt::stop_requested()`；如果它正睡在带超时的等待上，超时本身就会周期性唤醒它
——所以协程最坏在「超时周期」内就会醒来、检查到停机、退出。

配合节点主循环 `node_pump` 的 200µs 休眠，整个系统对停机的响应最坏迟 200µs——
远小于任何实时窗口。**这就是为什么项目把「停机路径」看得和「正常路径」一样重：**
一个退不出去的死协程，比一个跑得慢的协程可怕得多。

### 调度：协程谁在跑（和那个烧满 CPU 的坑）

协程不是自己凭空跑的——它需要一个执行器（executor）来驱动。节点建线程的标准模式：

```cpp
flowcoro::rt::RtExecutor ex{{ .pin_cpu = -1 }};
g_node_exec = &ex;
ex.spawn(task->run(), "node_name");           // 把协程交给执行器
node_pump(ex, [] { return g.should_stop; });  // 驱动循环（该睡睡，该跑跑）
ex.shutdown();
```

`node_pump` 是这里的灵魂（也是卷二开头那个「8 个核烧满」事故的止血药）：

```cpp
inline void node_pump(flowcoro::rt::RtExecutor& ex, StopFn stopped) {
    while (!stopped()) {
        ex.run();                                          // 非阻塞 tick：跑就绪的协程
        std::this_thread::sleep_for(std::chrono::microseconds(200));  // 没活就睡 200µs
    }
}
```

`ex.run()` 是非阻塞的——它把「就绪的协程」跑一轮就返回。如果外面不 sleep，这个循环
就是死空转，把整颗核烧满。加 200µs sleep 的代价极小：对 20Hz 定频节点，定时器精度损失
0.4%；对消息驱动节点，事件延迟最多 +200µs——远小于任何传感器对齐窗口。**省下的是一整颗
CPU 核。**

### 可观测性：协程在干什么，要有数

协程卡在哪、每次等待多久——这是调试「节点为什么不动」的第一手信息。flowcoro 内置
`CoroStats`：

```cpp
task.resume_count();     // 恢复了多少次（协程活了多久）
task.coro_latency();     // 每次挂起→恢复的延迟分布（avg/p50/p99）
```

**如果协程从不恢复，`resume_count` 就不涨——你一眼就知道它卡在哪次等待上。** 这就是
「可观测性」在协程世界的价值：你不能 debug 一个你看不见的等待。

### 生命周期：三条硬规则

协程和线程、总线、对象混用，有几个必须遵守的规则（违反就是悬垂指针崩溃）：

1. **MessageBus 的生命周期必须长于引用它的 Task 及其协程帧**。销毁顺序：先让协程
   结束/取消、`execute()` 返回，再 `message_bus_destroy(bus)`，最后析构 Task。
2. **一次挂起，至多恢复一次**：消息 / 取消 / 超时三条恢复路径竞争同一个挂起点，
   必须保证只恢复一次——否则同一个协程帧被两个线程同时 resume，就是双执行。
3. **跨线程回调不能读 TLS**：bus/timer 回调可能跑在别的线程，那上面没有你的线程局部
   执行器——协程在挂起时要先把 `exec_` 捕获到自己身上。

## 小结

这一章你亲手经历了中间件的第一块地基：

- **问题**：15 个模块直接互相调函数 → 耦合、不可替换、不可观测。
- **方案**：消息总线做中间人，模块只「发布/订阅」话题名——解耦、可替换、可观测。
- **两个性能教训**：队列存指针不存 64KB 消息体；无锁栈有 ABA 坑，用锁换正确性。
- **三块看不见的地基**：统一时钟（回放/仿真能工作的前提）、Transport 抽象（进程内/
  跨进程/跨机统一）、node_pump（别把 CPU 烧满）。
- 你学会了「问题 → 朴素答案 → 为什么不够 → 真正方案」这套阅读方法，后面每一章
  都用它。
