# 第 12 章：录下来，再原样放一遍

> **v2 范式章节**（2026-09 整治后保留）。本章保留低行号密度、真技术书
> 风格，参照 `docs/book/README.md` 写作风格约束与 `docs/book/08_discovery.md`
> 范式示范。v1 行号清单版本归档于 `docs/_archive/book_v1/`。

算法迭代里最怕听到的一句话是「昨天还好的」。如果手边没有一份录下来的现场数据，一次
偶发的误刹车或者漏检就只能靠猜，改完也无从验证。这就是数据录制与回放存在的意义：它让
「可复现」变成一件自动的事。

这一章讲 KunAutoDrive 的持久化子系统怎么做到这一点：自研的 Bag v2 时序二进制格式负责快，
兼容 MCAP 标准负责和外部工具对接，两者共用同一套回放引擎。

## 一条数据从总线到磁盘，再回到总线

整条链路是单向的。运行时数据流经 BagWriter 异步落盘，再由 BagReader 按原时序重新灌回
`MessageBus`。中间那层 RingBuffer 把录制和仿真循环解耦，落盘走的是批量流式 I/O：

```
  ┌─────────────────────────────────────────────────────────────┐
  │                    运行时数据流 (Dataflow)                  │
  │  sensor/lidar (10Hz)  │  sensor/gps (20Hz)  │  control/cmd  │
  └──────────────┬──────────────────┬──────────────────┬────────┘
                 │                  │                  │
                 ▼                  ▼                  ▼
  ┌─────────────────────────────────────────────────────────────┐
  │             BagWriter 异步录制引擎 (后台 Worker 线程)       │
  │     RingBuffer 异步解耦 ──► 批量流式落盘 (POSIX I/O)        │
  └──────────────────────────────┬──────────────────────────────┘
                                 │
                                 ▼
                 ┌──────────────────────────────┐
                 │     out.bag (v2 二进制)      │
                 │      或 recording.mcap       │
                 └──────────────┬───────────────┘
                                 │
                                 ▼
  ┌─────────────────────────────────────────────────────────────┐
  │              BagReader 确定性离线回放 (Replay Engine)       │
  │     - 相对时延补偿 (us)   - 任意倍速播放 (0.5x~10x)         │
  │     - Topic 正则过滤     - 统一时钟注入 (Clock Service)     │
  └──────────────────────────────┬──────────────────────────────┘
                                 ▼
                     重新发布至 MessageBus
```

## out.bag 里到底存了什么

Bag v2 是冲着 SSD 顺序写入优化的，结构分三段：固定 64 字节的文件头、紧密排列的数据记录
流，以及尾部的索引区：

```
Bag v2 文件二进制布局：
┌──────────────────────────────────────────────────────────────────────────────┐
│ [Header 区: 64 字节固定]                                                     │
│   ├── magic: char[4] = "FLB_" (0x46, 0x4C, 0x42, 0x5F)                       │
│   ├── version: uint32_t = 3                                                  │
│   ├── msg_count: uint64_t (记录总数)                                         │
│   ├── duration_us: uint64_t (持续总微秒数)                                   │
│   ├── index_offset: uint64_t (尾部索引区的文件起始偏移量)                    │
│   └── _reserved: uint8_t[32] (保留对齐)                                      │
├──────────────────────────────────────────────────────────────────────────────┤
│ [Records 流: 紧密排列的消息帧]                                               │
│   ┌── Record 0:                                                              │
│   │     type_id(4B) | schema_hash(4B) | schema_ver(1B) | endian(1B) |       │
│   │     topic_len(1B) | topic(N B) | data_size(4B) | data(N B)               │
│   ├── Record 1: ...                                                          │
│   └── Record N-1: ...                                                        │
├──────────────────────────────────────────────────────────────────────────────┤
│ [Index 尾部索引区: 加速 O(1) 随机 Seek 与统计]                               │
│   ├── entry_count: uint64_t                                                  │
│   ├── entries: [ topic(64B) | count(8B) | first_off(8B) | last_off(8B) ] × N │
│   └── crc32: uint32_t (全文件完整性校验)                                     │
└──────────────────────────────────────────────────────────────────────────────┘
```

三段各司其职：Header 记总量与索引位置，Records 是消息帧本身，尾部索引区把随机 Seek 和
按 Topic 统计降到 O(1)，最后再留一个 crc32 做整文件完整性校验。

## 顺手兼容 MCAP

除了轻量的自研格式，KunAutoDrive 在 `src/core/mcap_writer.c` 里把 MCAP 标准也实现了一遍：
Schema Chunk 记录 IDL 数据结构定义（Protobuf / JSON Schema），Channel Chunk 定义 Topic
名称与编码格式，Message Chunk 装高压缩比的时序载荷。好处很直接——录出来的 `.mcap` 不用
转换，拖进 Foxglove Studio 就能在浏览器里看 3D 轨迹、点云、时序曲线和视频流。

## 回放时怎么把时间对齐

回放最核心的挑战只有一句话：怎样让两个消息帧之间的间隔，和录制时完全吻合。

```c
/* BagReader 高精度回放循环逻辑 */
int bag_reader_play(BagReader* r, MessageBus* bus, float speed) {
    uint64_t prev_record_ts = 0;
    uint64_t play_start_wall = clock_now_monotonic_wall_us();
    
    while (bag_has_next(r)) {
        Message msg = bag_read_next(r);
        
        if (prev_record_ts > 0 && speed > 0.0f) {
            // 计算两帧之间的录制时间差
            int64_t delta_record_us = (int64_t)(msg.timestamp_us - prev_record_ts);
            
            // 按倍速缩放
            int64_t target_delay_us = (int64_t)(delta_record_us / speed);
            
            // 精确等待（自适应补偿调用开销）
            if (target_delay_us > 50) {
                usleep(target_delay_us);
            }
        }
        
        prev_record_ts = msg.timestamp_us;
        
        // 驱动统一时钟（仿真时钟注入）
        clock_set_sim_time(msg.timestamp_us);
        
        // 重新发布到总线
        message_bus_publish(bus, msg.topic, msg.sender, msg.data, msg.data_size);
    }
    return 0;
}
```

这里有个必须守住的前提：所有时延计算都只能用 `CLOCK_MONOTONIC` 单调时钟。真车运行或
回放跨越整点 NTP 对时时，系统时间可能往前或往后跳一下，如果用 `CLOCK_REALTIME` 做差值，
算出来的间隔就是错的。

## 一次断电事故

有次测试机在录制途中被直接断电。重启后 `out.bag` 能打开，但 `flowctl bag info` 显示
`msg_count` 是 0，整段录制看起来像空的。

查下来问题出在 Header 的回填时机。顺序写入过程中，`msg_count` 和 `duration_us` 是在内存里
动态累加的，只有走到 `bag_writer_close()` 时才会 `fseek(0)` 把它们写回文件头。进程被强杀
或断电，这一步就没机会执行，文件头里留下的还是初始的 0。

改法是让读的一端别那么依赖 Header：`BagReader` 打开文件时做一次向前容错扫描，如果发现
`index_offset == 0`，就从头顺序扫一遍记录，在线把索引重建出来。这样即便文件没被正常收尾，
里面的数据依然是完整的。

## 四、该录什么，不该录什么

前面讲了「怎么录」。这一节讲**录什么**——因为「全录」听起来最安全，实际上往往既不
安全也不够用。

### 全量录制的代价是算出来的，不是感觉出来的

`bag_writer_attach` 的实现是订阅通配符 `*`，也就是总线上的一切。一个字节级的账：

| 消息 | 打包后大小 | 频率 | 带宽 |
|---|---|---|---|
| `LidarPointCloud`（满 2048 点） | 40980 B | 20 Hz | 819 KB/s |
| `ObstacleList`（满 128 个目标） | 4496 B | 20 Hz | 90 KB/s |
| `ControlCmd` | 几十字节 | 40 Hz | < 2 KB/s |
| `flowrec/status`（JSON 状态） | 几百字节 | 1 Hz | 忽略不计 |

第一行是重点：**点云一个 topic 就能吃掉 800 KB/s**。录 10 分钟 = 480 MB，录 1 小时
≈ 2.9 GB。而且写入端是 1 MB 的环形缓冲，落盘线程跟不上时**最多等 10 毫秒就丢帧**
——注意是丢帧，不是阻塞业务。所以全量录制在带宽吃紧时的真实行为不是"变慢"，
是"静默丢数据"。控制节点那类 40 Hz 的关键指令如果被丢了，回放出来的场景是
"看起来跑完了，但车没按剧本走"。

### 建议的取舍

| 类别 | 例子 | 该不该录 | 理由 |
|---|---|---|---|
| 高频大载荷 | 原始点云 | 事件触发，环形留 5 秒 | 带宽之王，平时用不上，出事才要看 |
| 算法输出 | 障碍物列表、轨迹、行为 | **常开必录** | 体积小，是复现决策过程的关键 |
| 执行指令 | `control/cmd` | **常开必录** | 没有它就无法判断"车到底做了什么" |
| 状态与心跳 | 节点状态、延迟报告 | 可选 | 排查沉默失败时有用，量不大 |
| 诊断与调试 | 节点内部 trace、调试 JSON | **不录** | 量大、价值低、还会把关键数据挤掉 |
| 训练样本 | 已抽好的 JSONL | 不进 bag | 已经有独立的采集通道（见第 24 章） |

关键的一条判断标准是：**没有它，你能不能判断这次运行是"算法错了"还是"输入就不对"？**
`control/cmd` 之所以必录，正是因为它承担了这个区分责任——它记录的是"车实际做了什么"，
而不是"算法想做什么"。

## 五、`schema_hash` 这个字段为什么值得加进格式

Bag 的文件头里有一个 `version`，从 2 升到了 3。这个版本号不是随便升的——**格式里多
了一个 4 字节的 `schema_hash` 字段，插在 `type_id` 后面**，record 头和索引条目里都有。

### 它防的是什么

三个标识符的分工是这样的：

```
  type_id          "这是什么消息"        → 字段签名串的哈希，递归展开嵌套结构
  schema_version   "这个结构的第几版"      → 人工维护的整数
  schema_hash      "这个结构长什么样"      → 字段级布局哈希，不递归嵌套
```

`type_id` 和 `schema_hash` 覆盖的敏感范围不同：一个只看**名字**，一个看**布局**。
于是这样一对组合能定位到问题：

| 现象 | 判断 |
|---|---|
| `type_id` 变了 | 消息的**种类**变了（八成是线格式不兼容） |
| `type_id` 没变、`schema_hash` 变了 | 同一个消息类型**加字段或改了字段类型** |
| 两个都没变、`schema_version` 变了 | 只是人工升了版号，线格式可能没动 |
| `type_id` 和 `schema_hash` 都没变、但消费者拒收 | 该查消费者自己的判别逻辑 |

**如果没有 `schema_hash`**，第二行这一整类问题都会被归到"版本号变了，我猜是哪里不兼容"，
而实际上答案就在文件里。4 字节换掉一类猜谜，我认为很值。

### 代价与向后兼容

代价是每条记录多 4 字节、每个索引条目多 4 字节——对点云那种载荷来说可以忽略，
对小消息来说是几个百分点的膨胀。兼容性上，读端按 `version` 分发：v3 按新格式解析，
v2 缺的那 4 字节按 0 处理。**这是一个干净的字段级前向兼容**，因为新字段插在中间而
不是在末尾，靠版本号区分。

> **踩坑记录**：这里有一个我在验证时发现的、**至今仍然存在的不对称**，值得完整写下来，
> 因为它是"看起来对、跑起来也对、但索引已经废了"的那类问题。
>
> 写端在关闭文件时回填索引，每个条目依次写 topic、count、first_offset、last_offset、
> `type_id`、`schema_version`——**唯独没写 `schema_hash`**。而读端在 `version >= 3` 的
> 分支里，期望在 `type_id` 之后读 4 字节 `schema_hash`，然后才读 `schema_version`。
>
> 后果是**每个索引条目比写端多 4 字节**。我实际录了一个双 topic 的 bag 验证：
> 文件头写着 2 个索引条目，读端解析第一个条目时，把写端写的 `schema_version`(1 字节)
> 加上 crc 的前 3 字节当成了 `schema_hash`，然后 `fread` 失败——**整个索引丢失**。
>
> **而记录数据本身完全没问题。** 逐条扫描 record 流可以正确读出全部 46 条消息
> （30 条 `sensor/lidar` + 16 条 `sensor/gps`），只是索引不可用了。读端有一条容错
> 路径（索引为空时全文扫描重建 topic 统计），所以工具照样能把文件打开、显示
> 正确的 topic 列表——**这恰恰是它难被发现的原因**。
>
> 我不确定当初补 `schema_hash` 时为什么漏了索引这一处：record 头补了，索引条目补了
> 读端，就是忘了补写端最靠后的那个字段。**教训是：格式升级时"读端测试"和"写端测试"
> 是两套测试，只有往返（写→读）测试才能发现这种不对称。**

## 六、回放的确定性：时间戳倒挂把 1× 回放冻住

前面贴过一段回放循环的示意。真正实现里有三处细节，比示意复杂得多，每一处都对应一个
具体的坑。

### 睡眠是分片且可中断的

回放等待不是一次 `nanosleep` 了事，而是切成**不超过 10 毫秒的碎片**，每片之前检查
一次停止回调。原因是停止信号（Ctrl-C、时长截止）必须在有界的延迟内被响应——一次
睡 2 秒的等待会让 Ctrl-C 等 2 秒。

### 倍速是把间隙除以倍数，不是睡固定间隔

给定相邻两条记录的录制时间差 `gap`，实际睡眠 `gap / speed`。`speed = 0` 表示
"尽快回放"，直接不睡。**这个设计有个隐含要求：bag 里的时间戳必须单调递增，
否则 `gap` 的计算就是错的。**

### 时间戳倒挂：真实的 584 年

这条值得单独讲，因为它是我在这个仓库里见过最有戏剧性的一个 bug 形态。

多线程录制时，不同 topic 走的是各自的时间源，写入顺序不保证与时间戳顺序一致。
结果相邻记录的时间戳会**轻微倒挂**——源码注释里写的是实测可达约 300 微秒、几百处。

```
  prev_ts = 1000000
  ts      =  999700          ← 倒挂 300 µs

  若按无符号相减：gap = 999700 - 1000000
                       = 18446744073709550716  （≈ 2^64）
  再除以 speed=1.0 → 约 1.8×10^19 µs ≈ 584 年
  → sleep_interruptible_us(584 年)
  → 1× 回放永久冻结
```

修法是这一行：

```c
uint64_t gap_us = (ts > prev_ts) ? (ts - prev_ts) : 0;   /* 倒挂视为 0 间隙 */
```

倒挂时**不追赶、不倒退、不睡眠**，当作 0 间隙直接发。这是对的——因为倒挂的那几百微秒
本来就在录音抖动范围内，纠结它没有意义。**关键是它绝不能变成一次无符号下溢。**

> **这一节最值得记住的不是那个修法，是它的形状。** 一个「记录是乱序的」这样完全正常的
> 物理事实，通过「无符号减法」这一个语言细节，被放大成了 584 年的挂起。数据是对的、
> 意图是对的、只有一行算术是错的。**在时间戳这类量上，永远不要做无符号减法，
> 除非你已经证明了两边单调。**

### sim clock 到底要不要驱动

回放接口有一个开关：是否在每条消息前把 `clock_now_us()` 推进到录制时间戳。它的默认
行为是「如果进程已经在仿真模式，就跟着走」。

但启动器在单进程回放时**显式地关掉了它**，并且在代码注释里写清了原因。这段注释
本身就是一份好教材：

- 被驱动的 `clock_now_us()` 返回注入的消息时间戳，而不是单调墙钟；
- 依赖 `clock_now_us()` 排程的节点（比如监视器的 60 Hz 拓扑导出）在回放期间
  **只导出一帧**，于是 3D 可视化停在首帧；
- 而回放时所有计算节点都被 bag 输出覆盖而跳过，**没有任何节点需要被驱动的仿真时钟**。

> **作者立场**：这是我全书里最喜欢的几行注释之一。它示范了**一个诚实的取舍陈述**
> 应该长什么样：先说"我们本来打算怎么做"，再说"为什么不做"，最后说"在当前架构下
> 什么方案是对的"。它没有说"这是最佳实践"，也没有假装别的做法是错的。
>
> 更深一层：这个决定背后的判断是——**仿真时钟的语义是"我是仿真主循环的步进源"，
> 而不是"我是所有时间的权威"。** 之前把它当后者用，就会出现回放冻住 3D 这种
> 完全无法从错误信息里推出来的现象。

## 七、按配置留存 vs 全量录制：两条路的真实分工

仓库里其实有**两套录制**，它们的分工不是重复，而是不同的问题。

```
  全量录制（bag_writer_attach）
    订阅 "*"，一条不漏
    适合：调试期、算法迭代、复现某个整体行为
    代价：带宽/存储大，高频大数据可能静默丢帧

  按配置留存（flowrec）
    每个 collector 自己列 topic 清单（1~32 项，精确匹配，不支持通配）
    适合：车上/量产部署的常态采集
    代价：配置错了就录不到，不存在"全量兜底"
```

flowrec 比全量录制多出来的一整套能力，全都是围绕「**按配置留存**」这个前提设计的：

| 能力 | 全量录制有吗 | 为什么需要它 |
|---|---|---|
| 每个 collector 独立 topic 清单 | 没有（只有 `*`） | 传感器数据和指令流分开存放，便于事后取舍 |
| 事件触发 | 没有 | 平时不录，出事才录 |
| 触发前的滚动缓冲 | 没有 | **事故发生时需要看到"事前 5 秒"**，而事中才触发 |
| 触发后的续录窗口 | 没有 | 事故的因果链在触发之后才展开 |
| 按大小轮转 | 有 | 单文件不超过 1 GB 默认值 |
| 按时间轮转 | 有 | 支持 `hourly` / `daily` |
| 独立的输出路径模板 | 没有 | 传感器和事件分文件，互不覆盖 |

其中**预缓冲**是最能体现设计意图的一项。它解决的是一个看起来无解的问题：
"只在急刹时才录"听起来很好，但急刹的原因发生在急刹**之前**——你不可能在原因出现的
瞬间就知道后果。所以必须在**一直录着但只存在内存里**、触发时把最近几秒倒出来。
代价是这部分内存有上限（可配，默认 32 MB），超了淘汰最旧的。

### 两条路怎么选

我的判断标准很简单：

| 你的处境 | 选哪条 |
|---|---|
| 改算法，要对比改动前后的行为差异 | 全量。**这时候"多录"的代价远小于"少录"的代价** |
| 车上常态部署，磁盘有限 | flowrec 按配置 |
| 出了事故，要看现场 | 事件触发 + 预缓冲 + 后窗口 |
| 想长期保存数据集 | flowrec + 按时间轮转，**并确认它有事件触发** |

> **作者立场**：我倾向于认为全量录制是**开发期的正确默认值**，按配置留存是**部署期的
> 正确默认值**，把全量当常态部署用是把两个阶段的最佳实践混在一起。反过来更危险——
> 在车上跑按配置留存，一旦某次配置写漏了一个 topic，那一路数据就永久缺失，
> 而且**要等到需要它的那天才会发现**。这类不可逆的缺失比多占几个 GB 磁盘贵得多。
>
> 如果两者非要选一个作为默认，我选全量。理由很简单：**缺失的数据补不回来，
> 多余的数据可以再删一遍。**
