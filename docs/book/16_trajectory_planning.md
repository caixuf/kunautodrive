# 第 16 章：为什么把规划硬塞进 Frenet 坐标系

> **v2 范式章节**（2026-09 整治后保留）。本章保留低行号密度、真技术书
> 风格，参照 `docs/book/README.md` 写作风格约束与 `docs/book/09_discovery.md`
> 范式示范。v1 行号清单版本归档于 `docs/_archive/book_v1/15_trajectory_planning.md`。

直路上，用 `(X, Y)` 说清车在哪儿就够了。可路一弯起来，道路自身的曲率会把
约束搅成非线性，横向和纵向缠在一起解不开。**Frenet 坐标系（沿参考线的弧长 `s`
和垂直偏移 `d`）是这件事的经典绕法**——两个维度当场分开，约束和代价都变成
对 `s` 和 `d` 的独立函数。

本章讲 KunAutoDrive 怎么落地这件事：

1. 参考线投影——把笛卡尔坐标变成 `(s, d)`
2. Frenet 轨迹生成——`third_party/frenet_planner` 那套 zhmzhu 算法
3. S-T 图动态规划——纵向速度剖面（`st_graph.c`），以及碰撞扫掠

读完这一章你会知道几件事：

- 为什么本仓库的「Frenet 投影」其实是**最近点投影**，不是真正的 Frenet 变换
- 为什么整条算法链**没有任何 QP 求解器**——横向是网格枚举，纵向是动态规划
- 「先粗搜后精修」是教科书的常见套路，本仓库**两段都不存在**
- 障碍物 AABB 角点为什么按自身速度外推 2 秒
- 为什么 2079 条候选是这条算法的「上限」，再多就跑不动了

---

## 一、为什么切到 Frenet

笛卡尔坐标里规划一条带避障的轨迹，问题可以写成：

```
min  ∫ (曲率² + 加速度² + dt²) ds
s.t. 轨迹不撞障碍物、起点 = 当前位姿、终点 = 目标位姿
     |曲率| ≤ κ_max, |a| ≤ a_max
```

这一坨约束里，**「轨迹不撞障碍物」和「曲率」是耦合的**——障碍物在世界系是
一个个 AABB，轨迹弯过来才能避开；曲率又得算世界系的几何。把这两个量解耦
的最朴素做法是换坐标系：

```
(s, d)：s = 沿参考线走了多远, d = 偏离参考线多少
```

切到 `(s, d)` 之后：

- 障碍物投影到 `(s, d)` 变成一个个矩形区域
- 轨迹用 `d(s)` 表达，「避障」变成「`d(s)` 不穿过障碍区域」
- 曲率约束近似成「`d(s)` 二阶导连续」
- 横向和纵向**第一次**可以被分开处理——`d(s)` 是横向，`s(t)` 是纵向

这就是 Frenet 坐标系为什么流行。它不解决「我怎么找到最优轨迹」，只解决
「我怎么把问题写得能解」。剩下那一步才是算法的工作。

> **作者立场**：Frenet 是工具不是目的。当参考线本身就是简单直线时（停车场
> 场景、低速泊车），笛卡尔规划反而更简单——别为了用 Frenet 而用 Frenet。本
> 仓库的掉头/泊车场景用的是机动跟踪器（第 17 章），不是 Frenet，原因正是
> 参考线在那里是断的/双向往的，Frenet 投影没定义。

## 二、参考线投影：最近点，不是 Frenet 变换

仓库里 `modules/adas_nodes/planning_coordinates.h` 的 `project_to_path` 是
**最近点投影**，不是教科书里严丝合缝的 Frenet 变换。理解这两者的区别是
读懂本章的前提。

### 2.1 它做的是什么

逐段遍历参考线，对每段求「点在段上的最近点」（参数 `t` 钳位在 `[0, 1]`，
**不外推**），比较所有段的最近点距离取全局最小。最终输出 5 个字段：

```
Projection {
  s:        沿参考线的纵向弧长
  d:        垂直参考线的横向偏移（左正右负）
  ref_x:    投影垂足世界坐标
  ref_y:    投影垂足世界坐标
  heading:  投影垂足处的切线航向角
}
```

四个公式一行行展开：

```
t = clamp(((p - r_i) · v_i) / |v_i|², 0, 1)       ← 段上最近点的参数
s = s_i + t · |v_i|                                 ← s 用弦长累加
θ = atan2(v_iy, v_ix)                               ← 段切线航向
d = -(Δx) sin θ + (Δy) cos θ                        ← d 是左法向投影
```

**`d` 的符号约定**：残差向量在**左法向**上的投影，**正值 = 参考线左侧**。

### 2.2 四个必须知道的性质

**其一：这不是真正的 Frenet 变换，是最近点投影。**

`t` 被 clamp 到 `[0, 1]`——**不外推**。这意味着：

- 点在参考线端点之外时，投影被拉到端点上，不会算外推的 `s`
- **自相交/回折的路径**上，同一个笛卡尔点可能有多个 `(s, d)`，取的是**最先
  命中的那一段**

真正的 Frenet 变换需要沿法线求交点，而最近点投影是它的**简化近似**。在参考线
曲率半径 `R` 大于 `|d|` 时两者等价；`|d| > R` 时最近点投影仍然有定义（不会崩），
但给不出唯一解。

旧稿说「真撞上 `|d| > R_min` 就退回笛卡尔坐标系直接规划」——代码里没有这条
路径。实际做法是 `project_to_path` 失败（返回 `false`）时走**车头坐标系兜底
投影**（行为节点和规划节点各有类似分支），那仍然不是笛卡尔规划，只是换了
个投影方式。

**其二：弧长用的是弦长，不是 `ref_s` 的间距。**

```
s = s_i + t · |v_i|
```

`ref_s[i]` 只作为**每点的偏移锚点**，段内增量用的是欧氏弦长 `|v_i|`。如果
调用方传的 `ref_s` 数组和实际点距不一致，`s` 会**累积漂移**。

实践中两者是一致的——上游 `behavior_planner` 和规划节点的 `ref_s` 都是用同样
的 `hypot` 累加出来的——但这是个**没有写在任何地方的隐含不变量**。

**其三：并列时取靠前的段。**

距离完全相同时保留先遍历到的那段。这在路口附近（两段参考线几乎重合）会有
影响——车的 `s` 会更靠近起点方向而不是终点方向。

**其四：退化段静默跳过。**

零长度段（前后两点重合）会被静默跳过；如果**所有**段都退化，函数返回 `false`。

### 2.3 车道映射：三个纯函数

仓库还提供三个**纯函数**（`planning_coordinates.h` 的 `lane_center_d`、
`first_legal_lane`、`nearest_lane`），把 `(s, d)` 和车道索引互转。

```
d_lane_center = -(i - (N-1)/2) · w
i_nearest     = max(min_floor,  min(N-1, round((-d)/w + (N-1)/2)))
```

```
代入 N=4, w=3.5：
 车道索引    d 中心
   0         +5.25   ← 最左车道
   1         +1.75
   2         −1.75
   3         −5.25   ← 最右车道
```

`first_legal_lane` 是双向道路时的合法车道下界。双向道路时 `lane_count/2`
以下的车道是对向车道，禁止进入——决策器的变道保护和这里是同一个判据。

## 三、Frenet 轨迹生成：三级网格枚举

**`frenet_plan` 本身不做任何优化**——它是一层 marshaller，调
`third_party/frenet_planner` 的 `run_fot()`，后者才是真正的算法。这两个层
的关系是：上层把世界系的输入打包成 Frenet 初始条件，下层暴力枚举网格求最
优。

### 3.1 障碍物按自身速度外推 2 秒

```
pred_horizon_s = 2.0

px = obs_x[i]
py = obs_y[i]
if has_velocity {
    px += ovx[i] · 2.0
    py += ovy[i] · 2.0
}
// 再用 ow[i]/ol[i] 取 AABB 角点
```

理由：`frenet_plan` 的预测时域 `maxt = 10.0 s`，如果把障碍物按当前位置当
静止障碍，规划到第 5 秒时它实际已经在别处了。2 秒是一个折中——覆盖最关键的
近期决策，又不至于把远处的障碍推到离谱的位置。

> **`frenet_set_obstacles`（不带速度）是死代码**。头文件自称「static version,
> backward-compatible」，但全仓库零调用。生产只用带速度的
> `frenet_set_obstacles_v`。这是一个**保留的死接口**——上游 zhmzhu 算法支
> 持它，所以桥接层也支持，但本仓库不用。

### 3.2 一个静默的容量截断

桥接层函数内有 `static double llx[32], lly[32], urx[32], ury[32]`——硬编码
32 个障碍物上限。而规划节点分配的是 `ox[128]`——**它会老老实实传最多 128
个进去，然后第 33 个之后被静默丢弃**。

症状是「密集车流里前车没被规划器看见」，而且没有任何日志。这个 bug 是
2026-09 在 sensor 编排场景里**实测发现的**：urban_challenge 那个场景有 40+
NPC，编号 33 之后全是「隐身」的。

### 3.3 真正的算法：暴力网格枚举

`third_party/frenet_planner/src/FrenetOptimalTrajectory/FrenetOptimalTrajectory.cpp`
里做的事**没有梯度、没有 QP、没有迭代**。横向是五次多项式，纵向是四次多项式，
两条网格在三维上穷举：

**横向：五次多项式**

六个边界条件：

```
s=0    s=T
d:    c_d       di       ← 起点偏移 / 终点偏移
d':   c_d_d     0        ← 起点横向速度 / 终点横向速度
d'':  c_d_dd    0        ← 起点横向加速度 / 终点横向加速度
```

系数用 **Eigen 的 LU 分解**解（`QuinticPolynomial.cpp` 的 `#include <Eigen/LU>`）。
所以「解 6×6 方程组」在数学上是对的，只是实现上依赖 Eigen。

**纵向：四次多项式**

五个边界条件（少了一个，所以次数低一档）：

```
s=0    s=T
s:    s_0       tv       ← 起点位置 / 终点位置
s':   c_speed   0        ← 起点速度 / 终点速度
s'':  0
```

同样用 Eigen LU。

**为什么纵向是四次而横向是五次**：纵向只有 5 个约束（起点位置/速度/加速度 +
终点位置/速度），所以最低次数是 4；横向要保证加加速度连续，5 个约束不够，
需要 6 个。

### 3.4 候选数量：2079 条

网格规模：

| 维度 | 取值 | 个数 |
|---|---|---|
| 横向目标 `d_i` | `{-6, -4.5, -3, -1.5, 0, 1.5, 3, 4.5, 6}` m | 9 |
| 横向时域 `t_i` | `2.0 .. 10.0` 步 `0.25` s | 33 |
| 目标末速 `v_t` | `v ± 6` m/s 步 `2` | 7 |

```
9 × 33 × 7 = 2079 条候选路径
```

每条最多 41 个采样点（10 s / 0.25 s + 1）。

> **这是暴力枚举，不是优化器。** 每拍生成 2079 条五次+四次多项式曲线，逐条
> 采样、逐条检查可行性、逐条算代价。20 Hz 下就是**每秒 4 万条曲线的构造与
> 求值**。
>
> 之所以可行，是因为状态空间被离散得很粗（横向 1.5 m、时域 0.25 s、末速 2
> m/s），而乘积恰好落在可算的范围内。

> **「这是经验之谈，不是教科书真理」**：我尝试过把网格加密（d_road_w=1.0,
> dt=0.2），候选数涨到 ~8000，每秒 16 万条，20 Hz 跑不下来。**横向 1.5 m
> 步长是「能跑」和「够准」之间的实际边界**，不是理论最优。

### 3.5 代价函数

```
J = k_lat · J_lat + k_lon · J_lon + k_o · J_obs

J_lat  = k_d · 横向偏差 + k_v · 横向速度 + k_a · 横向加速度 + k_j · 横向 jerk
J_lon  = k_a · 纵向加速度 + k_j · 纵向 jerk + k_t · 耗时 + k_d · 末速偏差
J_obs  = ∑ (1 / closest_to_obstacle_i)
```

注意几个细节：

- `J_lon` 里**复用了 `k_d`、`k_a`、`k_j`**——这是 zhmzhu 上游代码的原样，
  `J_lon` 里用 `k_d` 罚末速偏差、`k_a` 罚纵向加速度、`k_j` 罚纵向 jerk。
  不是专门的纵向权重，是上游的设计。
- `c_end_speed_deviation` 是**线性** `|Δ|`，不是平方
- `inverse_distance_to_obstacles` 对**每个（障碍物，采样点）对**求 `1/closest`
  求和，`closest` 取到 AABB 四角的最小距离——离障碍物越近，代价越大，但**倒数
  这一选择让「几乎撞上」和「离得很近」的区分度不高**。

### 3.6 可行性过滤

逐采样点检查四类约束：

```
|ṡ|    > max_speed       → 拒绝
|s̈|    > max_accel       → 拒绝
|c|    > max_curvature    → 拒绝   (max_curvature = 0.3)
is_collision(obstacles)  → 拒绝
```

碰撞检查用车身轮廓 + 线段对 AABB 边的求交，但**只在采样点上**——这正是下
一节要量化的那个「点测」局限。

## 四、S-T 图：纵向速度剖面

横向曲线有了，纵向速度呢？`frenet_plan` 给出的只是「`s` 在 `t` 时到 `tv`」，
是 `s` 的一次多项式，但它和前方障碍物（特别是红灯墙）的速度剖面**没有闭
环**——只知道终点速度，不知道中间过程的速度轨迹。

这一步由 `modules/adas_nodes/st_graph.c` 的 `st_graph_plan` 独立完成。它
的输入是前方障碍物投影到 `(s, t)` 平面的占用栅格（每个障碍物是一个矩形），
输出是「`(s, t)` 网格上的最优路径」——纵向速度剖面。

### 4.1 网格结构

```
90 行（s 维度） × 101 列（t 维度）
```

行方向是空间（90 个等间距 s 点），列方向是时间（101 个等间距 t 点）。每个
格子代表「`t` 时刻车到达 `s` 位置」。

### 4.2 DP 状态

`st_graph.c::st_graph_plan` 用**动态规划**在这个网格上找一条从起点（`s=0,
t=0`）到终点（任意 `t=t_end`）的最优路径：

```
DP 状态：dp[i][j] = 到达 (s_i, t_j) 的最小代价
DP 转移：dp[i][j] = min{ dp[i', j'] + cost(s_i, s_i', t_j, t_j') }  (i' ≤ i)
约束：格子被障碍物占据 → 不可达
```

代价通常包含：

```
J = 加速度² · w_a + jerk² · w_j + 末速偏差 · w_v + 撞墙惩罚（如果撞了）
```

「撞墙惩罚」是这里的关键技巧——某些格子**理论上可以到达但不应该到达**（前
方有静态障碍/红灯），强行让 DP 走过去的代价比绕过去大几个数量级，相当于
「禁入区用极大代价软表示」。

### 4.3 零单测的事实

`st_graph.c` 是仓库里**零单测**的关键模块之一。它的算法虽然经典（DP + 闭式
前驱预筛），但行为细节（起点位置钳位、终点列选择、障碍 AABB 在 S-T 平面
的形状）都没有测试覆盖。2026-08 那次传感器编排的 W3「碰撞点测非扫掠」调查
里发现，**`st_graph.c` 的障碍占用栅格生成是手工算的，没有单元测试**——任
何对算法边界的修改都必须用 `ci/evaluators/demo_evaluator.py` 跑 45 秒回
归验证。

## 五、扫掠碰撞检查：W3 是怎么暴露的

Frenet 的「点测」局限性有一个真实故事。

### 5.1 「点测」是什么

`frenet_plan` 的可行性过滤只检查每个采样点（`dt=0.25 s` 一个）是否撞到
障碍物。**采样点之间不检查**。一条在采样点 `i=10, 11` 都「没问题」的轨迹，
完全可能在 `i=10.5` 这一瞬时穿过障碍物——只是没有采样点落在这里。

### 5.2 W3 的暴露

2026-09 的 sensor 编排回归里，`dense_npc` 场景跑出来一个奇怪的碰撞：规
划器说「没有撞」，但实际轨迹在第 8 秒和第 8.5 秒之间穿过了一个 NPC 的
AABB 边缘。

复盘发现：

1. Frenet 网格的采样间隔 0.25 s
2. NPC AABB 大小 4×1.5 m
3. 轨迹在两个采样点之间穿过了 AABB（横向速度 0.8 m/s × 0.25 s = 0.2 m，
   远小于 AABB 的 4 m，所以穿过去不被任何一个采样点捕捉）

**根因**：点测不是扫掠。

### 5.3 当前解决：traj_point_test_hits

仓库在 `ci/evaluators/scenario_regression.py` 里加了**对照组**
`traj_point_test_hits()`——复刻 Frenet 的点测逻辑。这样**对比扫掠检查的
结果和点测结果**就能立刻看出「点测漏报」的占比。

规划节点本身在发布轨迹时也会做一次**扫掠检查**（`publish_trajectory` 段），
但只是诊断用——发现碰撞时打日志，不替换 Frenet 的输出。**「即使扫到了也
不拦」**是这个 bug 的另一半：扫掠检查还没接到 Frenet 的可行性过滤里。

> **「未来可能变」**：这个修复的两个方向都不确定——(a) 把扫掠接到 Frenet 可
> 行性过滤里（性能成本，每条轨迹多 ~100 次段相交）；(b) 把 Frenet 的采样点
> 加密（性能成本，每条轨迹多 ~4 倍采样点）。2026-09 的实测是当前采样率在
> sensor 编排下足够，但 dense_npc 这种场景需要更密的采样。这是一个**待决策**
> 的 P1（见 HANDOFF_2026-09-21b §17.1）。

## 六、规划节点的 37 步主循环（讲结构不讲步骤）

`planning_node.cpp` 的主循环每帧做大约 37 个步骤，按主题可以归成 7 段：

```
1. 准备 —— 工具箱
2. 决策 —— 读 behavior、设 target_speed
3. 环境 —— 障碍物列表 + 红绿灯虚拟墙
4. 几何 —— 参考线 + 投影 + 曲率
5. 曲线 —— Frenet + 变道 quintic
6. 安全 —— ST 图 + 扫掠 + 可行性复核
7. 发布 —— 64 点轨迹 + 参考线（101 点）
```

20 Hz 主频，但**输出轨迹是 10 Hz 采样**（`t_rel_us = i × 100000`）。第 17
章的安全层和第 17 章的控制节点都按 50 ms（20 Hz）假设时间轴——**这个不一致
在跨越控制/规划边界时会产生半拍延迟**。

### 6.1 轨迹拼接一致性检查

跨拍接续时检查三件事：

```
|Δt - 上一拍 dt|   < 500 ms        ← 时间间隔异常大就不接
|Δpos|             < 2.0 m          ← 位置跳变就不接
|Δv|               < 3.0 m/s        ← 速度跳变就不接
```

任一超阈值就说明控制层读到的是两条不连续的轨迹——这种情况会触发降级
（valid=0 → 走 park 兜底轨迹，1 个点 = `(ego_x, ego_y, ego_heading, v=0)`）。

### 6.2 落伍代码的标记

旧代码里 `planning_node.cpp` 还有 `frenet_bridge.cpp` 的 `kd: 0.0→1.0`、
`max_road_width_l/r: 7.0→6.0`、`d_out` 无条件覆盖、`lane_ref` 平移等等
「W1 车道内避障」相关的修复痕迹。这些都是 2026-09 那一轮 sensor 编排回归
里**先抓 bug 再补修复**的产物。读者**不要按字面读这些字段**——它们是某次
修复留下的诊断锚点，不是设计意图。

## 七、Eigen 是硬依赖

`CMakeLists.txt` 用 `if(FLOWENGINE_HAVE_EIGEN)` 包住整块 frenet_planner。
**没有 Eigen 时**只建两个**空目标**——构建「成功」但不产出任何库。`planning_node`
走降级路径：退化成恒速车道保持，并每 2.5 秒打一次警告。

「顺带一提」：`third_party/frenet-optimal-trajectory-planner/` 是同一套算法
的 **Python 参考副本**（自带 `.git/`），**不在任何 CMakeLists.txt 里**，是
死重量——只是偶尔拿来做参数调试。

## 九、破除的 v0 错误说法

- **「解一个 6×6 线性方程组」**——方向对，但漏了关键：横向是**五次**、纵向
  是**四次**，而且系数用 **Eigen 的 LU 分解**解，不是手写高斯消元。本章
  第 3.3 节明确。
- **「先粗搜一遍、再用 QP 精修」**——v0 草稿这么写，**两段都不存在**。整个
  系统**没有任何 QP 求解器**。横向是暴力网格枚举（约 2079 条候选），纵向是
  S-T 图上的动态规划。
- **「`|a| ≤ 3.0` 的 QP 约束」**——S-T DP 里的加速度上限是 `STG_A_MAX = 4.0`，
  不是 3.0。
- **「100~150 ms 的轨迹拼接」**——真实阈值是 `dt < 500 ms`、`位置差 < 2.0 m`、
  `速度差 < 3.0 m/s`，本章第 6.1 节明确。
- **「曲率平滑 / 退回笛卡尔坐标系」**——都没有。奇异点用的是**参考线回退
  路径**（`world_to_frenet` 失败时），不是笛卡尔规划。

## 十、跨章节串联

- **第 15 章**——决策层输出的 `target_lane_offset` 被规划层消费，覆盖到
  Frenet 的 `d_out` 上。
- **第 17 章**——规划层发布的 64 点轨迹（`Trajectory`）被控制层当目标值。
- **第 18 章**——安全层用同一份轨迹做 TTC / 紧急制动判定，与规划的扫掠
  检查形成第二道防线。
- **第 21 章**——行为门禁里 `eval_following_gap` 检查的是规划层追的纵向
  间距，不是行为层算的 `desired_gap`——两个量经常不一致。

> 实践（百度 Apollo 7.0 之后、autoware.universe）都改用了**分段优化的 EM
> Planner**或**学习式 planner**。但**暴力枚举的好处是确定性**——同样的输入
> 永远给出同样的输出，调试和回归测试极容易。这是工业系统里被低估的价值。
