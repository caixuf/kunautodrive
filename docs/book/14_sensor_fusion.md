# 第 14 章：定位融合与它的三种沉默

> **v2 范式章节**（2026-09 整治后保留）。本章保留低行号密度、真技术书
> 风格，参照 `docs/book/README.md` 写作风格约束与 `docs/book/08_discovery.md`
> 范式示范。v1 行号清单版本归档于 `docs/_archive/book_v1/`。

[第 13 章](13_lidar_tracking.md#卡尔曼追踪器在追什么) 回答了"**别人**在哪"。
这一章回答一个不同的问题："**我**在哪"。

这两个问题的答案如果不稳，整条链子后面全是错的。超车时你判断自己在快车道还是
慢车道，靠的是自车位置；规划器投影到参考线时靠的是自车位置；控制的航向误差更是
直接由自车位置算出。自车位置飘了，轨迹会画到隔壁车道去。

但这一章真正值得讲的不是 EKF 的公式——那个教科书里有。我要讲的是三件教科书不
会告诉你的事：

1. **这个仓库里有两套互不调用的 EKF**，它们甚至用不同的状态顺序；
2. **位置更新有三个分支，中间那个分支什么都不做**——而这个"什么都不做"是 bug 的温床；
3. **在真车配置下，定位话题可能一直是空的**，而节点看起来完全正常。

## 自车位置有两条来路

默认仿真里，仿真器 `sensor_model` 把自车坐标写成 `LidarFrame` 发出去，融合节点
把它和 GPS、位姿收进同一个滤波器。

真车模板里多了一个 `slam` 进程。注意它的 `algo` 被写成 `ekf_slam`——而这个
`ekf_slam` **不调用** `ekf_fusion.c`。两者各有自己的状态向量，连成员顺序都不一样：

| | 融合节点 | SLAM 节点 |
|---|---|---|
| 状态顺序 | `[x, y, v, heading, yaw_rate]` | `[x, y, heading, v, omega]` |
| 精度 | 双精度 | 单精度 |

融合节点只消费位姿的 x、y，不把 SLAM 算出的速度和航向写进自己的状态。

**为什么是两份而不是一份？** 我认为这是一个正确的取舍：SLAM 需要在自己的优化框架
里迭代，它的滤波器是整条 SLAM 回路的一部分，不能被外部状态约定绑架；而融合节点要对
下游所有消费者（行为决策、规划、控制）承诺一个稳定的状态定义。让两者共享一个滤波器，
等于让 SLAM 的内部表示泄漏到感知链路的接口上。

代价就是这里：两份滤波器对"车在哪"的判断可能不一致，而系统只采用了其中一份
（位姿的 x/y），把另一份的速度航向扔了。

> **作者立场**：这个设计我认为是对的，但我没有在 Apollo / autoware 里找到完全
> 对应的做法。autoware 更倾向于让 localization 独占输出，融合层只做传感器级融合。
> 这里的"两个滤波器 + 只取位置"是本仓库自己的选择。

## 传播模型：头文件在说谎

融合节点的五维状态传播，源码里只有五行：

```c
x_pred[0] = x + v * cos(psi) * dt;
x_pred[1] = y + v * sin(psi) * dt;
x_pred[2] = v;
x_pred[3] = psi + yr * dt;
x_pred[4] = yr;
```

速度不变，横摆角速度不变。这是 **CTRV**（常速、常横摆角速度）模型。

而 `ekf_fusion.h` 的 Prediction 注释写的是 bicycle kinematic model，还写着
`v' = v + a·dt`。**这两句都过时了。**

这就是为什么加速度不进状态：加速度的影响只通过过程噪声 `Q` 让速度的方差慢慢变大。
这个选择的代价是——**没有 GPS 时，你会看到车速自己漂向 0**。因为位置的雅可比里
有一项是速度的偏导，位置测量一旦进来就会顺带把速度拉过去。

如果你按头文件注释去调参，你会花很久找那个不存在的"加速度"。

> **踩坑记录**：这一章的失败故事就是这个。按注释里的 `v' = v + a·dt` 去对拍，
> 发现速度怎么都不按加速度变。查了半小时才发现注释没跟着实现更新。
> **教训**：在这个仓库里，模型的权威是 `.c` 里的那几行，不是 `.h` 里的注释。
> 涉及物理模型的地方尤其如此。

## 三个分支，中间那个不做任何事

位置更新不在滤波器内部，而在融合节点的 `run` 里。那里有一个嵌套判断，
写成了**三个分支**而不是两个：

| 分支 | 条件 | 位置来源 |
|---|---|---|
| a | 位姿存在、已收敛、且 `cov_xx + cov_yy < 100` | 位姿的 x/y |
| b | 位姿存在、已收敛、但协方差之和 ≥ 100 | **不更新**，纯预测 |
| c | 没有位姿，或 `converged` 为假 | 激光帧的 x/y |

**分支 b 是这一章最值得记住的设计。**

第一眼看上去它像 bug：位姿明明在发，为什么不用？答案是——
"我知道位置，但我不相信它"。

协方差是 SLAM 自己报告的置信度。协方差和超过阈值，意味着 SLAM 知道自己的位姿不可信。
这时候如果退回用激光帧，滤波器就在"用另一个来源"和"完全不用位置"之间二选一；
而当前的实现选择了后者——保持纯预测，让不确定性自己长出来（协方差随时间变大），
等到 SLAM 重新收敛再用。

这是一个**保守的**选择：宁可暂时漂着，也不要用一份自己知道不可信的数据去拉状态。

但它的代价是：`else` 只挂在外层。**内层那个"协方差够小"的判断没有 `else`。**
所以当位姿持续到达但协方差一直超标时，系统会落进分支 b，而**不是**分支 c。
表现是：位置只按预测积分往前走，而真实的输入被完全无视。

我把这条写进书里，是因为它真的踩过。调试时看到"x 一直往一个方向漂，但传感器明明
在报位置"，第一反应永远是"订阅断了"。不是的，是分支 b。

> **如果你要改这里的语义**：把分支 b 改成"退回激光帧"是合理的，但要先确认
> 激光帧在真车配置下真的有数据（下面第六节会说：在真车模板里它没有）。

## 一致性检查：把统计上的和工程上的分开

融合节点用 `sizeof` 验收收到的消息。这里有一个隐蔽的不匹配：

| 类型 | 结构体大小 | 打包长度 |
|---|---|---|
| `Pose2D` | 32 | 29 |
| `GpsData` | 40 | 36 |
| `LidarFrame` | 24 | 24 |

`Pose2D` 打包时按字段紧排，`bool converged` 后面有填充，所以打包比结构体短 3 字节。

而消息总线上 `type_id` 是 0（发布时被打上），下游只能靠尺寸判断。
`LidarFrame` 恰好两边相等，所以仿真路径没暴露问题；`Pose2D` 和 `GpsData` 则可能
被尺寸检查拒掉。

这不是一个"设计决策"，这是一个**遗留的紧耦合**。正确的做法是让验收同时接受打包
长度，或者让总线保留真实的类型号。但改这个会牵动整条发布链，超出本章范围。

> **本章不动源码**。这一节记录的是问题，不是修复。真车上的影响见下一节。

## 真车配置下，这句话可能不成立

把上面所有东西拼起来，真车模板（`config/pipeline_car.json`）上会发生什么？

我按源码追了一遍，结论是：**`fusion/localization` 不会发出来。**

原因是三件事叠在一起：

1. 真车的激光雷达驱动发的是 `perception/obstacles` 上的障碍物列表，
   而且这个输出在配置里默认是关的。没有任何进程往 `sensor/lidar` 发 `LidarFrame`。
2. 融合节点的任务在 `LidarFrame` 缓冲为空时直接 `continue`——整个循环体不执行。
3. 配置里 fusion 进程只订阅了 GPS 和位姿，没有订阅激光，但**代码里仍然订阅了
   `sensor/lidar`**。

第 3 点是这个问题的伪装层：如果你看配置文件，会觉得"既然没订激光，节点就用 GPS 和
位姿呗"。但实际上节点订了，只是这条 topic 永远没有数据，于是它一直在等一个
不会来的消息。

再加上上一节的 `Pose2D` 尺寸问题——即便有人补了一路正确的 `LidarFrame`，
`slam_node` 发出的 29 字节位姿也过不了尺寸检查。

> **作者立场**：这一条我倾向于认为是**真 bug**，不是刻意的严格设计。
> 一个从不发数据、也不报错的定位节点，比一个发错误数据的更危险——因为下游会
> 一直等。而"等一个不来的人"这个模式，在配置层是完全看不出来的。
>
> 我在书里保留它，是因为这类问题只有把整条配置跟代码对着看才能发现，
> 而这类"沉默的失败"正是自动驾驶里最贵的错误形态。

## 故障清单：什么会静悄悄地错

下面这些是本章用故障注入跑出来的真实行为，都是"不报错、但结果不对"的类型。

**没有 GPS 时车速掉到 0。** 只有位置测量时，速度会从初值 5 附近一路滑到 0。
原因是位置的雅可比把速度耦合进来了。要稳定的速度必须有 GPS 的速度测量。

**旧帧把车速拽起来。** 激光雷达停了但位姿还在发时，位置查找会因为超过 100 ms
的配对窗口而失败，落进分支 c，把缓冲里那帧**旧的**激光帧再喂一次。
车辆会朝一个老坐标猛冲，速度飙到 28 m/s。根因是缓冲的"取最新"不检查过期。

**航向从 179° 到 -179°。** GPS 航向残差用 `while` 循环折到 ±π，不是 `atan2`。
结果是对的（走 2° 短弧而不是 -358° 长弧），但状态航向在这次更新里不会折回
±180° 以内——要到下次预测末尾才折。

**收敛失败不会立刻停。** 卡方门限要连续 11 次失败才置位发散标志。
而且门限只在成功更新 100 次之后才生效——前 100 次里再离谱的离群点也会被接受。
这是"先让它收敛"的合理妥协，但意味着**开机头几秒定位是完全没有防护的**。

**分歧后重置会丢掉计数。** 发散后每 10 帧用当前位置做种子重置滤波器。
重置清了失败计数，但没清门限计数——两个计数器会再次不同步。

## 性能：单次调用是微秒级，周期是消息决定的

一次预测约 190 纳秒，一次位置更新约 200 纳秒。这是单次函数调用，不是定位周期。

定位周期由**输入消息唤醒节点的频率**决定，而不是配置里的 `frequency_hz`。
实测：激光 20 Hz + 位姿 20 Hz 时，输出约 40 Hz（两路各唤醒一次）；
激光 20 Hz + GPS 10 Hz 时，输出约 30 Hz。

这里藏着一个容易踩的坑：滤波器内部的 `dt` 是**固定的 0.05 秒**，
不管两次唤醒之间真实过了多久。这意味着如果系统负载高、实际周期变成 0.1 秒，
状态积分的位移只有真实位移的一半——**滤波器会系统性地低估速度**。

> **这一条我没改**。改成用真实墙钟差值会让仿真和真车的行为不一致（仿真里
> 时钟是步进的、可以快进，真实间隔没有意义）。这是个明确的取舍：牺牲
> 真实间隔的正确性，换取仿真可重放。读到这里你应该能自己判断这个取舍对不对。

## 跑一下

`examples/ekf_chapter/` 有配套的示例程序，目标名 `ekf_chapter`：

```bash
cmake -S . -B build -DFLOW_BUILD_BOOK_EXAMPLES=ON
cmake --build build --target ekf_chapter -j
./build/bin/ekf_chapter demo          # 走一条合成圆弧
./build/bin/ekf_chapter bench         # 计时
./build/bin/ekf_chapter fault-off all # 离线的故障注入
```

`demo` 用 CTRV 走一条 8 m/s、横摆角速度 0.2 rad/s 的圆弧，40 步，每步把真值
送回去当测量。跑完你会看到融合的轨迹和真值完全重合——但那只是因为每步都给了
完美测量，不代表真实定位精度。**别把这个当成"定位很准"的证据。**

`fault-off all` 更值得跑。它会重现上面故障清单里的每一条，包括那个"发散标志
在 100 次更新后才生效"的窗口。

> 可运行示例默认不编（`FLOW_BUILD_BOOK_EXAMPLES` 关闭），所以它不进日常构建，
> 也不会在 CI 里被跑到。你得自己打开。

## 小结

这一章的核心不是 EKF。EKF 在任何一本控制理论书里都讲得比这里好。

值得记住的是三件事：

1. **两个互不调用的滤波器**，只取位姿的位置，丢掉它的速度航向；
2. **三个分支，中间那个故意什么都不做**——因为协方差超标时不信任任何位置来源，
   包括激光帧。读这段代码时千万别把嵌套的 if 收成一句"否则用激光"；
3. **沉默的失败比错误的输出更贵**。真车配置下定位节点不报错也不出数，
   这种问题看配置文件永远看不出来。

下一章的行为决策会直接消费这里输出的 x、y、v、heading。默认仿真里这份数
经常被真值盖住，真车路径上盖不住。所以读下一章之前，先确认你跑在哪个分支上。
