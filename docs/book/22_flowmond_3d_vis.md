# 第 22 章：在浏览器里看清这辆车

> **v2 范式章节**（2026-09 整治后保留）。本章保留低行号密度、真技术书
> 风格，参照 `docs/book/README.md` 写作风格约束与 `docs/book/08_discovery.md`
> 范式示范。v1 行号清单版本归档于 `docs/_archive/book_v1/`。

车在跑，可它到底跑得对不对？光盯着一堆日志很难判断：感知的点云是不是对齐了，规划出来的轨迹是不是太抖，控制有没有超调。这套系统配了一个轻量的 Web 可观测性套件 FlowBoard，底层用 C++ 写的监控守护进程 `flowmond` 采集拓扑和全总线遥测，中间经 `dashboard_bridge` 共享内存通道把结构化数据送出去，前端用 Three.js 渲染 3D 数字孪生，并靠前端航位推算（Dead Reckoning）插值把画面补顺。

## 前端 3D 场景是一组可插拔的 View

FlowBoard 的前端 3D 场景拆成了高内聚、松耦合的 View 模块（`tools/flowboard/js/views/`），每个 View 只管一件事：

| 视图模块 | 职责与渲染要素 | 关键技术 |
| :--- | :--- | :--- |
| **RoadView** | 道路路面、车道标线（白实线/虚线/黄线）、停止线 | 基于参考线法向扩展的三角面网格（Ribbon Mesh） |
| **EgoVehicleView** | 自车 3D 实体模型、车轮转动、刹车灯/转向灯状态 | GLTF 模型加载与动态材质贴图控制 |
| **ObstacleView** | 3D 边界框（Bounding Box）、速度矢量箭头、分类标签 | InstancedMesh 批量实例化渲染（百万级点云性能） |
| **TrajectoryView** | 规划期望轨迹线、历史行驶轨迹面包屑 | 动态 Catmull-Rom 曲线着色器 |
| **SafetyCorridorView** | 安全走廊包络、TTC 危险碰撞红色预警面 | 半透明动态多边形混合渲染 |

## 位姿更新太慢，画面就会抖

浏览器的渲染刷新率通常是 $60\text{ Hz}$ 或 $144\text{ Hz}$，而后端经 WebSocket 推位姿只有 $20\text{ Hz} \sim 50\text{ Hz}$。要是前端收到一帧才更新一次位置，画面就会明显一卡一抽（Jitter）。

FlowBoard 在 `tools/flowboard/js/app.js` 里做了一层前端航位推算插值：

```javascript
// 基于前向运动学的微秒级平滑插值
function updateEgoSmoothPose(deltaTimeSeconds) {
    if (!lastServerState) return;

    // 1. 沿当前航向推进局部位置
    const v = lastServerState.speed; // m/s
    const yaw = lastServerState.heading; // rad
    
    // 2. 局部积分推算
    predictedPose.x += v * Math.cos(yaw) * deltaTimeSeconds;
    predictedPose.y += v * Math.sin(yaw) * deltaTimeSeconds;
    
    // 3. 收到真实服务端帧时进行低通滤波软对齐 (LERP)
    predictedPose.x = THREE.MathUtils.lerp(predictedPose.x, serverPose.x, 0.3);
    predictedPose.y = THREE.MathUtils.lerp(predictedPose.y, serverPose.y, 0.3);
    predictedPose.yaw = THREE.MathUtils.lerp(predictedPose.yaw, serverPose.yaw, 0.3);

    // 4. 更新 Three.js 摄像机与自车模型 Transform
    egoMesh.position.set(predictedPose.x, predictedPose.y, 0);
    egoMesh.rotation.z = predictedPose.yaw;
}
```

## 3D 画面之外的那块内省面板

除了 3D 场景，FlowBoard 还挂了一块实时的系统内省面板：能看到 CPU、内存和线程亲和度；能看 Topic 拓扑连线图，实时显示发布者和订阅者的连接状态；还有一张延迟分布热力图，摊出每个算法节点耗时的 $P_{50}, P_{90}, P_{99}$。

## 前端崩过两次，都是显存惹的祸

第一次是页面开着开着就卡死。跑到 30 分钟左右，内存占用冲破 4GB，浏览器直接崩溃。翻代码发现，每帧都在动态生成新的轨迹曲线 `BufferGeometry`，却从没调用旧对象的 `geometry.dispose()` 和 `material.dispose()`，显存就这么被撑爆了。真正的改法是预分配一段定长顶点缓冲区，每帧只调 `positionAttribute.setXYZ()`，再把标记 `needsUpdate = true` 就行。

第二次跟显存无关，是依赖来源的问题。工业现场和车载局域网通常连不上外网，所以前端代码不能从公网 CDN 动态拉 `three.js`、`fonts` 或外部材质图片。所有依赖都得打包进 `tools/flowboard/vendor/` 这个本地目录，否则断网环境直接白屏。

## 零拷贝这三个字，代价是什么

上面那张图里写着"零拷贝聚合 Topic 统计"。这句话在实现层面是准确的——
算法进程把统计结果写进共享内存段，`flowmond` 直接读，不经过内核网络栈，
不做序列化，也不做内存拷贝。

但零拷贝不是免费的。这个选择意味着**两端必须对内存布局达成完全一致的共识**：
字段偏移、结构体大小、对齐要求，任何一边改了结构体，另一边读到的就是垃圾数据，
而且不会报错——它会读出一个"看起来合理但完全错误"的数字。

这个失败模式比崩溃难查得多。所以维护共享内存布局的规矩是：**只允许追加字段，
不允许改已有字段的顺序或类型**。追加是安全的（老读者只看前 N 个字节），改布局不是。

> 这也是第 14 章里 `sizeof(Pose2D)` 和打包长度不一致的那类问题的同一个根源：
> **布局一旦被多方共享，它就不能再随便改了**。区别只在于共享的双方是进程还是消息。

## 为什么要拆成可插拔的 View

FlowBoard 的 3D 场景不是一个巨大的 `app.js`，而是拆成若干个只管一件事的 View 模块。
RoadView 只画路，EgoVehicleView 只画自车，ObstacleView 只画障碍物。

拆开的理由不是"整洁"，是**崩溃隔离**。第 22 章开头那个显存泄漏事故，
如果场景是一个整体函数，泄漏点和渲染逻辑缠在一起，定位成本会高一个数量级。
拆成独立 View 之后，出问题只需要怀疑一个模块。

代价是多了一层调度：主循环要按固定顺序调用每个 View 的更新方法，并且保证
自车位姿在所有 View 之前算好（其他 View 都要用这个变换）。这个顺序约定是隐式的，
读代码时要注意——**新增 View 的人必须知道自己的 `update` 依赖什么**。

> **这一层没有文档**。如果你要加一个 View，得自己读现有几个的调用顺序来推断约定。
> 我倾向于把依赖显式写出来，但这超出了本章范围。

## 60 Hz 渲染，20 Hz 的数据

浏览器渲染通常是 60 Hz 甚至 144 Hz，而后端经 WebSocket 推来的位姿只有 20~50 Hz。
如果前端"收到一帧才更新一次位置"，画面就会明显地一卡一抽。

解法是**前端航位推算**：本地按上一帧的速度和航向，把位姿沿当前运动学往前积分，
收到真实帧时再用低通滤波对齐。这本质上是在**客户端重建一个最小的运动模型**，
把离散的状态更新变成连续的位置输出。

这里有个明确的取舍：插值让画面顺滑，但它**掩盖了数据不更新的事实**。
如果后端真的卡死了，画面依然会流畅地"往前跑"——因为插值只依赖上一帧的
速度和航向，不需要新数据。所以你在 3D 视图里看到的"车在动"，**不能证明数据链是通的**。

要判断数据链是否正常，要看内省面板里的 FPS 和延迟分布，不要看 3D 画面的平滑度。

再补一个具体判据：**看数据的"年龄"**。如果最新一帧的时间戳距离现在超过一个
周期（比如 50 Hz 推送却只有 10 Hz 更新），画面依然流畅，但那是 5 帧前的车在插值。
这个数字比 FPS 更能说明问题——FPS 掉说明系统慢，数据年龄涨说明链路断了。

> **作者立场**：我保留这个判断。"界面看起来是好的"和"系统确实是好的"之间，
> 插值、多线程、缓存这些技术每一种都在拉大这道缝。仪表盘的首要职责应该是
> **告诉你哪里坏了**，其次才是好看。

| 故障类型 | 是否响亮 | 排查手段 |
|---|---|---|
| 崩溃 / 断开 | 响亮 | 断线重连、退避 |
| 卡住 / 数据陈旧 | 沉默 | 查数据年龄与锁等待 |

## 崩溃和卡死，是两类问题

WebSocket 这条路上有两种典型的故障，它们的排查方式完全不同。

**断开。** 守护进程挂掉或网络断了，浏览器会触发 `onclose`。这是**响亮**的故障——
页面会停住，或者明确报错。处理也简单：重连、退避、甚至提示用户。

**卡住。** 守护进程还活着，WebSocket 连接也还开着，但数据不再流动。
这是**沉默**的故障——页面继续渲染，因为插值还在跑，只是数据越老，画面越飘。
如果你不盯着 FPS 面板，可能几分钟都发现不了。

**为什么会有卡住**：守护进程侧的拓扑导出是周期性的，某一轮导出如果阻塞在
某个锁上或者某个慢查询上，这一轮的更新就丢了。连接没断，任务还在跑，
只是这一拍没跟上。**这种故障不会自己恢复**，因为触发它的原因（那个锁）还在。

所以"重连"这个手段对卡住无效。你需要的不是重连机制，是**超时检测**：
如果超过 N 毫秒没收到新数据，前端应该主动显示"数据陈旧"，而不是继续插值。

> 这和第 14 章那个"定位话题永远是空的"是同一类问题的两个面：
> **连接状态不等于数据状态**。你得看有没有数据在看，而不是看连接在不在。

## 评估器不看画面

一个容易误解的点：第 23 章的场景回归**不使用这套 3D 可视化**。

评估器采样的是拓扑 JSON——节点状态、话题频率、连接关系。它不需要知道车
在画面里长什么样，也不需要渲染任何东西。这意味着：

- 评估可以在**没有显示设备**的 CI 机器上跑（大多数 CI 就是）
- 评估结果不受前端 bug 影响（CDN 挂了、显存泄漏了，评估照跑）
- 3D 视图崩溃**不会**被回归测试发现

最后一条是双向的：视图不能污染评估，但**视图自己的回归完全缺失**。
那个显存泄漏 bug 从来没有被任何测试抓到过，它是在"页面开着开着卡死了"
这种人工观察里发现的。

> **我倾向于给前端也加一道冒烟测试**——不需要验证渲染正确性，
> 只需要验证"能加载、不抛异常、控制台无错误、内存不持续增长"。
> 这类测试很便宜，能挡住本章开头那类事故。

## 这一章没讲什么

没讲 WebSocket 的协议格式、没讲 `flowmond` 怎么采集拓扑、没讲 Three.js 的

也没讲一个更根本的问题：**这套可视化在真车上怎么用**。车内没有浏览器，

不在本章范围内。
