# 第 10 章：用 C++20 协程拆掉回调地狱

> **v2 范式章节**（2026-09 整治后保留）。本章保留低行号密度、真技术书
> 风格，参照 `docs/book/README.md` 写作风格约束与 `docs/book/08_discovery.md`
> 范式示范。v1 行号清单版本归档于 `docs/_archive/book_v1/`。

写自动驾驶节点，最难忍的不是算法，是等待。一个融合节点要同时等点云、等 GPS、等定位服务的应答，每一路等待还得各自配一个超时看门狗。在传统的异步 C 写法里，这一整段业务会被拆成几十个回调函数，状态散落在全局变量之间，同步和停机的清理顺序稍微写错，就是死锁或者内存泄漏。

KunAutoDrive 的 FlowCoro 换了个做法：把 `MessageBus` 的 Pub/Sub、Req/Reply、Timer 和多路 Select 都包成标准 awaitable 原语，于是等待可以写成从上往下读的直序代码——看上去是同步的，跑起来不占任何线程。

## 同一段等待，两种写法

先看左边那种写法的后果，再看右边这种写法为什么能读得下去。

```
传统回调驱动 (切碎的逻辑与散落的状态):
┌──────────────────────────────────────────────────────────┐
│  void on_lidar(const Message* m, void* ctx) {            │
│      ctx->got_lidar = true;                              │
│      if (ctx->got_gps) trigger_fusion(ctx);              │
│  }                                                       │
│  void on_gps(const Message* m, void* ctx) {              │
│      ctx->got_gps = true;                                │
│      if (ctx->got_lidar) trigger_fusion(ctx);            │
│  }                                                       │
│  缺陷：超时看门狗、异常重试、优雅停机代码极度晦涩冗长。  │
└──────────────────────────────────────────────────────────┘

FlowCoro C++20 协程驱动 (直序、清晰、确定性):
┌──────────────────────────────────────────────────────────────┐
│  Task run() override {                                       │
│      while (!should_stop()) {                                │
│          // 50ms 超时等待点云，超时自动触发看门狗            │
│        auto r = co_await next_for("sensor/lidar", 50000);    │
│        if (r.timed_out()) { watchdog_alert(); continue; }    │
│          auto pose = co_await ask("service/locate", req);    │
│          publish("fusion/result", compute(*r, pose));        │
│      }                                                       │
│  }                                                           │
│  优势：代码自上而下直叙；挂起时不占 CPU 线程；无锁优雅停机。 │
└──────────────────────────────────────────────────────────────┘
```

## 无栈协程在编译器眼里是什么

C++20 协程是无栈协程。编译器在编译期把含 `co_await` 的函数改造成两样东西：一个堆上分配的协程状态帧（coroutine frame），和一个内部有限状态机。所谓挂起，并不是把函数卡在那里，而是把现场写进状态帧，然后返回。

```
FlowCoro 执行模型:
┌─────────────────────────────────────────────────────────────┐
│  RtExecutor (每个 Worker 线程独占一个确定性执行器)          │
│                                                             │
│  ┌───────────────┐     spawn()     ┌──────────────────────┐ │
│  │ 准备队列       │ ──────────────►│ 正在执行的 Coroutine │ │
│  │ (Ready Queue) │                 │ (执行至 co_await)    │ │
│  └───────▲───────┘                 └──────────┬───────────┘ │
│          │                                    │             │
│         │ post_ready() 唤醒                  │ await_suspend│
│          │                                    ▼             │
│  ┌───────┴────────────────────────────────────────────────┐ │
│  │             MessageBus / Timer 挂起等待监听器          │ │
│  └────────────────────────────────────────────────────────┘ │
└─────────────────────────────────────────────────────────────┘
```

### 执行器怎么跟着协程走

为了让多线程下的调度结果是确定的，每个 Worker 线程都维护一个自己的 `g_node_exec` 线程局部变量：协程执行到 `await_suspend(handle)` 的那一刻，从当前线程的 TLS 里读出 `RtExecutor*`，记在 awaitable 内部。之后外部总线分发线程收到消息、要唤醒这个协程时，走的不是 resume，而是调用当初记下的 `exec_->post_ready(handle)`，把协程投递回它自己的执行器线程。跨线程直接 resume 引发的那类竞态，就这样被挡在了门外。

## 可以 co_await 的五样东西

这张表是 FlowCoro 针对通信场景定的原语，日常代码里出现的基本就这几个：

| 原语 | 功能语义 | 典型应用场景 |
| :--- | :--- | :--- |
| `co_await next(topic)` | 阻塞挂起直到该 Topic 收到下一帧消息 | 传感器数据周期订阅 |
| `co_await next_for(topic, timeout_us)` | 带微秒超时的消息挂起 | 传感器丢帧看门狗防死锁 |
| `co_await select({t1, t2, ...})` | 多路话题竞争挂起，首个到达者唤醒 | 激光雷达与毫米波雷达首帧触发 |
| `co_await ask(service, req)` | 异步 RPC 请求挂起直到收到响应 | 路径规划向高精地图查询车道 |
| `co_await sleep_us(duration_us)` | 协程定时休眠（不阻塞系统底层线程） | 控制循环高频降采样定频 |

## 写一个带超时和多路选择的融合节点

把原语拼起来，一个节点的主循环就这么长。这段代码里同时用到了 `select`（点云和毫米波雷达谁先到先处理谁）、`ask_for`（20ms 超时的 RPC 查询）和 `sleep_us`（定频 100Hz）：

```cpp
/* modules/adas_nodes/coro_fusion_node.cpp */

#include "coroutine_task.h"
#include "logger.h"

class CoroFusionNode : public CoroutineTask {
public:
    CoroFusionNode(const TaskConfig* cfg) : CoroutineTask(cfg) {}

protected:
    Task run() override {
        LOG_INFO("CoroFusion", "协程任务已启动，进入主事件流循环...");

        while (!should_stop()) {
            // 1. 等待点云或雷达数据到达（谁先到处理谁）
            auto sel = co_await select({ "sensor/lidar", "sensor/radar" });
            if (sel.cancelled()) break;

            if (sel.matched("sensor/lidar")) {
                LOG_INFO("CoroFusion", "收到激光点云, 序号: %u", sel.message.msg_id);
            } else if (sel.matched("sensor/radar")) {
                LOG_INFO("CoroFusion", "收到毫米波雷达, 序号: %u", sel.message.msg_id);
            }

            // 2. 向定位服务发起 RPC 查询当前全局位姿
            Message req;
            auto rpc_res = co_await ask_for("service/localization", "coro_fusion", &req, sizeof(req), 20000 /* 20ms 超时 */);
            if (rpc_res.timed_out()) {
                LOG_WARN("CoroFusion", "定位服务超时，降级为航位推算");
            } else {
                LOG_INFO("CoroFusion", "融合定位成功对齐");
            }

            // 3. 定频休眠 10ms (100Hz)
            co_await sleep_us(10000);
        }

        LOG_INFO("CoroFusion", "协程任务安全退出");
    }
};

EXPORT_COROUTINE_TASK(CoroFusionNode, coro_fusion_node)
```

## 挂起的协程，怎么保证只被唤醒一次

协程挂在那里等消息的时候，宿主进程可能恰好下发了 `stop()`。消息到达、超时定时器触发、停机信号，这三件事是可能同时发生的，而它们之中只能有一个真正生效。

`coroutine_task.h` 里的 `AwaitCtl` 就是管这件事的：一个基于 CAS（Compare-And-Swap）的原子恢复守卫。三路唤醒源要竞争同一个恢复权，CAS 保证同一个挂起句柄 `std::coroutine_handle<>` 在它的生命周期里有且仅被 resume 一次。少了这道守卫，两次恢复撞在一起就是段错误。

## 协程里翻过的三次车

### 挂起点前面留了个裸引用

现象很干脆：节点跑上几分钟，进程毫无征兆地 SIGSEGV，可一旦放慢复现节奏又什么都看不出来。最后是在代码里找到了这一段：

- 当时的写法：
  ```cpp
  // 错误代码:
  auto& ref = get_local_struct();
  co_await next("sensor/lidar");
  process(ref); // 灾难！挂起后局部栈帧可能已失效或被重新分配
  ```

问题出在 `ref`：它指向一个局部结构体，`co_await` 挂起之后那个栈帧可能已经失效或者被重新分配，再拿 `ref` 用，读到的就是垃圾内存。改法很简单也很死板：所有要跨越挂起点的持久变量，要么存成类的成员变量，要么按值拷贝一份。

### 在总线回调线程里直接 resume

`resume()` 会在当前调用者线程上立即同步执行协程后续代码。如果这条路径是总线工作线程走的，一个重型算法就能把整条总线堵在那里——现象是所有节点的消息延迟一起抬高，而不是某一个节点变慢。

改法是把任务交还给协程自己的 Worker 线程：调 `exec_->post_ready(handle)`，而不是 `handle.resume()`。这也是上面那句「记下自己所属的执行器」真正的用处。

### 同一个句柄被 resume 两次

前面说过 `AwaitCtl` 的 CAS 守卫，这里说它还没写出来之前的样子：进程偶尔崩在 resume 的调用点上，core dump 里两个线程的栈都停在同一个 `coroutine_handle` 上——消息到了、超时也到了，两边都认为自己该唤醒这个协程。修法就是给恢复权加一把原子锁，让三路唤醒源去竞争，输的那两路直接放弃。

## 六、为什么是协程，而不是回调或线程

前五节讲的是「协程怎么写」。这一节回头回答「为什么值得」。我把三条路都摆出来，
包括它们各自在什么地方是对的：

```
       回调驱动            线程/线程池           协程（FlowCoro 选的）
  ┌────────────────┐   ┌────────────────┐   ┌────────────────────┐
  │ 状态散在结构体  │   │ 状态天然隔离    │   │ 状态天然隔离        │
  │ 里，取消最难写  │   │ 但每次等待换一次│   │ 每次等待只换一次栈帧│
  │                │   │ 上下文（贵）    │   │ （几十 ns）          │
  │ 上下文切换     │   │                │   │                     │
  │ 几乎免费        │   │ 上下文切换     │   │ 上下文切换          │
  │                │   │ 上百 µs         │   │ 几乎免费            │
  │ 一个融合节点    │   │ 一个融合节点    │   │ 一个融合节点         │
  │ 20 个回调       │   │ 20 次线程切换   │   │ 20 次 co_await      │
  └────────────────┘   └────────────────┘   └────────────────────┘
   停机顺序易错          核数是硬上限            挂起点数无上限
```

**回调的真实成本是可读性，不是性能。** 一个节点要同时等三路输入、每路带独立超时、
外加一个周期定时器，回调写法里这些等待会互相嵌套。每加一路输入，所有已有回调的
控制流都要改一遍——这是 O(n²) 的复杂度，而且是那种编译器和 code review 都抓不到的复杂度。

**线程的真实成本是上下文切换和核数。** 挂起一个等待中的线程，等价于保存一整个栈
（几十 KB 加上寄存器上下文），恢复时再搬回来。自动驾驶一个节点 20 路等待、20 路等待
每秒各触发一次，就是每秒 400 次切换——每次上百微秒量级的开销。这个开销换来的好处
是「每个任务有独立的失败域」，而这一点协程同样有（每个协程有独立的状态帧）。

**协程同时拿到了两个好处**：等待点的切换成本接近于零（只搬状态帧），失败域依然是每
任务一份。这就是「同时拥有线程的隔离性和回调的轻量」。

> **另一个选择：async/await + 事件循环。** 我不确定它在 C++ 里能不能给出一个更好的
> 答案。std::async 底层还是线程池，libuv 那类库又要求把回调包成 promise。在 C++20
> 协程之前，「等待」这件事在 C++ 里没有一个既轻又原生的表达。作者立场上，我认为
> 协程是 C++20 之前最诚实的答案——它没有假装能取消，只是把取消这件事显式化了
> （见第八节）。

## 七、BusQueueBridge：把订阅从「每帧一次」提到「节点一生一次」

这一节讲一个我认为是全仓库最有价值的一次重构，因为它的驱动力不是性能，是**一类
真实的、沉默的挂起事故**。

### 事故长什么样

`when_any_bus_for` / `select_for` 这两个原语是「每次 co_await 订阅一次、醒来退订一次」。
代码本身是对的，`AwaitCtl` 的 CAS 守卫也做了。但订阅的注册和注销之间存在一个窗口：
如果在这个窗口里，总线既没有把消息交给这个订阅、又没有把超时判给这个 awaitable，
那么两个唤醒源都失效，协程就**永久挂起**。

```
  协程视角                          总线视角
  ─────────────────────────────────────────────────
  co_await select_for({a,b}, 20ms)
    ├─ 订阅 a                      ──►  投递 a 的消息……
    ├─ 注册 20ms 超时定时器           （窗口开始：订阅已在，awaitable 还没排上 waiter）
    │                                 （消息被丢弃——此刻没有 waiter 认领它）
    └─ 挂起                              （窗口结束：等待者登记完毕，但消息已经丢了）
         ⋮
       20ms 后定时器到期 → 唤醒              ✓ 超时这条路是好的
         ⋮
    下一帧 co_await → 又一个窗口
```

实测的现象是：节点启动后 1~3 秒内永久挂起，下游 topic 断流，同一个适配器在仿真器上
也复现。**最贵的地方在于它不报错**——协程对象还活着，节点线程还在，只是永远不再发数据。

### 修法：把订阅的生命周期提到协程之外

`BusQueueBridge` 的做法是把「订阅」和「等待」拆成两件事：

```
  订阅（构造时一次，整个 run() 期间不变）
  ├──────────────────────────────────────────┐
  │  BusQueueBridge bridge(bus, {"a","b"});   │  ← 在 while 循环【之外】
  │  for each topic: subscribe(→ 覆盖槽)      │
  └──────────────────────────────────────────┘
                      ↓
  等待（每帧一次，但不再碰订阅表）
  ┌──────────────────────────────────────────┐
  │  co_await bridge.recv_any_for(20ms)       │  ← 每帧只做「看槽 + 挂起」
  │    有槽 → 立刻返回，不经过定时器            │
  │    没槽 → 挂起，等 on_message 或超时        │
  └──────────────────────────────────────────┘
```

这样做的收益有三层，按重要性排：

1. **竞争窗口消失了。** `on_message` 只做一件事——把消息拷进槽里、把 `has` 置 true。
   消息随时到达都不会丢，因为它不需要「有 waiter 才接收」。这一条是根治。
2. **每帧不再付订阅/退订的代价。** 总线的订阅表要加锁、可能要分配。用桥之后，一拍只
   持有一次互斥锁做槽位拷贝。原来的写法在 1 kHz 以上的发布频率下是笔实打实的开销，
   但那是次要理由。
3. **背压语义变得明确。** 槽的深度是 1，新消息直接覆盖旧消息（drop_oldest）。控制
   回路要的是「最新状态」，不是「每一帧都不能丢」。这一点和 `control/cmd` 这类 topic
   的 QoS 配置是对齐的。

### 自愈：一个比"根治"更贵的补丁

代码里还留了一个 `reconnect()`，用来处理另一类更难缠的竞争：启动早期多节点并发订阅时，
桥的回调可能**永久停滞**——同一个节点跑 45 秒正常、60 秒正常，120 秒的 run 里启动即断，
回调计数停在 5 再也不涨。这类问题的根因在总线订阅的并发窗口里，短期修不掉。

于是 `reconnect()` 做的事就是：退订、重订、计数清零。**这不优雅，但它把"永久断流"
降级成了"短暂停滞"。** 现在的生产代码里，这个自愈被严格加了三个约束才敢用：

- **只在回调计数真的没增长时才重连**（不是每 N 拍无条件重连）；
- **10 秒防抖**；
- **重连后重置一次控制数据的时间戳**，给新订阅一个宽限期。

> **踩坑记录**：早先版本是「每 600 拍无条件 reconnect」。事故链是这样的：
> 重连把回调计数清零 → 重连窗口内消息丢失 → 安全状态机立刻触发 → 车速恒为 0 →
> 下一轮检查计数仍然异常 → 再次重连……无限循环，**重连本身成了断流的制造者**。
> 教训很朴素：**自愈机制必须先证明"病还在"，否则它就是致病源。**

> **作者立场**：这一节揭示的是一类无法靠文档根治的问题。回调丢失、订阅停滞、并发
> 窗口——这些在纯逻辑推理里都是「不可能发生」，只有跑够多的 run 才能碰到。我倾向于
> 认为 FlowCoro 里剩下的 awaitable（RPC、延迟等待）**也都应该往"常驻 + 槽"的方向改**，
> 而不是等到再出一次事故再说。这条路走下去，最终形态大概是：所有 awaitable 都只做
> 「登记 → 挂起 → 等唤醒」，订阅一次都不做。

## 八、取消为什么必须显式：它不是「不要了」，是「下一次醒来就不做了」

协程取消是这门语言里最容易写出 bug 的地方，因为**协程不会自己停下来**。

### 为什么不能靠"不唤醒"来取消

一个挂起的协程，如果取消后不再被任何东西唤醒，它就永远不执行到循环体的 `while (!stop)`
检查——**这个检查写在挂起点之后，而挂起点永远过不去**。看起来"停住了"，实际上它
还挂在内存里，还占着订阅，还占着状态帧。

所以 C++20 协程的取消必须是**协作式 + 可达**的：

```
  ❌ 期望的取消语义                  ✅ 实际的取消语义
  ──────────────────                ──────────────────
  cancel()                          should_stop() = true
      ↓                                 ↓
  协程立刻消失                     唤醒（或超时）→ 协程在下一个循环头读到标志 → 主动退出
      ↓                                 ↓
  （做不到：挂起点无法越过）       主循环退出 → 栈帧销毁 → 订阅随桥析构释放
```

这就是为什么 `run()` 里的循环条件必须是 `while (!should_stop())`，
**而且每次挂起都要带一个有限超时**。控制节点里那行 50 毫秒的超时就同时是看门狗和
取消检查点——没有它，协程在停机时最多要等到永远。

`AwaitResult` 里那个 `Cancelled` 状态就是为这条路径准备的：被显式取消的 await 返回它，
调用方按 `cancelled()` 分支退出。`co_await` 的返回值因此**必须检查**——忽略它就等于
放弃了取消语义。

### 关停还有第二道坎

即使循环退出了，还有一个坑：`RtExecutor::shutdown()` 内部是
「反复 run() 直到所有协程结束」的死循环。如果还有协程帧挂在一个**永远不会触发的外部
生产源**上（定时器服务、延迟 awaitable），这里就**活锁**——不崩溃，就是永远转下去。

所以宿主代码的固定套路是三步：先 `node_pump` 看到停止标志退出，再用一个**有预算的**
drain 循环（2 秒）尝试让剩下的帧自然结束，然后直接 `~RtExecutor` 销毁剩下的帧。drain
用 `rt::sleep_for` 而不是 `run()`，是为了让 `request_stop` 能在循环中被观测到。

> **作者立场**：我认为这是本章里最值得记住的一句话——**在无栈协程里，取消是一个
> "需要被安排执行的"动作，而不是一个"可以发生在任意时刻"的事件。** 大部分协程框架
> 的文档把取消包装成后者，用起来很爽，但心智模型是错的，出了 bug 你会怀疑人生。
> 显式一点，慢一点，但能推理。
