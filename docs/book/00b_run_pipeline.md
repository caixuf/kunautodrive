> 范式示范。

后面每一章都有一堆"跑一下看看"的建议。在读它们之前，你得先有一个真的在跑的系统——
不然那些建议全是空话。这一章不讲设计，只做一件事：**把仓库编出来、跑起来，
并且看懂启动时那份进程表到底在说什么**。

看懂进程表比看懂任何一章都重要。后面第 05 章讲消息总线、第 11 章讲调度器，
它们讲的都是这张表里那些格子在运行时怎么互相牵制。

## 先编出来

仓库用 CMake Preset 管理构建配置，不要手写编译参数：

```bash
bash build.sh              # 包装脚本，内部走 cmake --preset
```

`build.sh` 只是把 `CMakePresets.json` 里的 preset 展开成实际的 cmake 调用。直接
用 preset 也一样：

```bash
cmake --preset dev
cmake --build build/dev -j
```

如果你改了编译器选项、asan/tsan 之类的开关，去改 `CMakePresets.json`，不要在命令行
上临时追加——那些追加出来的选项下次就没了，而且会和 CI 的配置漂移。仓库里另外
准备了 `build-asan/`、`build-tsan/` 这样的目录，它们对应的是不同的 preset，
不是"上次编的东西忘了删"。

## 再跑起来

```bash
bash scripts/demo.sh
```

然后浏览器打开 `http://localhost:8800`。你会看到一辆车在 3D 场景里跑。

**如果这一秒没看到车，后面所有章节都读不下去。** 所以值得花五分钟排障：

| 症状 | 大概率原因 |
|---|---|
| 端口 8800 被占 | 上一次 demo 没退干净，`flowmond` 还在监听 |
| 页面能开但车不动 | 某个进程启动就崩了，链路上的 topic 没人发 |
| 浏览器白屏 | 前端依赖没打包好（见第 22 章讲的 CDN 断网事故） |
| 画面在抖 | 前端航位推算没跑起来（也是第 22 章） |

`tools/pipeline_check.py` 可以在不启动的情况下先做一遍离线检查——它读同一份
进程表，静态地把明显的配置错误挑出来。跑不动的时候先跑它，比盯着屏幕猜快。

## 进程表：这才是重点

启动时，`src/flow_launcher.c` 读的那份 JSON 决定了整个系统长什么样。默认的
`config/pipeline.json` 里有 **17 个进程**：16 个跑算法，加 1 个跑监控可视化。

按数据流从上游到下游读：

### 仿真优先的代价

注意默认配置里**没有 `slam` 进程**。位置来自仿真器直接写的激光帧，经 fusion 的
EKF 出来。真车模板 `config/pipeline_car.json` 里才有 `slam`，而且它跑的是
`ekf_slam`——一套和 fusion **不互相调用**的独立滤波器（`modules/adas_nodes/ekf_slam.h`
里的状态顺序都不一样）。

这个差异会一路影响到第 15 章：真车上没有仿真真值，超车时你在快车道还是慢车道，
**只**看 `fusion/localization`。仿真里被真值盖住的那条路径，真车上是唯一的路径。

这也是本书为什么说"仿真优先"而不是"仿真是全部"——你必须知道哪几条路径在默认配置
下是**空的**，否则调试时会把"这条话题没数据"误当成 bug。

### 六份进程表

仓库里有六份 pipeline 配置，按场景切换：

| 配置 | 场景 |
|---|---|
| `pipeline.json` | 默认仿真全栈 |
| `pipeline_car.json` | 真车，带 slam / 传感器驱动 / 执行器 |
| `pipeline_manual.json` | 手动驾驶 |
| `pipeline_sensor.json` | 只跑传感器 |
| `pipeline_cortex.json` | Cortex 硬件 |
| `pipeline_windows.json` | Windows 开发环境 |

**它们的进程名单不一样。** 后面章节里凡是写"默认配置下……"的，指的都是
`pipeline.json`。如果你换了配置，某个话题可能是空的——这不是 bug。

## 动手：改一个数，看它怎么动

不要只是"跑起来看一眼"。做一件小事：

1. `scripts/demo.sh` 跑起来，浏览器开着 3D 视图
2. 打开 `config/pipeline.json`，把 `behavior_planner` 的跟车时距参数改大

## 17 个独立的崩溃域

`flow_launcher` 默认跑单进程模式：把每个节点 `.so` `dlopen` 进同一个地址空间，逐个校验
ABI 版本、`init()`、`start()`。多进程模式是 `--multi`：fork 之后 exec 同目录下的
`flow_node_host`，一个节点一个进程。

差别不在性能，在**爆炸半径**：

| | 单进程（默认） | `--multi` |
|---|---|---|
| 进程数 | 1 | = `processes[]` 里的节点数 |
| 一个节点段错误 | 全部节点一起没 | 只带走自己 |
| 节点间通信 | 进程内总线直调 | 共享内存 IPC（第 07 章） |
| 谁发现节点死了 | 立刻，launcher 就是它 | 10s 之后拓扑图上变灰（第 08 章） |

**第三种选择**是"每个节点都单进程、只在真车上才隔离"。本仓库没选，`--multi` 是个纯开关：
默认给开发用单进程（少一层 IPC、日志串在一起好读），上车前打开。值得注意的是无论选哪个，
跨机都还是不可能——那一层的能力来自第 08 章末尾讲的 TCP 通道，不来自进程模型。

### 崩溃不会自动恢复

多进程模式里，launcher 拿到子进程 pid 之后只做两件事：退出时给所有还记着 pid 的进程发
`SIGTERM`，以及每 200ms 一次 `waitpid` 回收僵尸。**它不检查退出码，也不重启。** 一个节点
崩了，链路上游还在按它的频率发消息，下游照常订阅、照常等，等到自己的超时逻辑触发。整条
链路的恢复只能 Ctrl+C 重来。

单进程模式更极端：任何插件里的段错误会带走整个进程。但它有一个单进程独有的好处——**启动
失败是可见的**：`dlopen` 失败、找不到插件入口符号、ABI 版本不匹配、`init()` 返回非零，
四种情况都会打一条 WARN 然后跳过这个节点，其余节点照跑。于是"页面能开但车不动"这个症状
有一个非常具体的成因：某个节点被静默跳过了，而启动器照常打出"all nodes running"。

> 这里藏着一个不太好的性质：**启动器的成功判据是"我遍历完了"，不是"全部节点都活着"**。
> 看到那行成功日志的时候，应该顺手数一下前面 `loaded` 那几行是不是有 17 行。

节点之间按默认 300ms 的间隔错开启动。17 个节点就是约 5 秒启动时间，而这段时间的目的不是
"让 CPU 喘口气"，是**别让十几个节点在同一个毫秒里发 HELLO**——理由见第 08 章那个丢心跳
的现场。

## 仿真时钟不能快进

`flowsim` 是全系统唯一的逻辑时钟源：启动时把仿真时间设成 0，之后每个 tick 推进一个固定
步长。别的节点读的是这个逻辑时间，不是墙钟。

有一条实现细节决定了"快进"这件事根本无处下手：**推进逻辑时钟的函数在真实时钟模式下是
空操作**。把步长调大、或者让 `flowsim` 一帧多走几步，改变的都是"逻辑时间往前走了多少"，
不是"墙钟花了多少"。这两个量之间没有倍率关系可以调。

想跑得快只有一条路：回放倍速。它跳的是消息之间等待墙钟的那一段，不动任何节点看到的逻辑
时间戳。代价是破坏进程之间的相对时序——某个节点处理慢了那一下，倍速回放并不会等它。

仓库里踩过这个坑并且留了注释：Bag 回放时启动器**刻意不去驱动仿真钟**。仿真钟一旦被驱动，
所有节点的 `clock_now_us()` 就返回注入的消息时间戳，而 monitor 那个 60Hz 的拓扑导出因此
只导出一帧，3D 画面停在首帧——一个完全健康的过程被时钟源的选择搞成了"看起来卡死"。

> **作者立场**：我一开始觉得"1 秒的场景 10 秒跑完"这种想法很自然，直到发现它要求**每一个**
> 节点都不得用真实时间做排程。仓库现在的做法是"逻辑时间单一真源 + 加速只发生在等待处"，
> 看起来保守，但它让"同一份场景在单进程、多进程、回放三种模式下跑出同样的结果"这件事
> 成立。加速如果不能复现，它省下的时间会全部还给下一次排查。

## 改配置之前，先确认真源在哪

这个仓库里有两处"文档与代码谁是真源"的显式约定，都写在 `CLAUDE.md` 里，而 `CLAUDE.md`
自己的章节编号又以 `docs/BOOK.md` 为准。初学者最容易踩的坑，是**改了一个不是真源的东西，
然后困惑于"为什么没生效"**。

真源就两张表，没有第三张：

| 你想知道的 | 真源 | 不是真源 |
|---|---|---|
| 系统现在跑哪些进程 | `config/pipeline.json` 的 `processes[]` | 本书第 00b 章那张 ASCII 图、任何手写拓扑文档 |
| 某章讲的是第几章 | `docs/BOOK.md` 的编号 | 章节文件名里的数字前缀 |

所以改配置前的动作是固定的：先打开 `processes[]` 确认进程名和数量，再跑一次
`tools/pipeline_check.py`（它读的是同一份表），改完启动之后数 `loaded` / `started` 的行数。

跳过第一步，就会改到一份当前配置里根本不存在的东西——本章第一节那张进程表里少一个节点，
在你改的那个参数就永远不会被读到。跳过最后一步，就会在"改了没生效"和"改了但被静默跳过"
之间猜错方向，而这两者的排查路径完全不同。
