## 为什么需要这一张表

这本技术书按"一个问题一章"展开：01 章造对象、02 章拆 .so、08 章做状态机、13 章做定位 EKF、21 章做回归评估。
问题驱动的写法容易让人**读完一章就以为这是它的私事**，但实际工程里，同一颗钉子常常被三个不同的视角各敲一遍：

- 同一个卡尔曼滤波器，感知用它跟踪前车，定位用它算自车位姿；
- 同一座时钟服务，规划算法消费仿真逻辑时钟，仪表盘消费真实墙钟，Bag 回放引擎负责把两者搭起来；
- 同一种反射式状态机，行为决策拿来决定跟车还是变道，仪表盘拿来实时画出当前允许的事件。

这种"一个抽象多视角"的复用不是装饰，是**工程取舍被沉淀下来的结果**。它意味着：换一种实现往往要牵动好几章；写新节点时如果不先知道这一层，下笔就会重复造一份。

这张表的目的只有一个——让读者**读完任意一节都能跳到相关章节**。具体的代码细节交给源码和原章节；这里只负责"哪几章共用什么、按什么顺序读"。

## 怎么用这一张表

每一行包含四件事：抽象名字、出现在哪些章节、各章里的视角差异、推荐阅读顺序。

- 如果你正打算改一个抽象，先把"涉及章节"那一列扫一遍，避免漏改某个消费方；
- 如果你读完某章发现一个陌生名词（如 `ClockService`、`EKF`、`ReflectiveStateMachine`），去下面找它在哪几章被讲过，按推荐顺序从源头读起；
- 如果你只想知道"哪些章值得通读、哪些可以跳"，翻到文末的「作者建议」。

## 核心共用抽象表

### 时钟服务：ClockService（三层时间源）

系统里"一秒钟"其实有三种含义：算法要的逻辑时间、QoS 要的真实物理延迟、训练样本要的 Unix 绝对时间。
共用这一抽象的三层 API 在不同章节里被不同的人以不同的姿势消费。

- **06 章（09 时钟服务）**：唯一权威定义。逻辑调度时间 `clock_now_us()` 可被仿真注入，物理墙钟 `clock_now_monotonic_wall_us()` 用于延迟统计，绝对时钟 `clock_now_realtime_us()` 用于训练样本与对时。
- **05 章（12 Bag 录制）**：回放引擎在每帧重发前调一次 `clock_set_sim_time(msg.timestamp_us)`，把总线时间戳与逻辑时钟重新对齐；两帧间隔只能用 `CLOCK_MONOTONIC` 做差，否则 NTP 回拨就会让等待时间算成负值。
- **10 章（C++20 协程）**：协程里的 `sleep_us` 和控制循环里的 `co_await sleep_until(...)` 都消费这一层时钟，所以高负载下回放与实时两条路径都能拿到同一份"现在"。
- **11 章（调度器与绑核）**：`RateControl` 与 `LatencyTracker` 内部计时间戳全部走 `CLOCK_MONOTONIC`；`scheduler_set_params` 写频率上限时仍然用相对周期，不直接读墙钟。
- **21 章（验证关卡）**：故障速查表里点名——回归测试偶发失败往往是因为脚本用了真实 `time.sleep`，CI 机器一忙断言就超时报错；改法是把测试接到 `ClockService` 上跑离散逻辑时钟。

**推荐阅读顺序**：先 06 章读三层 API 的设计动机与踩坑故事，再跳到 05 章看回放引擎怎么用 `clock_set_sim_time` 注入，最后扫 10 / 11 / 21 章确认各消费方都在同一个语义里。

### 卡尔曼滤波族：KF、EKF 与它们的变体

滤波公式本身不难；难的是**同一个思想在两个不同语义的物体上各跑了一遍**，参数、坐标系、状态向量都不一样。

- **12 章（13 感知：从激光点云到目标）**：线性恒速 KF 跟踪障碍物，状态 `[x, y, vx, vy]`，`F` 常速转移、`H` 只观测位置；关联用匈牙利算法配对马氏距离。
- **13 章（14 定位融合：EKF）**：扩展卡尔曼滤波做自车定位，融合状态 `[x, y, v, heading, yaw_rate]` 走 CTRV（常速、常横摆角速度），SLAM 另有自己一套五维 EKF（`float`）。两个滤波器在不同文件里互不调用，但都进同一个 `fusion_node` 的三分支位置选择。
- **17 / 19 章**：行为决策和学习闭环会**消费**这两套滤波器的输出（`perception/tracked_objects`、`fusion/localization`），但自己不写滤波器。

**推荐阅读顺序**：先 12 章把 KF 五步流水线（预测 / 观测 / 增益 / 更新 / 协方差收敛）走一遍，再到 13 章看 EKF 在弯的运动方程上怎么用雅可比把直线近似拉直，最后回头看 17 章行为决策怎么把这两种输出当输入。混淆 KF 和 EKF 的代价很高——12 章用的是常速线性 KF，13 章是 CTRV 弯运动 EKF，混用 `Q` 矩阵会让车辆在弯道里冲出车道。

### 反射式状态机：通用模式 + 行为决策实例

状态机的核心不是"枚举状态"，而是**转移表（Transition Matrix）+ Guard + Entry/Exit + 环形历史**这一组原语。这套原语在工程里被多个层级复用：任务生命周期、行为决策、模式切换、仪表盘渲染。

- **08 章（04 状态机）**：唯一权威定义。`ReflectiveStateMachine` 把规则表、守卫、Entry/Exit、8 条历史都放在内存里，自带 `statem_can_event` / `statem_export_json` / `statem_dump_history` 三个在线自省函数。
- **19 章（24 端到端学习闭环）**：行为决策节点虽然用了一套自己的 8 态 FSM（巡航 / 跟车 / 变道 / 让行 / 掉头 / 急停 等），但**那一套也是反射式的**——这一点 08 章讲的转移表缺行、Guard 是纯函数两条速查表，在这里同样适用。
- **20 章（22 Flowmond 与 3D 可视化）**：仪表盘的"FSM State Visualizer"直接消费 `statem_export_json` 输出的拓扑，把当前状态、合法事件、历史栈画在浏览器里；不重画一份状态转移图。

**推荐阅读顺序**：先 08 章掌握"反射式"三字的全部含义；之后读 19 章时把它当成 08 章原语的一个大实例去对照；最后扫 20 章，确认你看到的状态机可视化来自同一个抽象、不是另起炉灶。

### 消息总线：Pub/Sub 的多视角复用

`MessageBus` 是这整个仓库的血液循环。同一段 `publish / subscribe` 在不同章节里担任完全不同的角色。

- **01 章（用 C 造一个对象）**：把 `MessageBus` 当成**被注入的依赖**——`TaskInterface` 的 `on_message` 钩子是事件响应的统一入口。
- **02 章（可插拔 .so）**：`NodePlugin::init` 由宿主把 Bus、Transport、Discovery、Scheduler 一起注入节点；插件不许出现 `extern MessageBus g_bus`，否则 L0 门禁会拦下来。
- **05 章（Bag 录制）**：Bag 录制挂总线全量话题；回放时再 `message_bus_publish` 灌回总线，对下游节点看起来和实时一模一样。
- **09 章（Discovery）**：Discovery 不直接收消息，只看节点在信标里**宣称**的 Topic，匹配后再由 discovery 帮两个进程自动建 IPC 通道——总线层面的连接依然走 `MessageBus`。
- **10 章（协程）**：`co_await next(topic)` 是 Bus 的协程包装；订阅变成"等一帧"这种直序代码。
- **11 章（调度器）**：DAG 依赖的拓扑排序靠 Bus 上的 topic 出现与否触发；调度器配 RateControl 时不动 Bus，只约束自己。
- **20 章（3D 可视化）**：`dashboard_bridge` 共享内存通道拿到的就是 Bus 的一份聚合（FPS、p99、丢包数），与原 Bus 拓扑解耦后单独推给前端。

**推荐阅读顺序**：01 章先理解 Bus 是被注入的而不是被全局 include 的；02 章再看 NodePlugin 怎么把 Bus 和 Transport 一起交出去；之后任何带 `co_await next` 或 `message_bus_subscribe` 的章节都能直接上手。

### 共享内存 IPC：跨进程通道

IPC 通道不是节点自己建的，而是 Discovery / 仪表盘桥接器统一搭起来的。

- **09 章（Discovery）**：`discovery_create_ipc_channels` 在本地节点两两匹配 Pub/Sub 时，**自动**建好深度为 32 的 POSIX 共享内存环形通道——节点只负责声明能力，不负责连通道。
- **20 章（3D 可视化）**：`dashboard_bridge` 和 `stats_bridge` 同样基于共享内存，把仪表盘 JSON 和 Topic 统计从算法进程零拷贝送到 `flowmond`。
- **05 章（Bag 录制）**：Bag 录制可以选择把多进程全量话题在同一台机器上按共享内存聚合落盘。

**推荐阅读顺序**：先 09 章理解"自动建通道"为什么重要（同一 Topic 反复被多个节点订阅时，谁来建），再看 20 章理解 dashboard_bridge 与 discovery 共享内存是同一层抽象。

### 插件契约：NodePlugin 与 ABI 门禁

所有节点都遵循同一份契约；契约变了，下游所有 `.so` 都要重编。

- **02 章（可插拔 .so）**：`NodePlugin` 结构体的定义与 `api_version` 首字段门禁；`RTLD_NOW | RTLD_LOCAL` 的 `dlopen` 标志选择；五种生命阶段（Unloaded / Loaded / Initialized / Running / Stopping / CleanedUp）。
- **10 章（协程）**：协程节点走 `CoroutineTask` 派生类 + `EXPORT_COROUTINE_TASK` 导出，但**底层仍是一份 NodePlugin**——协程只是 `execute` 步骤的一种风格。
- **11 章（调度器）**：`scheduler_register_task` 接受的是插件回调，与调度器内部 DAG 解耦。
- **20 章（监控）**：`flowmond` 不直接 dlopen 业务插件，但它通过 Discovery 信标消费每个插件的 `name / version / capabilities` 字段做拓扑渲染。

**推荐阅读顺序**：02 章从头读一遍契约定义与生命周期图；10 / 11 章只需要扫一眼"协程 / 调度器怎么挂到契约上"那一段。

### Bag 时序文件：录制、回放、训练、评估共享同一份数据

Bag v2 + MCAP 是这个系统里**唯一**承认的"事实容器"。它的消费者多到值得专门列一行。

- **05 章（Bag 录制）**：Bag v2 二进制 + MCAP 兼容；统一回放引擎按相对时延补偿重灌总线；`BagReader` 头部回填失败时做向前容错扫描。
- **06 章（时钟服务）**：Bag 回放引擎在每帧前调 `clock_set_sim_time`，让算法在确定性逻辑时钟里消费回放数据——这是 05 和 06 两章真正握手的地方。
- **19 章（端到端学习闭环）**：`data_recorder_node` 把训练样本落到本地 JSONL / Bag；同一条 Bag 既能被回放用于影子评估，也能被 `export_e2e_dataset.py` 转成 295 维特征离线训练。
- **21 章（验证关卡）**：`demo_evaluator` 的场景回放走的也是同一套 BagReader；L2 黑盒评估的输入可以是 Bag 回放，也可以是实时 demo。

**推荐阅读顺序**：05 章先掌握 Bag 格式与回放协议；06 章读懂回放时的时钟注入；19 章看训练样本怎么从 Bag 抽出来；21 章看 Bag 怎么再被回放一次用于评估。

### 评估与门禁：从秒级到分钟级的同一架阶梯

评估不是一个工具，而是一座**从 L0 到 L2 的阶梯**——每一级都不替代上一级，而是补上它抓不到的那一类故障。

- **21 章（验证关卡）**：权威定义。L0 是 `pipeline_check.py` 秒级静态门禁（30 项硬指标 + 架构铁律），L1 是 CTest / GTest 单元与集成测试，L2 是 `demo_evaluator.py` 3~5 分钟黑盒回归。
- **19 章（端到端学习闭环）**：`train_demo_model.py --strict-promote` 在 L2 之上再叠加一条"模型准入门禁"：碰撞=0、越界=0、Jerk 方差<1.5、C++ 推理<2ms。这条门禁直接复用 L2 的 `demo_evaluator`——评估器和学习闭环共享同一根评分尺。
- **02 章（插件系统）**：L0 门禁里点名"插件不许 `extern g_bus`"这条架构铁律。
- **11 章（调度器）**：`LatencyTracker` 是 L0 / L1 阶段快速暴露延迟抖动的低开销探针；统计本身也是评估指标的一部分。

**推荐阅读顺序**：21 章先读懂 L0 / L1 / L2 各自抓什么；19 章看训练闭环怎么在 L2 上再叠一层；02 / 11 章挑感兴趣的扫两段即可。

### 航位推算（Dead Reckoning）：后端滤波器 + 前端补帧器

同一个名字在前端后端各跑一遍，但各自的角色完全不同。

- **13 章（定位融合：EKF）**：当 `slam_node` 切到 `dead_reckon` 算法时，IMU 加速度积分推自车位姿，每轴每秒协方差加 0.05，到 1000 秒后协方差大到让 fusion 进入三分支的位置选择路径 2。
- **20 章（3D 可视化）**：前端 `app.js` 在收到 20~50Hz 服务端位姿之间，用速度 + 航向积分推 60FPS 平滑插值，再用 LERP 软对齐真实帧——避免画面一卡一抽。

**推荐阅读顺序**：13 章先读懂 dead_reckon 模式的协方差增长与何时被融合节点弃用；20 章再读前端插值的几何推导。两者不要混——后端滤波器是状态估计，前端插值是渲染平滑。

### CTRV / 运动学：定位 EKF 的运动学选择

运动学模型不是细节，是定位 EKF 正确性的前提。

- **13 章（定位融合：EKF）**：融合节点的 `ekf_fusion_predict` 走 CTRV（常速 + 常横摆角速度），加速度不进状态，只通过过程噪声 `Q` 让速度方差变大；SLAM 的 EKF 是另一套五维状态，靠 IMU 直接写 `omega`。
- **17 章（跟踪控制）**：横向控制用更简化的自行车模型或 LTV-MPC——这一章当前是 v1 归档，未必能直接对照，但读者应该知道"定位用 CTRV、控制用更简单模型"是有意为之的层级。

**推荐阅读顺序**：13 章先读懂"运动方程是弯的，雅可比把它在当前点拉直"，再去对照 17 章的简化模型。混用运动学方程是定位漂移的常见起点。

### JSON 序列化：全栈通信事实标准

消息总线载荷不是裸字节流，而是结构化 JSON；这一点在多个章节里以不同角色出现。

- **02 章（插件系统）**：`NodePlugin::init` 拿到的 `params_json` 字符串就是用 cJSON 解析的，**禁止** `strstr + sscanf` 手写。
- **13 章（定位融合）**：`FusionTask::run` 把 EKF 状态打成一行 JSON 发到 `fusion/localization`——下游行为决策订阅的是 JSON，不是 `Pose2D` 结构体。
- **09 章（Discovery）**：`statem_export_json` 把状态机拓扑导出为 JSON，给前端画图用。
- **20 章（3D 可视化）**：仪表盘消费的几乎所有字段都是 JSON；`dashboard_bridge` 把大 JSON 拓扑分块传输，前端再拼回。

**推荐阅读顺序**：02 章先学 cJSON 入口；13 章看 EKF 状态怎么打成 JSON 发到决策端；20 章最后扫一眼 dashboard_bridge 的分块协议。

### 依赖注入：禁止 `extern g_bus`

这条不是"一个抽象"，是**贯穿全书的铁律**。它保证单测能不启动完整 pipeline 而只跑算法。

- **01 章（用 C 造对象）**：`TaskInterface` 的所有方法都把 `TaskBase* self` 当显式参数，不去碰任何全局变量。
- **02 章（可插拔 .so）**：`NodePlugin::init(bus, transport, discovery, scheduler, params_json)` 把所有外部设施一次注入；插件内**严禁** `extern` 全局符号。
- **10 章（协程）**：`CoroutineTask` 构造函数拿 `TaskConfig`，协程运行期不再去碰任何全局总线句柄。
- **21 章（验证关卡）**：L0 门禁 `pipeline_check.py` 把"`extern MessageBus g_bus`"列为硬阻断规则。

**推荐阅读顺序**：这是设计约束，不是教程章节——任何写新节点的 commit 都必须先在心里过一遍这条铁律，再去看 02 章的依赖注入示例。

## 跨章节陷阱：只读一章会怎么误解

下面五个误解都来自"读 A 章但不读 B 章"的现实案例，作者本人也都踩过。

### 1. 误以为 EKF 只是定位的事

13 章把 EKF 当成定位的代名词；但 12 章的障碍物跟踪用的是**线性 KF**，状态 4 维、运动模型常速。把这两件事说成"同一个 EKF 做两件事"会立刻在弯道里翻车——12 章和 13 章的运动方程、`Q` 矩阵、协方差传播都不同。把 12 / 13 章连读一遍，再下笔。

### 2. 误以为评估只是离线

21 章的 `demo_evaluator.py` 看起来是离线的 3~5 分钟工具；但 19 章的模型准入门禁直接调用它——`--strict-promote` 一旦失败，新模型就不进 inference_node 的实时路径。评估器和学习闭环共享同一根尺，这条腿断了另一条腿就站不住。

### 3. 误以为状态机只是行为决策

08 章把反射式 FSM 写成"通用模式 + 实例"两层；但很多人只读到 19 章那个 8 态行为决策机就以为状态机只有行为决策用。事实是任务生命周期（`INITIALIZED → RUNNING → STOPPING`）、行为决策、模式切换、仪表盘可视化都在用同一套原语；甚至 21 章 L0 门禁也会校验转移表是否覆盖完整 `[State × Event]`。

### 4. 误以为 Bag 只是录数据

Bag 是 05 章的录制文件，看起来只是一个"事后回放"的工具；但它同时是 06 章时钟服务的回放驱动（`clock_set_sim_time`）、19 章训练样本的源头（`data_recorder_node` 落盘后被 `export_e2e_dataset.py` 转特征）、21 章回归评估的输入（`demo_evaluator` 跑场景也走 BagReader）。把 Bag 当成"录完看一眼"的工具，会错过它作为整个工程事实容器这一身份。

### 5. 误以为前端航位推算和后端 dead_reckon 是同一个东西

13 章 `slam_node` 切到 `dead_reckon` 时用 IMU 积分推位姿，是带协方差的正式状态估计；20 章前端 `app.js` 用速度 + 航向积分做 60FPS 插值，只是为了渲染平滑、不维护协方差。两者同名但语义完全不同——后端滤波器失效会让 fusion 进入三分支位置选择路径 2，前端插值失效只会让画面抖一下。

## 作者建议：哪几章必读、哪几章可跳

这本书的章节按"问题驱动"展开，但**不是每一章都对所有读者同等重要**。下面是按读者画像给的最小阅读集合。

### 三类读者画像

**学习者**（从头到尾按顺序读，10 周完成）——这一类读者可以直接顺着 BOOK.md 的卷一到卷五往下走，不需要这本交叉章节。

**工程师**（转行 / 入职，先搭环境再按需跳读）——按以下优先顺序：

1. **必读**：`02_plugin_system.md`（插件契约是所有节点的统一入口）、`08_state_machine.md`（通用 FSM 原语，被多个章节复用）、`09_discovery.md`（跨进程通道的自动建立，是规模化部署的关键）。
2. **强烈推荐**：`01_oop_in_c.md`（理解底座）、`05_bag_recording.md`（理解事实容器）、`06_clock_service.md`（理解三层时间）、`10_coroutine.md`（理解现代节点写法）、`11_scheduler.md`（理解 DAG 与绑核）、`21_demo_evaluator.py` 对应的 21 章（理解验证阶梯）。
3. **按需阅读**：`12_lidar_tracking.md`（感知算法入门）、`13_sensor_fusion.md`（EKF 细节）、`19_e2e_learning_loop.md`（学习闭环）、`20_flowmond_3d_vis.md`（可视化）。

**研究者**（专注算法验证）——优先 12、13、19、21 章；02、10、11 章作为"运行环境"速读。

### 通读两遍都嫌少的章节

只有 `08_state_machine.md`（通用反射 FSM）和 `09_discovery.md`（去中心化发现协议）值得通读两遍——前者是横向复用最广的抽象，后者是规模化的关键转折点。其他章节读完一遍后，按需跳读即可。

### 可以跳过的章节

`00_preface.md` 之外的元文件（`README.md` 等）只在写新章节前需要参照；`12_lidar_tracking.md` 与 `13_sensor_fusion.md` 在不碰感知与定位算法时可以只读引子和最后一节，跳过中间的具体公式推导。
