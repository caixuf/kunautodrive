# 第 18 章：控制指令最后过一遍谁的手

> **v2 范式章节**（2026-09 整治后保留）。本章保留低行号密度、真技术书
> 风格，参照 `docs/book/README.md` 写作风格约束与 `docs/book/09_discovery.md`
> 范式示范。v1 行号清单版本归档于 `docs/_archive/book_v1/17_safety_envelope.md`。

前 17 章的所有算法都只是「统计意义上的稳」：多项式规划偶尔吐 NaN，纯追踪
（Pure Pursuit）会看走眼，端到端学习模型（端到端模型）会偶发退化。这些异常
一旦原封不动地送到刹车和转向，就是一次事故。

KunAutoDrive 的做法是在控制节点和执行器之间插一道**安全闸门**，让所有指令
先过一遍物理合理性审查。本章讲清三件事：谁说了算（规则与模型的仲裁）、什
么时候踩刹车（TTC 的真实公式与方向感知）、上游卡死了怎么办（降级阶梯）。

在读之前，先说破：上一版这一章里的示例代码，几乎全是凭空写的。仓库里没
有 `is_obstacle_in_collision_corridor()`，教科书式的三级 TTC 阶梯不存在，
`safety/cmd` 这个话题也不存在。本章按真实源码重建，并明确指出与旧稿的几
处关键分歧。

## 一、闸门的位置和数据流

```
[control_node]    ──control/raw_cmd──┐
 PID + 横向级联                       │
                                      ▼
[inference_node]  ──inference/raw_cmd─┐
                                      ▼
                [ safety_control_node ]
                          │
   fusion/localization ──┤  1. 仲裁（规则 vs 模型）
   perception/obstacles ─┤  2. 指令包络钳位
                          │  3. TTC / 障碍物守卫
                          │  4. 降级阶梯执行
                          ▼
                      control/cmd
                  （+ safety/evidence）
                          │
                          ▼
              flowsim / actuator_pwm
```

闸门是默认配置下唯一一条合法路径，订阅的是 `control/raw_cmd`，不是
`control/cmd` —— 后者是它自己发布的。这意味着**任何节点如果绕过这一道闸
门直接发布到执行器，topic-contract-gate 会拦住**（参第 23 章）。

唯一的例外是手动驾驶模式：`config/pipeline_manual.json` 里没有
`safety_control` 节点，`manual_drive_node` 直接发布 `control/cmd`，整道闸
门被跳过。这是设计意图（人开车不需要自动驾驶的仲裁），但也意味着手动模式
下一条 NaN 指令可以直达执行器。

输出是另一个结构体（`ControlCmd`，20 字节），不是输入的 `ControlRaw`
（59 字节）。下游只该有能力做一件事，而不该有能力做别的事 —— 剥掉了所有
调试字段，新增了 `emergency_stop`。

## 二、仲裁：规则与模型谁说了算

这是整章最值得学的部分。KunAutoDrive 有一条端到端学习链路（参第 24 章）
会发布 `inference/raw_cmd`。同一条车上跑着两套控制源，安全节点必须回答：
**模型的输出，能信多少？**

仲裁器被刻意抽成纯函数（`safety_arbiter.{h,c}`），理由和 `pwm_map.{h,c}`
一样：节点内的纯逻辑如果塞在 `.cpp` 私有命名空间里，就只能靠测试副本覆盖，
副本漂移时 CI 不报。抽成 C 之后，单测直接编同一份实现。

仲裁的优先级链在 `safety_arbiter_apply` 里只有 60 行，但每一层对应一个
明确的安全命题：

| 优先级 | 条件 | 行为 | 计入干预 |
|---|---|---|---|
| **P0** | `rule_cmd == NULL` | 全零输出 | 否 |
| **P1** | 无新鲜模型 / 降级生效 | 规则全权 | **否** |
| **P2** | 转向偏离超 0.12 rad | 转向回退到规则 | 是 |
| **P3** | 规则制动 > 0.10 | brake 取 max，throttle 归零 | 是 |
| **P3′** | 否则 | throttle 上限 = max(规则, 0.85) | 否 |
| **P4** | 灯光 / 档位 | 规则优先 / 双闪取或 | 否 |

三个值得单独说的决策：

**决策一：降级的优先级高于模型。** P1 用「没有新鲜模型 OR 系统降级」统
一处理：一旦进入 L1 及以上，模型输出就被整体屏蔽。理由很直接 —— 降级
状态下系统的行为规范已经变了（禁止变道、限速），而模型是按全功能状态训
练出来的，它根本不知道现在处于降级。让它继续输出就是在执行一个过时的策
略。

**决策二：P1 不计入 `intervened`。** 这是 `intervened` 标志的语义定义：
它回答的是「我是否否决了模型」，而不是「输出和规则是否一致」。模型没上
线、降级生效时，输出确实等于规则指令，但**没有发生任何否决**。这个区分
让 `control/debug` 里 `ARBITER[MODEL]` 和 `ARBITER[OVERRIDE]` 两个标签
的语义保持干净 —— 如果把 P1 也算作干预，模型从未上线时日志会满屏
`OVERRIDE`，真正的否决反而被淹没。

**决策三：转向和纵向独立仲裁。** P2 只管 `steer`，P3 只管 `brake` /
`throttle`，两者互不影响。模型可以在纵向被否决的同时保留转向（反之亦然）。
横向和纵向的失效模式不同、风险不对称，不应该因为纵向超了就一票否决转向。

而且 P3 用的是**取最大值**而不是「规则赢」：制动是取或，不是取谁。规则
和模型都认为要刹车时，取更狠的那个。**纵向控制的错误代价是不对称的：漏
刹会撞车，多刹只是不舒服。**

### 一个真实的架构漏洞

仲裁器本身写得没问题，但调用它的那一行代码有一个 bug：消息驱动桥里取
出 `inference/raw_cmd` 时，若规则指令超过 100 ms 未到达，会走一个
`base_cmd` 分支直接送达 `apply_safety()`，**`safety_arbiter_apply` 根本没
被调用**。P2 的转向包络、P3 的油门上限、P1 的降级屏蔽 —— 在这条路径上全
部失效。

从频率上看这条路径并不罕见：`control_node` 是 40 Hz（25 ms 一条），100
ms 的去重窗口意味着正常运行时模型指令几乎总是被去重掉。但**一旦控制节
点卡住超过 100 ms，模型指令就会以每条直通，而此时系统恰恰是最需要仲裁
的时候**。

这个 bug 的危险性在于它和故障条件高度相关：**仲裁器在系统正常时工作得
很好，在系统出问题时反而被绕过。** 这是一个典型的「保护逻辑的失效模式
与它要保护的对象的失效模式相关」的设计缺陷 —— 排查方向：消息桥里的
`continue` 语句与 `base_cmd` 分支。

## 三、指令包络：NaN、限幅与钳位

### NaN 防护的两道防线

第一道在 `clamp`：IEEE-754 里 `NaN` 和任何值比较都返回 false。`clamp` 没
加防护时，`clamp(NaN, 0.0, 1.0)` 返回 **0.0** —— 「不刹车」。一次数值发
散（规划层吐了 NaN）会被安全层「温柔地」翻译成「松开刹车」。这是最坏的
失效方向：出错的不是刹车，是**刹车的解除**。

对 `steer` 同样危险：`clamp(NaN, -0.22, 0.22)` 会返回 `-0.22` —— 打死
一侧。

`if (!std::isfinite(value)) return lo;` 把两侧拉到了安全侧：刹车 0.0、
转向 −limit。但 **0.0 对刹车来说仍然不是安全侧**（安全侧应该是 1.0），
所以有了第二道：

第二道在 `publish_cmd`，在所有检查之后：**任一字段非有限 → 强制
`emergency_stop`**（brake=1.0, throttle=0.0, steer=0.0）。两道防线的分
工：第一道负责转向和油门（把 NaN 收敛到「不动作」），第二道专门兜住刹
车（把 NaN 转成「全力刹车」）。

### 三个包络限幅

| 量 | 巡航限幅 | 条件 | 说明 |
|---|---|---|---|
| `throttle` | `[0, 0.85]` | 倒挡 `[-0.85, 0.85]` | 负油门即倒车 |
| `brake` | `[0, 1.0]` | — | |
| `steer` | `[-0.22, 0.22]` | 低速(<3 m/s) `±0.18`；机动 `±0.62` | |

低速收紧转向（0.22 → 0.18）是一条实车经验：低速时转向机构的非线性
（齿隙、助力泵滞后）占比大，放大转向权限容易在小角度上产生大误差。机
动放宽到 0.62 rad 是为了容纳第 17 章讲的掉头弧（需要 0.60 rad 满舵）。

每一处修改都走 `set_changed`，它同时做两件事：**写值 + 置 `changed`
标志**。最后统一打标签：模式串里追加 `+SAFE`。所以实车日志里的
`ACCEL+SAFE`、`MRM+MANEUVER+SAFE`、`DATA_TIMEOUT+SAFE`，就是「安全层改
过这条指令」的证据。排查异常时第一件事就是看这个标签。

## 四、TTC：真实的公式与方向感知

### 一句话破除教科书式的分级响应

旧稿给过一张表：TTC > 3.0s 绿灯、2.0~3.0s 黄灯 + 预充液压制动器、
1.0~2.0s 橙灯 0.3g 减速、≤ 1.0s 全力制动。**这套分级在代码里完全不存
在**。仓库里没有「预充液压制动器」，`brake` 是归一化量不是 g，TTC > 3.0s
也不存在「绿灯」档位。

真实的阈值是 2.5 / 1.5 / 1.0 三个，但它们触发的不是三个「档位」，而是
三件不同的事：温和减速、强制 L2 降级、`brake = 1.0` 硬 AEB。

### 真实公式与四个门限

```
along  = 障碍相对自车的车头方向投影
lat    = |垂直分量|
clearance = along − 4.8   （4.8 = 车身长度 + 余量）
closing   = v_ego − v_obs_along   （相对速度）

TTC = clearance / max(0.1, closing)
```

四个门限，每一个都有理由：

| 门限 | 值 | 含义 |
|---|---|---|
| `along` | `[0, 35]` m | 车头前方，35 m 是感知上限 |
| `lat` | `≤ 2.3` m | 同车道判定（≈ 车道宽 3.5 m 的 2/3） |
| `closing` | `> 0.4` m/s | 接近速度太小时不报警（避免除出巨大 TTC） |
| `clearance` | `along − 4.8` | 把「碰撞」定义为「两车车头接触」 |

### 方向感知是显式修过的 —— 这是掉头返程踩的坑

旧实现用世界系 `dx = obs_x − ego_x` 判断「在不在前方」，在掉头返程
（车头朝西）时，「前车在 −x」恰恰意味着**前车在自己正前方**。用世界坐标
判断前后，等于把「前方」定义成「东边」——这个定义在车辆朝北时恰好正
确，在朝西时就完全错了。而掉头返程正是最容易发生追尾的时刻。

修复：把前方判据改为**沿车头方向投影 ahead + 沿向速度**，前进/返程统一。
这个修改的故事收录在 `docs/HANDOFF_2026-09-23.md` 的掉头返程 TTC 失效段
里。同样的方向感知在第 13 章的「感知预测」也讲了一次 —— 同一个坐标系
陷阱在感知侧的反应是「斜视目标被 DBSCAN 拆成多簇」，但根因相同：**用世
界坐标判断相对位置**。

### 三个阈值，三件不同的事

| 条件 | 动作 | 性质 |
|---|---|---|
| `risk_dx < engage_dist`（未锁定） | 触发制动 | 空间判据，看「够不够刹停」 |
| `ttc < 2.5` | 触发制动 | 时间判据，看「会不会撞上」 |
| `ttc < 1.0` 或 `dx<6.5 ∧ dy<1.9` | `brake = 1.0` | **硬 AEB** |
| `ttc < 1.5` | **L2 降级** | 不是刹车，是系统状态变更 |

**空间与时间双判据的必要性**：低速时停车距离很小（v=2 m/s 时只有 2.2 m），
感知要是丢一帧就漏报；高速度时停车距离可能超出 35 m 感知范围，TTC 判据
才是主力。两个判据互为补充。

### 制动力的连续 ramp 与迟滞

**触发门槛 0.5 m，释放门槛 2.0 m，中间 1.5 m 是迟滞带。** 如果两者相同，
前车停在恰好等于停车距离的位置时，制动力会「踩一下松一下」反复横跳。
制动力从 0.45（刚进入停车距离）线性升到 1.0（已在停车距离内或更近），
按 deficit 线性给：一上来就全力刹车是把 20 m 的可用距离在 2 秒内烧掉，
乘客和后车都受不了。

### 对向来车：闭合成速度

对向车的接近速度是**速度之和**而不是差。触发阈值 4.0 秒，比同向的 2.5
秒宽得多：两车以相对速度 $v_1 + v_2$ 接近，制动距离是 $(v_1+v_2)^2$ 量
级 —— 20 m/s 对 15 m/s 时相对 35 m/s，停车距离超过 120 米。如果等到
2.5 秒才反应，根本来不及。

### 横向穿越守卫：变道过半后豁免

横向守卫**只在有变道意图时触发**：`fabs(cmd.steer) > 0.08` 意味着车确
实在往旁边打；`ROAD_GUARD` 紧急回正时豁免，否则会把车锁死在错误方向。
更重要的是**只压「朝风险车方向」的转向**，且在风险车变负（已到侧后
方）后不再限制转向 —— 自然的回正转向「看似朝向风险车，实为正确的变道
收尾动作」。如果这里不做这个豁免，每次变道都必然被安全层误判。

### 机动硬碰撞：为什么必须单独写一条

巡航段的守卫全部被 `if (has_state && !maneuver)` 挡在外面。机动模式走另
一套完全不同的逻辑：注释里写得很直接 —— `min_vehicle_ttc` 在没有候选障
碍物时返回 `1e9`，但 `out_dx` 保持 `0.0`。而掉头轨迹的 `apply_safety`
里 `risk_dx` 会被当作「0 m 处有障碍」来用，直接导致**恒定全刹**。
2026-08-03 掉头测试两次死在这。

三个关键设计：

- **不用 TTC，用纯空间门限** —— 4.8 m 内才算；
- **方向随挡位翻转** —— `ahead = backing ? −lon : lon`，倒车时只看车后。理由是「倒车逃离前方障碍是腾挪的合法动作，不得拦截」；
- **施工区感知点被豁免** —— 施工区在感知里是「墙」，但对规划器来说它是「生成机动轨迹的边界约束」。把墙纳入倒车硬门，车后 4.8 m 内有墙就永久 `brake = 1`，机动会一直卡到 40 s TIMEOUT。

这条豁免是个精确但脆弱的划界：它依赖 `obs_type` 字符串精确等于
`"construction"`。感知侧一旦改了这个类型名，豁免会静默失效，掉头立刻
回到 40 s 超时。**而且这条豁免没有任何测试覆盖** —— 它藏在
`apply_safety` 里，无法单测。

## 五、降级阶梯：上游卡死了怎么办

`degrade_ladder.h` 把降级分成 L0~L3 四档：

| 等级 | 含义 | 触发 |
|---|---|---|
| **L0** | 全功能 | 默认 |
| **L1** | 禁变道、限速、加大安全余量 | 单节点超时 > 500 ms 且持续 150 ms |
| **L2** | MRM（最低风险机动）：车道内减速停车 | `ttc < 1.5` 或单节点超时 > 2 s |
| **L3** | 立即停 | 全链路超时 > 2 s |

监督者（Supervisor）按 20 Hz 滴答，检查所有节点超时，自动递进等级。恢
复必须经 `degrade_clear()` 显式完成 —— 不允许自动降级，避免系统在 L0↔L1
之间反复抖动。

### 两套互相独立的心跳监控

`health.h` 是一套完全独立的健康上报（`HEALTH_OK` / `DEGRADED` / `STALE`
/ `ERROR`），由每个节点在 `execute()` 循环里调 `health_heartbeat` 上报。
它和 `degrade_ladder` 的关系是：

- `health` 提供原始数据（每个节点最后心跳时间、错误计数、延迟分布）；
- `degrade_ladder` 把这些数据**翻译成系统级降级决策**；
- 安全层拿到的只是「`is_degraded()` 是否为真」和「原因码」，**不关心具体哪个节点超时**。

**一个重要的设计选择**：`HEALTH_STALE` 仅上报不动作（5 s 内无心跳标
`STALE`）。它不会自动触发降级 —— 降级由 `degrade_supervisor_tick` 决
定，且其触发节奏和 health 不一致（health 是被动观察，supervisor 是主动
检查 + 粘滞锁存）。两套机制各有用途，单点故障不会让整辆车黑屏。

### 粘滞锁存：防止 L0↔L1 来回跳

degrade ladder 有一个隐含但关键的属性：**只允许向更高风险等级迁移；恢复
必须经显式 `clear()`**。这避免了「上游暂时卡一下 → 进入 L1 → 上游恢复
→ 退出 L1 → 又卡一下」的抖动循环。但代价是：恢复路径上的「我是不是真
的好了？」判断必须由更高层做，不能由 supervisor 自己决定 —— 这就是为什
么手册强调「恢复路径要人/场景确认，不要自动清零」。

## 六、两条独立路径：一道闸门 + 一个学习闭环

第 24 章讲的端到端学习闭环是另一条独立路径：模型预测的
`inference/raw_cmd` 也走这一道闸门，**但它的仲裁优先级低于规则主干**。
这意味着学习闭环可以激进尝试（这是它的价值所在），但激进的后果是被安
全层裁掉 —— 这是它可以放胆尝试的前提条件。

把这件事反过来看：**安全闸门不是为「规则主干」写的，是为「边界」写的**。
无论未来再接入几条控制源（手写规则 / 学习模型 / 模仿学习 / 远程接管），
仲裁的规则都是一样的：先看降级、再看包络、再看纵向。**让边界成为不变
量**是这层抽象最值得借鉴的设计。

## 七、我们踩过的坑

**1. clamp(NaN, 0, 1) = 0（「不刹车」最坏方向）。**
规划多项式偶尔吐 NaN，安全层「温柔地」翻译成「松开刹车」——出错的不是刹
车，是**刹车的解除**。修复：`isfinite()` 显式判断 + brake 的 NaN 单独走
「全力刹车」分支。**经验之谈：任何用 `<` `>` 做数值边界判断的代码都要先
想 NaN 会走哪一侧**。

**2. 方向感知踩了世界系 dx 的坑。**
掉头返程（车头朝西）时，前车在世界 −x 方向，恰好在车头前方，但旧实现
按世界系 dx 判断「在不在前方」把它漏掉了 —— 返程同向防撞完全失效。
修复：沿车头方向投影 ahead + 沿向速度。**经验之谈：用世界坐标判断「相
对位置」时，先想象车头朝每个方向时的后果**。

**3. 掉头两次死在「TTC 返回 1e9 但 out_dx=0」。**
机动模式复用了巡航段的 `min_vehicle_ttc`，它没有候选时返回大数，但
`out_dx` 保持 0.0 —— 机动段被当作「0 m 处有障碍」处理，恒定全刹。
修复：机动段另写一套纯空间门限，不复用 TTC。**经验之谈：把工具函数
跨界使用时，先看它在边界条件下返回什么**。

**4. 施工区豁免是字符串精确匹配的。**
机动硬碰撞对 `obs_type == "construction"` 豁免，但这条豁免**没有任何测
试覆盖**。感知侧一旦改类型名（"construction_zone" / "barrier"），豁免
静默失效，掉头立刻回到 40 s 超时。**经验之谈：精确字符串匹配的安全
约束都要有「改名即失败」的回归测试**。

**5. 消息桥让保护逻辑在故障时被绕过。**
仲裁器在系统正常时工作得很好，在系统出问题时反而被绕过 —— 因为保护
逻辑的失效模式与它要保护的对象的失效模式相关。修复方向：把桥里的
`continue` 和 `base_cmd` 分支改成无条件调用仲裁器。**经验之谈：消息
驱动回调里所有的「捷径」都要在故障注入下重走**。

**6. `HEALTH_STALE` ≠ 触发降级。**
`health.h` 是被动观察，`degrade_ladder` 是主动检查 + 粘滞锁存。两套独
立的目的是单点故障不黑屏，但新人容易把 `HEALTH_STALE` 当成降级触发器
—— 它不会自己动作。**经验之谈：分层系统里每个层只负责自己的语义，
跨层协调要走显式 API**。

## 八、与行业坐标

| | Apollo | autoware.universe | Tesla（公开材料） | KunAutoDrive |
|---|---|---|---|---|
| 安全闸门位置 | control → canbus | control → vehicle | 域控 MCU | control → actuator |
| 多源仲裁 | 有 | 无（纯规则） | 无（纯模型） | 规则 + 模型 + 降级 |
| NaN 防护 | 分散在各模块 | 仅日志 | 真上是 CCDC 校验 | 两道防线集中 |
| 降级自动恢复 | 允许 | 允许 | 不公开 | 必须显式 clear |

Apollo 的安全模块是独立的 cyber RT 进程，与控制进程通过共享内存通信；
我们的安全节点是普通 `NodePlugin`，更轻但失去物理隔离。autoware 走纯
规则路线，学习模型要单独接 safety module；我们把规则与模型合并到一个
仲裁器，简化集成代价是失去独立的 rollback 通道。
