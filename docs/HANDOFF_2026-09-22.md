## 0. 一句话总结

抽出 `modules/adas_nodes/lidar_scan.{h,c}` 纯逻辑（3D 多层扫描 / 容量守卫 / 可达距离
推导 / 自持 RNG），顺带修掉**四个叠加缺陷**：单层扫描 z 恒 0、写点无容量守卫（会越界写）、
测距噪声 σ=0.08·range（33m 处 2.6m，把相邻车道的两台车糊成 width=17m 的"车"）、
以及**消费者侧的第二份 60m 量程门**（生产者发到 120m 也被整帧丢掉）。

实测（`urban_challenge` 45s，sensor 模式）：

| 指标 | 改前 | 改后 |
|---|---|---|
| 锥内识别率（真值限定在传感器 120°/120m 锥内） | 25.6% | **86.9%** |
| 每帧检出目标数 | 0.76 | **3.58** |
| 粘连大簇（width > 4m） | 21/25 | **0/118** |
| `perception_coverage`（官方口径） | 0.742 | **1.000** |

官方口径的 `recognition_rate` 仍 < 50% FAIL —— 但**这不是感知的问题，是度量的分母
问题**（见 §3.1）：只有约 27% 的真值实体落在前向 120°/120m 锥内，任何真实前向传感器
在该场景的上限就是 ~30%。

## 2. 四个叠加缺陷（含证据）

### 2.1 单层水平扫描：点云是一张平面（z 恒 0）

旧 `publish_raycast_points` 只发射方位射线、`p.z = 0.0f` 写死，AABB 求交也是 2D
（忽略 z）。后果：`ClusterBounds.min_z/max_z` 恒 0 → 无法做地面分割、无法用高度做
3D 分类；且**装在 1.8m 高处的水平射线物理上看不见 1.5m 高的车**。本次改为
"方位 × 仰角"的 3D 射线 + 3D AABB，点云有真实 z。

> 副作用（有意为之）：`channels=1` 现在语义是"单束在传感器水平面"，只会扫到高于安装面
> 的目标 —— 这是物理正确的结果，单测里用 3.0m 高的目标把"方位角几何"与"仰角可见性"
> 解耦后验证。

### 2.2 写点循环没有容量守卫（会越界写内存）

旧实现 `LidarPoint* p = &cloud.points[cloud.count]; ... cloud.count++;` **没有任何上限
检查**。`n_rays=240` < 容量 2048 时侥幸没炸；一旦提高射线数（尤其 42 个 actor 的
`lane_change_traffic`），命中数可以超过 2048 → 越界写栈/静态缓冲。本次在
`lidar_scan_generate` 里写满即停并把 `dropped` 上报（节点侧限频 WARN）。
单测 `test_lidar_scan_capacity_guard` 用 2048×32 根射线罩住整个 FOV 钉死该行为。

### 2.3 测距噪声模型错误：σ = 0.08·range（33m 处 2.6m）

旧代码注释写的是"σ=α·range"，直接把 `obs_noise_std_m`（0.08）当相对系数用。真实 LiDAR
测距噪声是 2~5cm 量级；0.08·range 在 33m 处就是 **2.6m**，而相邻车道中心间距只有 3.5m
（车宽 2m → 车间空隙 1.5m）—— 噪声足以把两台车糊成一个簇。实测证据（sensor 模式）：

```
ego=(169.7,-5.3)  真值：car id=1 (202.5,-1.75) / car id=2 (207.0,-5.25)
感知：1 个簇 (202.1,-3.07) width=17.12m  ← 两台车糊成一个
```

改为 `σ = noise_std_m + noise_rel·range`（默认 0.08m + 0.2%/m；120m 处 0.32m），
`lidar_noise_rel` 单列参数，`obs_noise_std_m` 回归其字面语义（绝对 1σ，与 mode=0 一致）。

### 2.4 ⚠️ 最致命：消费者侧有第二份量程门（默认 60m）

`perception_node.cpp:495` 有**自己的** `lidar_max_range_m = 60.0`（可被同名 param 覆盖），
`perception_points_from_cloud()` 用它把远处点全部丢弃。只在 `sensor_model` 上把量程提到
120m 时，**生产者发到 120m、消费者把 >60m 的点静默丢掉**，无任何日志。
修好后锥内识别率从 37.0%（噪声修完时）跳到 86.9% —— 这一步的收益最大。

这正是 CLAUDE.md 铁律里那条 **"同一功能出现第二份实现 = 违规，必须收敛到权威模块"**：
量程目前是"生产者参数 + 消费者参数"，两者必须同值，且**分歧时毫无信号**。

### 2.5 DBSCAN `eps=2.0` > 相邻车道空隙 1.5m

即使点云零噪声，`eps=2.0m` 也会把相邻车道的两台车连通。本次在 sensor 配置里把
`dbscan_eps` 收到 **1.2**（`dbscan_eps` 本身是可配 param，`perception_node.cpp:514`）。
配合 0.167° 方位分辨率（120m 处点距 0.35m < 1.2m）不牺牲连通性。

## 3. 两个度量伪影（**阻塞 Phase 2**，本次只量化未改）

### 3.1 识别率的分母不感知 FOV/量程

`demo_evaluator._compute_perception_metrics()` 对**所有**真值实体求分母，不筛选
"sensor 能不能看到"。实测该场景（33 帧）：

```
真值实体 9.36/帧，其中落在 ego 前向 120° FOV + 120m 量程内的只有 2.55/帧 = 27.2%
```

于是**任何真实前向传感器**的 evaluator 口径上限就是 ~27%。实测印证：
`recognition_rate_overall = 0.291` ≈ 锥内 86.9% × 27.2% + 噪声。

`ground_truth` 模式能拿 1.000，只因它把**全部**真值（含背后、含 800m 外的 actor）直通，
根本不存在"可见性"概念 —— 也就是说这个指标对 sensor 模式**结构性不公平**。

**要落地 sensor 门禁，必须先让分母锥内化**（按 ego 位姿 + FOV + 量程筛真值，或改用
"tracker 已确认航迹 vs 真值"的一致口径）。这是一次**度量语义变更**，按 2026-09-21b §14.3
的教训（"先量化伪影、再改门禁，顺序不能反"）应单独决策。

### 3.2 sensor 模式的簇 id 每帧都变 → 预警提前量恒 0

`perception_points.c::perception_clusters_to_obstacles()` 用
`ob->id = pose->frame_id * 100u + ci` 当障碍物 id → **每帧都是新 id**。预警提前量指标
（按 id 跨帧跟踪）因此恒为 0，实测 `warning lead time too short: min=0.00s (11 critical events)`。

上一 session（§14.1）在 ground_truth 模式用 `vehicle/state` 的 `oid%d` 修掉了这一点，
但**sensor 模式没有 oid 可用**。正确修法是让 sensor 模式也用跨帧稳定 id
（消费 `object_tracker` 的已确认航迹 id，或给簇做最近邻跨帧关联）。

## 6. 不要做的事

1. **不要**只改 `sensor_model.lidar_max_range_m` 而不改 `perception.lidar_max_range_m` ——
   消费者的量程门会把远处的点静默丢掉，现象是"改了没效果"（§2.4）
2. **不要**把测距噪声写成 `σ = k·range` 且 k 取 `obs_noise_std_m`（0.08）—— 33m 处 2.6m，
   相邻车道的车会糊成一个宽簇（§2.3）
3. **不要**在 sensor 模式下用 `dbscan_eps >= 1.5`（相邻车道中心间距 3.5m、车宽 2m）
4. **不要**在 `sensor/lidar_points` 上发 JSON 或别的类型（二进制契约是 `LidarPointCloud`）
5. **不要**用 `msg_init_typed(&struct, sizeof(struct))` 发 `LidarPointCloud`（见
   `HANDOFF_2026-09-21b.md` §3.2 的 msg_codegen padding 陷阱）
6. **不要**在 sensor 模式给 DBSCAN 开 RANSAC 地面去除（本模型不投地面回波，z 不是地面）
7. **不要**相信手写的 `docs/PIPELINE_ARCHITECTURE.md`（DEPRECATED），真拓扑看
   `config/pipeline.json` 的 `processes[]`

## 9. 追加（同日续）：识别率分母锥内化 ✅

§3.1 量化的那条度量伪影已修。改动面比预期小：**只动 `_compute_perception_metrics`
的真值枚举一处**，门禁判定 / 报告打印 / `--json-out` 都自动跟随 summary。

| 文件 | 改动 |
|---|---|
| `ci/evaluators/demo_evaluator.py` | 新增 `_node_params()` / `pipeline_perception_spec()`（返回 `(是否 sensor 模式, FOV, 量程)`，量程取生产者/消费者两处的 **min**）；`_compute_perception_metrics` 的 truth 枚举加锥内过滤 + 5 个新返回键；`score()` 在"sensor 模式但锥内化未生效"时打 WARN；两条识别率失败串改说 `observable truth samples` |
| `ci/evaluators/test_demo_evaluator.py` | +4 用例（锥外真值不计入分母 / **锥只在 sensor 模式武装** / 缺 ego 位姿退回旧口径并标记未生效 / 量程取 min），27/27 |

关键设计：
- **规格来自在跑的 config**，不写死常量 —— 锥内化的分母必须等于"这份 pipeline 实际能
  看到的范围"，否则改了 config 指标就失真。
- **锥只在 `perception.mode == "sensor"` 时武装**（`pipeline_perception_spec()`）。
  这一点是踩过坑才定下来的：第一版无条件锥内化，`scenario_regression --baseline`
  立刻冒出 2 个新 FAIL —— `city_comprehensive` / `multi_light` 只声明 1~2 辆车且**全程
  在视锥外**，锥内化后分母归零 → `INCONCLUSIVE [recognition_rate_vehicle]: cannot
  evaluate`，门禁从"虚满分"翻成"无法判定"，**两者都是错的**。正确口径是
  "分母 = 这份 pipeline 的**感知输入级**能知道什么"：sensor 模式吃点云、有 FOV/量程；
  ground_truth 模式直接吃 `vehicle/state` 真值、能"看到"的就是全部真值 → 不筛。
- **sensor 模式下缺 ego `y`/`heading` 时退回"全部真值"旧口径，但把
  `perception_observability_applied=False` 报出来并由 `score()` 转 WARN** —— 不允许静默
  退回旧口径（否则度量退化无人知晓，这正是本项目反复踩的坑）。老 series / 单测构造的
  样本没有这两个键，所以现有 3 条识别率用例的断言原样成立。
- 量程取 **min**：生产者/消费者各有一份量程门，链路实际能看到的是较小者。

实测（`urban_challenge` 45s，sensor 模式；数值随 flowsim 非确定性有小幅波动，两次跑分别为
0.958/0.875 与 0.931/0.944）：

| 指标 | 改前 | 改后 |
|---|---|---|
| `recognition_rate_vehicle` | 0.302 FAIL | **0.93 ~ 0.96** |
| `recognition_rate_vru` | 0.250 FAIL | **0.88 ~ 0.94** |
| `recognition_rate_overall` | 0.291 | **0.93 ~ 0.94** |
| 分母样本数（vehicle/vru） | 672 / 192（全部真值） | 217 / 54（**锥内**真值） |

`ground_truth` 对照组仍 `1.000`（它不做锥内化，分母就是全部真值）—— 注意两种模式的
分母语义**本就不同**（各自描述"该编排的感知输入级能知道什么"），所以不应横向比较绝对值，
但**每种模式内部现在都是公平的**：sensor 模式再也不会因为"看不到物理不可见的东西"被判漏检。

**sensor 模式剩下的唯一真 FAIL 是 §3.2（簇 id 每帧变 → 预警提前量恒 0）**；另一条
"vehicle stuck or no progress" 在真值对照组同样 FAIL（288m < 400m），是场景阈值问题，
非本次引入。

### 10.2 ⚠️ 推翻 §5.1 的一条判断：`lane_change_traffic` 不会撞簇数上限

实测该场景（45 帧样本，sensor 模式）：

```
truth 42.00/帧（全部 actor 都在 scene 里）  但同帧锥内真值只有 0.93/帧（2.2%），最多 2 个
perceived 1.16/帧，单帧最多 3       (DBSCAN_MAX_CLUSTERS = 32 → 从未接近)
锥内真值距离 min=8.6m p10=17.6m     (→ 单帧 2048 点预算从未顶；零 "lidar cloud full")
锥内识别率 92.9%；perception 零告警（无 "no fresh" / "DBSCAN overrun" / deserialize failed）
perceived 宽度 median=1.09m，>4m 的占 12/52（超车时邻车道两车偶有粘连，epsilon=1.2 边界）
```

原因：actor 是"两车道各 200m 等间隔、互相错位 100m"，而量程/视锥只有 120m/120° ——
**42 个 actor 里同时进视锥的最多 2 个**。所以 §5.1 那句"42 actor 撞 `DBSCAN_MAX_CLUSTERS=32`"
是按 actor **总数**而非"同时可见数"的推断，**是错的**。

要真正压这两个上限，需要的是"很多目标**同时**在视锥内"的场景（同车道近距离排队 /
密集交叉口），而不是"actor 总数大"。这是后续造难例场景的依据。

## 12. 追加（同日续）：预警提前量改按真值身份跟踪 ✅（§3.2 结案）

§3.2 修掉了。**两次换源才定下来**，过程值得记：

| 方案 | 结果 |
|---|---|
| 感知输出自己的 id（原状） | `perception/obstacles` 的 id 是帧内局部的（`perception_points.c` 的 `frame_id*100+ci`），每帧都变 → 提前量恒 0 且**凭空伪造** 11~16 个 critical event |
| 换成 `object_tracker` 的航迹 id | 提前量**均值**变成 6.66s（有救了），但 `min` 仍是 **0.00s** → 仍 FAIL。抓现场数据（73 帧样本）查因：12 个航迹 id 对应 9 个 actor，且两个"车"在 **14m / 16m** 处才首次出现（首次检测与临界同帧 → lead=0）。即这条路继承了**跟踪器的 id churn** |
| **按真值实体身份跟踪**（最终） | 仿真的真值 id 天然稳定；"检测到" = 本帧有感知输出落在该真值 `PERCEPTION_MATCH_DIST_M` 内；TTC 用该真值的前向距离 |

实测（`urban_challenge` 45s，sensor 模式）：

| 指标 | 改前 | 改后 |
|---|---|---|
| `warning_lead_min_s` | **0.00**（FAIL < 0.3） | **4.51** |
| `warning_lead_avg_s` | 0.00 | **14.16** |
| `critical_event_count` | 11~16（伪造） | **4**（真实事件） |
| `perceived_track_count` | 14（帧内 id 数） | **6**（被检测到的真值障碍数） |

sensor 模式现在**没有感知/预警类 FAIL 了**，只剩 `vehicle stuck or no progress`
（288m < 400m）—— 那条在真值对照组同样 FAIL（284m），是场景阈值/行为问题，与本次改动无关。

语义变化（有意，已写进 docstring 与单测）：
- 跟踪键从"某个内部 id"改成"障碍本身"，所以**幻影感知不再能造出 critical event**——
  本指标按真值定义障碍；假阳性导致的幽灵刹车属于**正精度**指标范畴，需要单独的门禁。
- 反之，真值障碍变成临界却**从未被命中** → 提前量 0（"完全没预警"），要 FAIL。
- 不依赖 `object_tracker` 是否存在了（原先为了拿稳定 id 必须依赖它），
  所以 `pipeline_manual.json` / `pipeline_car.json`（无跟踪器）也能算这一路。

单测 +4 例（真值身份跟踪 / 真值未命中 → lead 0 / 幻影不造事件 / 无临界事件），29/29。
