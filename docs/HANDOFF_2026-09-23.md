## 2. 根因一：空障碍物列表被当成"感知没就绪"（行为决策整块被跳过）

`modules/adas_nodes/behavior_planner_node.cpp` `on_raw_obstacles()` 原先：

```c
if (obs_list.count == 0) return;      /* ← 空列表直接返回 */
```

后果链：`has_obs` 恒 0 → `run()` 前置守卫（`if (!g.has_fusion || !g.has_obs) return;`）
把**整个决策块**跳过 —— 包括路端掉头触发（`UTURN_TRIGGER`）。而车还在动，
所以既有的量活性门禁（speed/x/heading/steer/lane_count 全部有值）**全绿**。

为什么只在 sensor 模式暴露：ego 起步背对路线（视锥 120° 内空无一物），
真点云链路"正确地"连着发**空** `perception/obstacles`；ground_truth 直通编排
一开始就有 19 个真值目标，所以 `has_obs=1` 从未缺席。同一 bug 在 `curve_road`
（该场景本就没有可观测 actor）**默认编排里也一直在发作**：见 §4。

**修法**：空列表是**合法感知结果**（视野内无目标），不是"还没数据"。
置 `obs_count=0` + `has_obs=1`，让决策在"无目标"这个真实状态下继续工作。

## 3. 根因二：清零的未用槽位在世界原点变成"幽灵障碍物"

`modules/adas_nodes/planning_node.cpp` `on_perception_obstacles()` 每帧把 128 个
槽位全部清零再填 `list.count` 个；但 TTC 跟车 / 窄路会车 / Frenet 避障注入 /
ST 图障碍四处循环**扫满 128 槽**，于是 `(0,0)` 被当成"世界原点有个静止障碍物"。
自相矛盾的是同一份数据在 `forward_space` 里有一条 `if (obs_x==0 && obs_y==0) continue;`
豁免 —— 一个文件里两套有效性语义。

影响面：ego 所在车道经过世界原点前后 80m 内就会**幽灵刹车**（真实部署里原点
可以是任意地图坐标）。**实测证据**（`straight_road`，两种编排都命中）：

```
# 修复前（默认编排 logs_gt、sensor 编排 logs_sensor 都在同一时刻出现）
TTC follow: gap=20.0 (src=percept) -> 3.7 m/s (was 20.0)
TTC follow: gap=19.7 (src=percept) -> 3.7 m/s (was 20.0)   ← gap 随 ego 逼近原点递减
TTC follow: gap=12.5 (src=percept) -> 1.9 m/s (was 20.0)
# 修复后（默认编排回归日志）
TTC follow: gap=77.1 (src=percept) -> 18.0 m/s (was 20.0)  ← 只剩 80m 外的真障碍物
```

ego 起步 x=20 朝 -x，世界原点恰在前方 20m 同车道 → (20−5)/4 = 3.7 m/s。
注意这条链在 `straight_road` 的**committed 基线**里同样生效（基线
`avg_speed_mps = 12.0` 是在被压到 3.7 m/s 起步的条件下测出来的）。

**修法**：引入权威计数 `g.obs_count`（与既有 `truth_obs_count` 对称），
四处循环改为 `i < g.obs_count`，并删除那条 `(0,0)` 补丁式豁免。

## 4. A/B：两个 FAIL 场景到底是谁造成的

方法：`git stash` 两处 C++ 改动 → 重建节点 → 跑场景 → 恢复 → 重建 → 再跑
（脚本 `~/.hermes/cache/scratch/ab_two_scenarios.sh`）。改动前/后各一次：

| 场景 | 改动前 | 改动后 |
|---|---|---|
| `curve_road`（默认编排） | FAIL —— **新门禁抓到 `behavior/state == "NA"` 全部 251 样本** + `exceeded max duration 62.7s` | FAIL —— **只剩** `exceeded max duration 62.8s`（行为已 CRUISE） |
| `lane_change_traffic` | PASS | 第 1 次 FAIL `min_forward_gap 4.80m < 9.27m`；第 2 次 PASS（`min_forward_gap 10.95m` WARN） |

两条结论，都写清楚以免下次误判：

1. **`curve_road` 的时长 FAIL 与本次改动无关**：改动前 62.7s、改动后 62.8s，
   同值；而 `curve_road` 提交在库的基线是 59.9s。这台机器（WSL，负载）比 CI
   慢约 2s 启动/收尾 → 这是**环境敏感的墙钟度量**问题（见 §6 待办 1）。
2. **`curve_road` 的 committed 基线是在 behavior 静默状态下采的**
   （`tests/baseline/curve_road.json` → `behavior_state: "NA"`, `behavior_obs_count: 0`）。
   也就是说该场景的"绿灯基线"由一台**行为决策已死**的车跑出来，且此前无门禁能看见。
   修复后它变成 `CRUISE`，行为判据照样 PASS，但基线语义已经过期。
3. `lane_change_traffic` 的跟车距离**本来就在判据阈值附近**（50% × desired 18.5m =
   9.27m）。去掉幽灵障碍物后更多时间落在 4.8–11m 区间 → 判定在 FAIL/PASS 间跳。
   当时的读法是"幽灵障碍物掩盖了 ACC 跟车过近"，**后续证伪**：见 §10 ——
   那几帧的 ego 速度只有 1.0 m/s（期望间距 6.5m），是判据用整段中位速度当参考
   造成的**度量误报**，不是跟车控制缺陷。

## 12. 追加：`max_duration_s` 按仿真钟判（同类度量伪影，已修）

`curve_road` 在**两种编排**下都只剩一条 FAIL：`exceeded max duration: 62.7s / 62.8s /

逐样本核对后发现判据量的根本不是"仿真跑了多久"：


`demo_evaluator` 的判据取自 monitor 的 `clock_now_realtime_us()`（墙钟，含 demo.sh

`summary` 增 `sim_duration_s`（`duration_s` 保留墙钟语义，基线兼容）；
墙钟超而仿真没超 → **WARN**（保留可见性，不再当成"没跑完"）。

- 单测：`test_demo_evaluator.py` +2 组（墙钟超/仿真正常→不 FAIL 但有 WARN；
  仿真真超→FAIL；无仿真钟→回退墙钟语义不变）→ **35/35**；

## 14. 追加：steer 速率判据的"单点擦线"伪影（同类于 §17.1，已校准）

**症状**：合并树（含 `8ff9bfd`）上默认编排 `straight_road` 首跑 **FAIL**：
`steer bang-bang oscillation: steer_rate_rms=0.58/s, max=6.25/s, flips=0.06/s`，
同代码随后两趟 **PASS**（max 3.88 / 3.76）→ 门禁在窄带里抖。

**根因（不是控制抖动）**：

1. 触发项只有 `max_steer_rate`。同一判据的另两个量全程健康：`rms 0.39~0.58`（FAIL 线 1.6）、
   `flips 0.06`（FAIL 线 2.5；真 bang-bang 复发时实测 9~10/s）。
2. 逐样本定位：最高的 5 对样本 `behavior/state` 全是 `U_TURN`，最大一对
   `Δsteer=0.9005 rad / dt=0.239s = 3.76/s`（`-0.3005 → +0.6000`）；`|steer|=0.6` 的 20 个样本
   全在起手掉头段。
3. ±0.60 是掉头的**合法量程**：`flowsim/physics.cpp:57-60` —— 正常行驶限幅 0.25 rad（≈14°），
   掉头 `steer_override` 放宽到 0.60 rad（≈34°）。三把方向 lock-to-lock 扫角在一个采样间隔内
   Δsteer≈0.9 rad 是机动自身动力学，不是控制每帧翻符号。
4. 该门禁**没有机动窗口概念**且取整段 max（旁边 excursion 判据会写 "expected for cross-road
   maneuver"）；它的 FAIL 文案也印错了阈值（打印 flip 线 2.5，实际触发的是速率线 6.0）。

**校准（用户拍板选"加佐证条件"）**：

- `max_steer_rate > STEER_MAX_RATE_FAIL` 现在需 `steer_rate_rms > STEER_RATE_RMS_WARN(0.9)`
  佐证才 FAIL，单点擦线只留 WARN；`rms`/`flips` 两条 FAIL 线原样不动（先例：yaw 判据要求
  `yaw_rms` 佐证）。
- FAIL 文案改为印**真正生效**的三条阈值。
- 不加机动窗口豁免、不抬 `STEER_MAX_RATE_FAIL`：前者会让掉头自身的控制质量失去覆盖，
  后者会把真的单帧跳变一起放掉。
- 新增门禁自检 `[22]`（掉头扫角不得误报）+ `[23]`（max>6/s 且 rms>0.9/s 仍必须 FAIL，
  防"改成永远 PASS"）。门禁自检 **35/35**。

逐趟定位 max|Δsteer|/dt 的样本对、dt、行为状态）；本轮 dump 分析见
