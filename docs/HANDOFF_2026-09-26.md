## 2. 关键设计点

### 2.1 Rule 4 容差：`SPEED_LIMIT_TOLERANCE_MPS = 0.01 m/s`

契约 `M1_OSM_INTERFACE_CONTRACT.md §2.5.2` 写 "单位 m/s，**2 位小数**"。2 位小数浮点的
表示精度 = 0.005，再加 0.005 epsilon 防 `0.005+0.005 != 0.01` 边界 → **0.01**。

- 10.00 vs 10.005（偏差 0.005）→ PASS（单测 `test_value_within_tolerance`）
- 10.00 vs 10.01（偏差 0.01）→ PASS（边界）
- 10.00 vs 12.00（偏差 2.0）→ FAIL（单测 `test_value_mismatch`）

**为什么不取更小**：M2 阶段 `speed_limit` 数据源是 road 级继承 + lane 级 override；
osm_test/osm_zhengdong 等大地图的数值是整数（如 13.89），不会触发更精细的边界。
M3 真接 Lanelet2 后若数值精度提至 3 位小数，本常量同步缩到 0.001 + 注释更新。

### 2.2 Rule 5 用 count 而非 set

map.json 的 `landmarks.stop_lines[]` 每条 item 没有唯一 id，只有 `lane` 字段指向 lane_id；
理论上同一 lane 可以有多条 stop_line（直行停止线 + 左转停止线）。所以 Rule 5 校验**数量一致**
而非"set 覆盖"，单测 `test_count_match` 验证 lane_a 有 2 个 stop_line、osm 也写 2 个 → PASS；
`test_count_mismatch` 验证 map.json=1 vs osm=2 → FAIL。

### 2.3 `parse_regulatory_elements` 与 `parse_lanelet_osm` 并存

两条解析路径**互不重叠**：

- `parse_lanelet_osm()`：只挑 `type=lanelet` → Rule 1/2/3（车道 relation）
- `parse_regulatory_elements()`：只挑 `type=regulatory_element` → Rule 4/5（交规 relation）

契约 `M1_OSM_INTERFACE_CONTRACT.md §7.3` 明确说 "D2-09 gate 只收 type=lanelet 的 relation，
regulatory_element 完全跳过"——但 §7.3 是 D2-08 **M2 之前**写的；M2 起 gate 必须也收
regulatory_element（否则 Rule 4/5 失守）。本期把 §7.3 的语义收窄："D2-09 gate 收 lane
（Rule 1/2/3）+ 收 regulatory_element 的 speed_limit/stop_line（Rule 4/5），
traffic_light 由 D2-02 转换器自测守"。**§7.3 的更正文案留给 M3 step 2 收口时合并入契约**。

### 2.4 8 个 maps 一次性生成 → 单测为什么能稳

```bash
for d in maps/*/; do
  [ -f "$d/map.json" ] && [ ! -f "$d/lanelet.osm" ] && \
    python3 tools/json_to_lanelet.py -o "$d/lanelet.osm" "$d/map.json"
done
```

osm_zhengdong 跑一次 5.4s、6.0s（生成 63MB .osm），其它地图秒级。**全部 8 个一次过**，
转换器单测 `test_11_byte_stability_with_regulatory_D2_08` 验证字节级确定性。
