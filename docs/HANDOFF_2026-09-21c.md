> 接力 `HANDOFF_2026-09-21b.md`：收尾排查前端车不动、后端在动、手动接管加速有速度显示但车不动的问题。

---

## 0. 一句话总结

- **根本原因排查与修复完成**：
  1. `src/core/monitor_server.c` 存在**短连接描述符泄漏**与**缺少空闲超时**：`dispatch_request` 返回 `false` 时未调用 `close(fd)`，而 `handle_client` 误以为已被关闭，导致每个非 keep-alive 短请求（以及浏览器关闭连接）永久泄漏一个处于 `CLOSE-WAIT` 状态的 socket；
  2. 原 `MONITOR_MAX_CLIENTS = 8` 极其脆弱，现代浏览器并发加载静态资源直接打满连接池，导致前端核心的 SSE 流（`/api/stream`）被拒（HTTP 503）或阻塞；
  3. SSE 断流使得前端 3D 渲染无法接收到新的车辆世界坐标与姿态，画面冻结；
  4. 手动接管（Game Mode）时，`POST /api/game/control` 虽然正常送达后端 `flowsim` 推进物理积分，且前端 HUD 高频轮询展示了速度，但由于 3D 渲染帧依赖 SSE 流喂送数据，导致用户看到"有速度显示但车不动"；
  5. 此外，接管时相机会切到 `driver`（驾驶员座舱内视角向前看），若外部场景缺乏流式位姿驱动，车体本身不可见且环境静止。
- **修复方案落地**：
  - 引入 `finish_response(fd, client_keep_alive)`，在连接非 keep-alive 时显式 `close(fd)`，消除描述符泄漏；
  - 9 处请求分支统一接入 `finish_response`；
  - `handle_client` 增加 5 秒 keep-alive 空闲超时与每 500ms 巡检退出机制；
  - 设置 socket 读写超时 `SO_RCVTIMEO` / `SO_SNDTIMEO`；
  - 并发连接容量从 8 扩至 64。
- **全量验证通过**：
  - `ctest` 34/34 100% 全部通过；
  - 4 项 CI 静态门禁全部通过；
  - `bash scripts/demo.sh 10 --no-browser` 成功跑通，端口 8800 与进程干净退出。

### 核心改动对照

| 模块 / 项 | 改动前 | 改动后 | 修复目的 |
|---|---|---|---|
| 并发客户端上限 `MONITOR_MAX_CLIENTS` | 8 | 64 | 容纳浏览器静态资源多路并发与长连接 SSE |
| 非 keep-alive 连接清理 | `return client_keep_alive;`（未调 `close`） | `return finish_response(fd, client_keep_alive);`（显式 `close`） | 根治描述符泄漏与 `CLOSE-WAIT` 堆积 |
| HTTP/1.1 空闲超时 | 永久阻塞在 `read(fd)` | 5 秒 `select()` 超时循环，每 500ms 检查服务退出 | 杜绝浏览器连接池常驻耗尽服务端槽位 |
| Socket 读写保护 | 默认无超时 | `SO_RCVTIMEO` / `SO_SNDTIMEO` 设为 5 秒 | 防止网络挂死或死锁 |

## 2. 根因深度还原

### 2.1 描述符所有权错位（Ownership Mismatch）
在 `monitor_server.c` 的旧实现中：
```c
/* handle_client() 中：*/
bool ok = dispatch_request(fd, ms, req, n, accept_enc, keep_alive);
if (!ok) return; /* dispatch_request 已 close(fd) */
```
注释假设 `dispatch_request` 在返回 `false` 时一定会关闭 `fd`。然而在所有 GET 静态文件和 JSON API 的末尾：
```c
return client_keep_alive;
```
当客户端请求 `Connection: close`，或者客户端是短连接时，`client_keep_alive == false`，函数直接 `return false`，但**完全没有执行 `close(fd)`**。
结果就是每个短连接完成响应后，该 socket fd 在进程内泄露，保持在 `CLOSE-WAIT` 状态直到进程被杀。

### 2.2 前端冻结与接管"有速度车不动"的因果链
1. 浏览器打开 `http://localhost:8800`，发起 index.html、js、css 以及若干 API 请求；
2. 由于 `MONITOR_MAX_CLIENTS = 8`，几个短请求后所有 8 个线程槽位全部被卡死在 `CLOSE-WAIT` 泄漏或空闲阻塞中；
3. 前端随后发起 `new EventSource('/api/stream')`，服务端拒绝连接或挂起；
4. **自动驾驶视角**：因为没有 SSE 消息推送，`app.js` 的 `eventSource.onmessage` 不触发，`updateAll()` 和 3D 渲染无法获取新姿态，主车停在初始位置；
5. **手动接管视角**：
   - 用户点击"接管车辆"，进入 `gameMode`，相机自动切到 `driver` 座舱视角；
   - 按 W 加速时，前端通过定时器 `updateGameControl()` 向 `/api/game/control` 发送控制指令；
   - 后端 `flowsim_node` 接收到了指令，更新了物理模型积分，主车速度增加并在内部发布；
   - HUD 的速度显示有轮询或在接管循环中读取了部分状态；
   - 但是 3D 场景的位姿完全由 SSE 驱动（`topoData.metrics.scene.ego`），SSE 处于断流重试状态，因此 3D 场景中车辆的坐标未发生任何改变，呈现"有速度显示但车不动"的诡异现象。
