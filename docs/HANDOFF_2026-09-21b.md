## 3. 本次挖出的关键问题

### 3.1 `sensor/lidar_points` 早有二进制契约，JSON 是冲突的

`msg/adas_msgs.msg:59-64` 定义了 `LidarPointCloud`（2048 点、含 `time_offset_us`，
给 deskew 用），`slam_node.cpp:543` 就是按它 `LidarPointCloud_deserialize` 的。
上一 session 的 e86ea5b 却在这条 topic 上发 ad-hoc JSON —— slam 收到必然解失败，
`config/pipeline.json` 声明的 `"type":"JSON"` 也是错的。已改回二进制（§2 表）。
**教训**：新增 producer 前先 grep topic 名，看有没有既有消息契约/消费者。

### 3.2 `msg_codegen` 的 padding 陷阱 —— 20 个类型里 12 个尺寸不一致 ⚠️ 最大发现

生成器的 `_struct_size()` 是**字段尺寸直接相加**（= 期望的线格式尺寸），但生成的结构体
**没有 `__attribute__((packed))`**。只要字段排列产生对齐填充，两者就不等：

```
LidarPointCloud   声明 40980 / sizeof 40984      ObstacleList  4368 / 4632
PredictionSet     3068 / 3088                    Trajectory    2581 / 2592
PredictionHypothesis 1017 / 1020                 Localization  57 / 60
GpsData           36 / 40                        ImuData       36 / 40
Obstacle          34 / 36                        Pose2D        29 / 32
Behavior          22 / 32                        ControlRaw    59 / 60
（审计脚本：解析 build/gen/*.h 的 "size=NB" 注释 vs sizeof，见 §6）
```

于是仓库里并存两套互不兼容的约定：

| 约定 | 语义 | 代表用法 |
|---|---|---|
| 线格式 | 紧密排布，`*_serialize`/`*_deserialize` | perception 发 `ObstacleList`、slam 收点云 |
| 内存布局 | 自然对齐，`msg_cast`/`msg_init_typed(&T, sizeof(T))` | `_msg_cast_impl` 的 legacy 分支就是按 `sizeof` 比对 `data_size` |

同一 topic 的生产者/消费者**必须成对使用同一套**，否则静默错位。今天各 topic 靠
约定侥幸一致；`LidarPointCloud` 是第一个踩中的（无人用过这个类型）。

本次的踩坑现场（两处都已在 01a1cc2 修）：
1. producer 用 `msg_init_typed(..., &cloud, sizeof(cloud))` 发内存布局 → 对端按线
   格式读 `count`，读到的其实是 `timestamp_us` 的高 32 位。仿真时钟 <2³² µs 时高
   32 位恒 0 → `count=0` → 点云静默为空（无任何错误日志）。
2. consumer 用 `msg->data_size < sizeof(LidarPointCloud)` 当长度门槛 → 线格式
   40980 < 40984，每帧都被当"太短"丢掉（表现为 "no fresh sensor/lidar_points" 刷屏）。

**根治建议（需要单独决策，本 session 不动）**：codegen 给结构体加
`__attribute__((packed))`（或让 `_struct_size` 计对齐）。代价：12 个类型的 ABI 变化，
可能影响录制回放（`pem`/`mcap`/`bag`）、`flowmond` 前端与 `tests/baseline`。
建议顺序：先加一个"每个生成类型 `sizeof == 声明 size`"的 CI gate 暴露现状 →
再评估是否 pack。**注意 pack 会让 `uint64` 落在非对齐偏移**，ARM 上取值需
`memcpy` 语义（x86 无碍）。

### 3.3 DBSCAN 的 RANSAC 地面去除在 z=0 点云上"点数相关"地失效

真点云只有障碍物命中点、没有地面回波（z 恒 0）。`ransac_fit_ground()` 会把 z=0
拟合出来、命中 100% 内点 → 整帧清空 → 0 聚类。但它的候选平面预筛要求
`quick_count >= 20`，而采样只在 `min(50, n)` 个点上做：

- `n >= 20`：真的会拟合出 z=0 并把点全清掉；
- `n < 20`（含 `n < 10` 直接返回 -1）：地面去除**静默失效**，点活下来。

即同一辆车 8m 处（约 30 点）会消失、30m 处（约 8 点）反而可见 —— "看不见近处、
看得见远处"。所以 sensor 模式改用 `GROUND_REMOVE_NONE`（`dbscan_set_ground_mode`），
并留了回归用例 `test_perception_ground_remove_none_rationale`。
**代价**：这条路径不再做地面分割；将来 producer 补 elevation/地面回波时应重新评估。

### 3.4 `demo_evaluator` 的识别率/预警指标是"真值自比"，测不出感知

`_compute_perception_metrics()` 用的是 `series[i]["obs_world"]`，而它来自
`scene.obstacles`，`monitor_node.c:1530` 是从 **`vehicle/state` 真值** 构造的
（`perception/obstacles` 只进 `g.latest_obstacles_json`，没进 scene）。

实测对照：`urban_challenge` 的 baseline（ground_truth）与本次 sensor 模式跑出来的
`recognition_rate_vru/vehicle = 1.000`、`perceived_track_count = 9` **完全一致**。
所以：

- `recognition_rate_*` / `warning_lead_*` / `perception dropout` 目前**不能**用来
  判断感知链路好坏；
- 要真正评估 sensor 模式，得先把 `scene.obstacles` 换成 `perception/obstacles`
  （或让 evaluator 用 monitor 的 `latest_obstacles_json`）。这是一个独立且有价值的
  P1：现在 CI 的"感知 100%"是自证。

自证闭环的 consumer 侧已接通并端到端验证（sensor 模式 demo 与场景评估都过，默认
